# 0014.4. `ghx-sidecar` Benchmark: LLM-as-Judge Trajectory Evaluation

## Context

ADR-0014.3 delivered the `ghx-sidecar` MVP. The first A/B benchmark
(`benchmarks/bench.ts`, committed `2641a9e`) validated that the harness runs
correctly end-to-end but used deterministic precision/recall scoring against a
hardcoded file list.

The first run exposed the scoring model's failure modes immediately:

- Agent A (with sidecar) found `src/compose.ts` **and** `src/hono-base.ts` — both
  correct and relevant. Deterministic scoring penalized it for "low precision"
  because `src/hono-base.ts` wasn't in the ground-truth list.
- Agent A produced a structured `<ghx-report>` with verified/inferred claims,
  evidence citations, commands run, and uncertainty. Agent B produced prose.
  The scoring treated these as equivalent.
- Agent B searched the local package filesystem before reaching the remote repo —
  a silent failure. The scoring did not penalize it.

Precision/recall on file paths measures one narrow signal: did the agent mention the
right filename? It cannot measure whether the agent:

- understood what the code does
- cited actual evidence from `ghx read` output
- made good tool decisions (search before read, stop before over-reading)
- followed an efficient path to the answer
- carried context across turns

These are **reasoning** and **judgment** — the two things the sidecar was built to
improve. A benchmark that cannot score them is not validating the hypothesis.

### Prior art survey

Before committing to a custom approach, the open-source eval landscape was surveyed.

| Framework | What it measures | Why it doesn't fit |
|-----------|-----------------|-------------------|
| **τ-bench** (Sierra, 2024) | Multi-turn tool-agent-user interaction; scores database state transitions against goal state; introduces `pass^k` reliability metric | Python, domain-specific (retail/airline), not a reusable library |
| **τ²-bench** (2025) | Dual-control environments where both agent and user use tools | Same constraints as τ-bench; telecom domain |
| **AgentEvals** (LangChain) | Tool call trajectory evaluation; scores whether agent called right tools in right order | Python, LangChain-native; trajectory scoring concept is directly borrowable |
| **Inspect AI** (UK AISI) | Full agentic eval framework: `Task → Solver → Scorer` pattern, multi-turn, LLM-as-judge scorers, sandboxed execution, VS Code log viewer | Python only; strongest framework in the space but wrong language |
| **Braintrust / autoevals** | LLM-as-judge via `autoevals` library; TypeScript-friendly; agentic trajectory eval | Requires Braintrust platform API key for the judge LLM; doesn't plug into ACP harness |
| **Evalite** (Matt Pocock, 2025) | TypeScript-native, Vitest-based, LLM-as-judge scorers, trace capture | Requires direct API key for the scorer LLM; no ACP integration |

**The common constraint:** every existing framework assumes direct API access for the
judge LLM. This project runs agents through the `acpx/runtime` ACP harness using the
engineer's locally installed agent (Codex, Claude, Kiro) — no raw API token is
available.

### Borrowed concepts

From **τ-bench**: the `pass^k` insight that single-run scoring is unreliable. A
correct-looking answer on one run may reflect luck on query formulation, not reliable
competence. Implication: the benchmark should support multiple trial runs.

From **AgentEvals / τ-bench**: **trajectory scoring** — score the path, not just the
destination. An agent that stumbles to the right answer through a chain of
wrong queries and unnecessary file reads is worse than one that finds the answer
efficiently. The tool call sequence is part of the evaluation signal.

From **Inspect AI**: the `Task / Solver / Scorer` separation. The evaluation task
(scenario), the system under test (agent A or B), and the scoring logic (judge) should
be independent. A scenario should be re-runnable against any combination of
solver and scorer without modification.

## Decision

Replace deterministic scoring with **LLM-as-judge evaluation** using the existing
`acpxSend` harness. No new dependencies. The judge is a third ACP session that
receives both agents' traces and scores them on three dimensions.

### Architecture

```
benchmarks/
  scenarios.ts   — Scenario registry (declarative data, no logic)
  judge.ts       — JudgeReport types, prompt factory, trace formatter, parser, runner
  bench.ts       — A/B harness entry point: run agents, capture traces, call judge, print
```

**Data flow:**

```
Scenario (id, repo, turns, judgeContext)
  ↓
runWithSidecar()  →  AgentTrace (turns, toolCalls, filesFound, finalAnswer)
runWithout()      →  AgentTrace
  ↓
createJudgePrompt(scenario, traceA, traceB)
  ↓
acpxSend({ session: "bench:judge-<runId>", prompt: judgePrompt })
  ↓
extractJudgeReport(<judge-report>{ ... }</judge-report>)
  ↓
JudgeReport (agentA scores, agentB scores, verdict, summary)
```

### Judge evaluation dimensions

Three dimensions, each scored 1–10 with a written rationale:

**reasoning** — Does the final answer correctly explain the implementation? Are claims
backed by evidence from actual `ghx read` outputs, not plausible-sounding inference?
Is uncertainty acknowledged where appropriate? Does the agent carry question context
across turns (turn 2 should build on turn 1)?

**judgment** — Did the agent make good decisions about which files to read and which
to skip? Did it avoid over-reading (tests, examples, unrelated files)? Did it identify
the most relevant files without being given a hint?

**trajectory** — Did the agent follow an efficient path: search before read, narrow
before expand, stop when evidence was sufficient? Penalizes: calling `--help`
unnecessarily, wrong query formulation that fails and requires retry, reading
files that turn out irrelevant, redundant commands covering the same ground, failing
to find the key file within budget.

Trajectory scoring is borrowed from the AgentEvals / τ-bench concept: the tool call
sequence is evidence of the agent's planning quality, not just the final answer.

### Why the judge runs via acpxSend

The judge is a text-reasoning task: given two traces, evaluate them against a rubric.
No tool use is needed or desirable. The judge prompt explicitly instructs the agent not
to call any tools.

`acpxSend` with `permissionMode: 'deny-all'` enforces this at the runtime level: any
tool call the agent attempts will be silently denied. The judge cannot accidentally
reach out to `api.github.com` to verify claims in the traces.

The judge uses a fresh session key (`bench:judge-<runId>`) per run, ensuring no
cross-contamination from prior evaluations.

### Scenario registry design

Scenarios are pure data — a `readonly` array of `Scenario` objects in `scenarios.ts`.
Each scenario carries:

- `id` — stable identifier, used as CLI arg (`npx tsx benchmarks/bench.ts hono-middleware`)
- `repo` — the GitHub repo under investigation
- `turns` — the sequence of questions sent to each agent
- `judgeContext` — a description of what a correct answer looks like, visible only
  to the judge, not to the agents under evaluation

The `judgeContext` field is the critical design choice: it gives the judge a reference
answer without hardcoding file names into scoring logic. The judge can weigh partial
credit, note what was missing, and explain its rationale in plain text.

### AgentTrace capture

Both agents are instrumented via `onEvent` and `onReport` callbacks in `acpxSend`:

- `text_delta` events accumulate into per-turn response text
- `tool_call` events accumulate into per-turn tool call lists (commands the agent ran)
- `onReport` captures the structured `SidecarReport` from Agent A's `<ghx-report>` output

Agent A's trace is structurally richer because it emits a `SidecarReport`. Agent B's
trace is reconstructed from raw text and tool call events. The judge receives both
traces in the same format.

### JudgeReport schema

```typescript
interface DimensionScore {
  score: number;      // 1–10
  rationale: string;  // one sentence explaining the score
}

interface AgentJudgement {
  reasoning:  DimensionScore;
  judgment:   DimensionScore;
  trajectory: DimensionScore;
  overall:    number;  // arithmetic mean, rounded to 1 decimal
}

interface JudgeReport {
  agentA:  AgentJudgement;
  agentB:  AgentJudgement;
  verdict: 'A' | 'B' | 'tie';
  summary: string;
}
```

The judge outputs this schema inside `<judge-report>` XML tags, parsed by
`extractJudgeReport()` using the same regex pattern as `extractReport()` in `acpx.ts`.

## What Is Not Built

- **Multi-trial averaging**: a single run is scored once. `pass^k` reliability metric
  (from τ-bench) would require N independent runs per scenario. Out of scope for now.
- **Persistent verdict storage**: judge results print to stdout only; not saved to
  `~/.ghx-sidecar/bench/`. Future work.
- **Cross-model judge**: the judge runs on the same agent (e.g. Codex gpt-5.5) as the
  agents under evaluation. Self-evaluation bias is a known weakness. A different judge
  model would require a second ACP agent configuration.
- **Adversarial judge prompting**: the judge rubric is fixed. No chain-of-thought forcing,
  no multi-agent debate (MAJ-EVAL style). Single-pass judgement is sufficient for now.
- **Automated scenario expansion**: one scenario (Hono middleware) is included. New
  scenarios are added manually to `scenarios.ts`.

## Open Questions

- Should verdict results be saved to disk so multiple runs can be compared?
- Should the bench support `--trials N` to run each scenario N times and report
  mean ± stddev scores, addressing τ-bench's `pass^k` reliability concern?
- Should a second judge agent be configured to reduce self-evaluation bias?
- Should `judgeContext` include the ground-truth file list, or remain prose-only to
  avoid anchoring the judge on filenames?
- Is trajectory scoring too correlated with reasoning to be a distinct signal?
  After several runs, check whether the three dimension scores consistently differ.

## Consequences

### Positive

- Reasoning and judgment are now first-class evaluation signals, not proxies.
- The sidecar's structured `<ghx-report>` output is directly rewarded by the judge
  rubric — a correct design incentive.
- A plain agent that stumbles to the right file through wrong queries will now score
  lower on trajectory than a sidecar that finds it efficiently.
- Scenarios are declarative and reusable — adding a new scenario is a data entry in
  `scenarios.ts`, not a code change.
- The judge harness reuses `acpxSend` with no new runtime dependencies.

### Negative

- LLM judge scores have variance: the same traces may score differently across runs.
  This is intrinsic to LLM-as-judge and cannot be fully eliminated without multi-trial
  averaging.
- The judge and the agents under evaluation share the same model (e.g. Codex).
  A model evaluating its own output family may be systematically biased.
- `judgeContext` prose is harder to version and audit than a deterministic file list.
  A poorly written `judgeContext` can mislead the judge.

### Neutral

- The deterministic file extraction from Agent B's text is kept as a secondary
  informational display but no longer drives the verdict.
- The bench CLI interface is unchanged: `npx tsx benchmarks/bench.ts [scenario-id]`.
