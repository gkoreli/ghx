# 0030.1. Session Routing — the Main Agent Never Sees Sessions

## Status

Accepted; v1 implemented 2026-07-06 (see Implementation Notes).
Governs NORTH_STAR workstream **B7** (session routing) toward the
capability §4 end state: "the sidecar routes each incoming question to the
right active session internally — the main agent never knows sessions exist;
it just talks to ghx." Depends on ADR-0030 B6 (shipped: the daemon owns the
session registry, D5). This ADR does not change scoring, detectors, eval
gates, or the measurement stack.

A precision on "never sees sessions": the end state removes session
*management* from the caller, not session *visibility*. Sessions stay fully
visible in `~/.ghx` and in the artifacts footer — NORTH_STAR §3 makes the
main agent a first-class consumer of that audit surface. What disappears is
the obligation to name, pick, and thread sessions correctly before asking.

## Context

ADR-0030 D5 moved session resolution inside the runtime boundary as
`ResolveSessionName` (`internal/sidecar/runtime.go:459-468`): explicit
`session` wins, then the repo slug, then a question-derived slug. That was
deliberately labeled "B7 groundwork," and it has a hole exactly where B7
lives — the repo-less question:

- `QuestionSlug` (ADR-0019.1 D2, `internal/cli/sidecar.go:411-417`) appends
  the first 8 hex chars of the question's SHA-256. Distinct questions never
  collide — by design — which means **every repo-less follow-up creates a
  fresh session** unless the caller re-passes `session` by hand. Ask "which
  Go libraries do structured concurrency", then ask "how mature is the
  second one" — the second ask lands in a brand-new empty session, blind to
  the ledger, reports, and warm ACP conversation the first ask built.
- The signals to do better already exist per session: `meta.json` carries
  `Repo`, `Scope`, `TurnCount`, `UpdatedAt` (`internal/sidecar/session.go`);
  `ledger.json` carries `RelevantFiles`, `GrepPatterns`, `MappedGlobs`,
  `InspectedPaths`, and — crucially — `OpenQuestions`, which is the union of
  every prior report's `uncertainty` and `nextReads`
  (`internal/sidecar/ledger.go:104-112`). A session's ledger is literally a
  vocabulary of what that investigation is about, plus the model's own
  prediction of what gets asked next.
- ADR-0031 (anticipation research) independently arrives at the same
  machinery from the other direction: serving an anticipated answer requires
  matching an incoming question to stored per-session state, and its
  sequencing note says 0031.1 "should check whether one resolver serves
  both." This ADR answers that: one matching primitive, two policies (D6).

The stakes of getting routing wrong are asymmetric in a specific way. A
question routed to a **new** session when it belonged to an existing one
loses continuity — annoying, recoverable, the status quo today. A question
routed **into the wrong existing** session pollutes that session's ledger
(`UpdateLedgerFromTurn` merges its report and traces into shared memory) and
injects an off-topic turn into a live ACP conversation. Wrong-existing is
strictly worse than wrong-new. Every threshold below is set with that
asymmetry, and D5 makes the residual mistakes cheap.

## Decision

Route inside the daemon with a **deterministic, ordered signal cascade**
whose every decision is explainable from logged inputs. No LLM and no
embedding model in the routing path for v1 (considered and rejected below).
The recon consumer surface starts treating `session` as an advanced override
on a deprecation path, not a routine parameter.

## D1. The routing cascade

`ResolveSessionName(req)` grows into `RouteQuestion(req, registry) →
RouteDecision`, evaluated top to bottom; the first rule that fires wins and
is recorded as `source`:

| # | Rule | Routes to | `source` |
|---|---|---|---|
| R1 | `session` explicitly provided | that session | `explicit` |
| R2 | `repo` provided, or an `owner/repo` token appears in the question text | the repo-slug session for that repo (created if absent) | `repo` |
| R3 | question carries a continuation marker (D2) **and** exactly one session was updated within the continuation window | that session | `continuation` |
| R4 | best ledger-overlap score (D3) ≥ threshold **and** leads the runner-up by ≥ margin | the best-scoring session | `overlap` |
| R5 | otherwise | new discovery session (`QuestionSlug`, unchanged) | `new` |

Rules R1 and R2 preserve today's behavior byte-for-byte (ADR-0019.1 D2
precedence; ADR-0030 D5), so repo-scoped callers and the eval runner (which
always passes explicit sessions) see zero change. R3–R5 replace the
unconditional question-slug fallback and are the substance of B7.

R2 deliberately keeps routing repo-scoped questions to the repo-slug
session even when explicitly-named sessions for the same repo exist and are
more recent. Named sessions are deliberate isolation — "parallel
investigation threads" is their documented purpose — and auto-injecting
un-addressed questions into them is exactly the wrong-existing pollution D5
exists to undo. They are reachable only via R1. (Revisiting this with
overlap scoring restricted to same-repo sessions is a v2 candidate, gated on
dogfood evidence that the repo-slug default actually loses wanted context.)

## D2. Continuation fast path (R3)

The hard case inside the hard case is the follow-up that shares almost no
vocabulary with its session: "how mature is the second one", "what about
its tests", "and error handling?". No overlap scorer can catch these —
"the second one" names nothing. But they carry surface markers of anaphora:

- leading connectives: "and", "also", "what about", "how about", "then",
  "ok so", "now";
- bare pronouns/deixis with no repo or code identifier in the question:
  "it", "that", "this one", "the first/second/third one", "those", "them";
- short length (a handful of content tokens after stopword removal).

The marker list is a fixed, versioned table in code — testable, auditable,
extendable from dogfood evidence. R3 fires only when the marker test passes
**and** the candidate is unambiguous: exactly one session updated within
the continuation window (default: the daemon's warm-worker TTL, 30 minutes
per ADR-0030 D4 — "the session you were just talking to is still warm" is
the honest meaning of "continuation"). Two warm sessions → R3 declines and
the question falls through to R4/R5; recency alone must never pick between
live topics, because interleaved multi-session callers (the normal agent
shape) would ping-pong pollution between threads.

## D3. Ledger-overlap scoring (R4)

Deterministic lexical scoring, no model calls:

- **Question tokens:** lowercase, split on non-alphanumerics, drop
  stopwords and tokens shorter than 3 chars.
- **Session vocabulary,** weighted by how strongly a hit indicates "this
  investigation": `OpenQuestions` tokens ×3 (a hit here means the session
  *predicted* this question — `nextReads`/`uncertainty` are the model's own
  follow-up forecast, the same seed signal ADR-0031 identified for
  anticipation); `RelevantFiles` path segments and `GrepPatterns` ×2;
  `Repo` segments and `Scope` tokens ×2; `InspectedPaths`/`MappedGlobs`
  segments ×1.
- **Score:** weighted overlap normalized by question token count, so short
  questions aren't penalized and long questions can't win on volume.
- **Candidate set:** sessions with `UpdatedAt` within the routing window
  (default 7 days — ledgers persist, and yesterday's discovery thread is a
  legitimate continuation target even though its worker went cold). A
  recency decay multiplies the score so an equally-overlapping fresh
  session beats a stale one.
- **Accept gate:** score ≥ `route.overlap.threshold` **and**
  (best − runner-up) ≥ `route.overlap.margin`. Both are config values under
  the standard scope ladder; defaults chosen conservatively (initial values
  proposed at implementation, pinned by the decision-table tests) because
  of the wrong-existing asymmetry: when in doubt, R5.

R5 (new session) is the explicit safe default, not a failure. It is exactly
today's behavior, and D5 makes a missed join recoverable, whereas D5 also
exists because a false join is the expensive branch.

## D4. Consumer surface: `session` becomes an override, then leaves the recon tool

Three phases, each gated on evidence, not calendar:

1. **v1 (this ADR):** the recon MCP tool and CLI keep accepting `session`
   (R1 compat — it is also the mis-route correction lever, D5). The tool
   description and recon skill stop *recommending* it: the parameter is
   re-documented as "advanced: pin a specific session; normally omit — ghx
   routes for you." `handleRecon`'s local session defaulting
   (`internal/cli/serve.go:172-182`) is deleted; the daemon routes.
2. **Deprecation:** after a dogfood cycle shows routing precision holds
   (D7), the recon tool marks `session` deprecated in its description.
3. **Removal:** `session` is removed from the recon MCP tool (and any A2A
   surface) — the §4 end state. The **CLI keeps `--session` permanently**:
   control mirrors visibility (NORTH_STAR §3), and the human operator's
   ability to pin, inspect, and correct sessions is a product feature, not
   a compat shim. "The main agent never sees sessions" is a statement about
   the agent surface, not the operator surface.

## D5. Mis-route recovery

The ledger is a derived structure: `UpdateLedgerFromTurn` computes it from
per-turn report artifacts and traces, and every entry carries the turn that
added it (`LedgerEntry.Turn`). Reports are stored per turn
(`reports/<turn>-<ts>.json`, with `ActualCommandLedger` capturing observed
commands). So a polluted ledger is not a corrupted database — it is a cache
that can be rebuilt by replaying the surviving turns' artifacts.

Recovery mechanisms, cheapest first:

1. **Immediate caller correction:** re-ask with explicit `session` (R1).
   The wrong session still holds the stray turn; see (3).
2. **Route transparency makes mis-routes catchable at the moment they
   happen:** the artifacts footer and CLI stderr line grow the route
   provenance — `session: honojs-hono (routed: overlap 0.62, next 0.21)` —
   so both the agent and the human see where the answer came from before
   they build on it.
3. **`ghx sidecar sessions reroute <from> --turn N --to <session|new>`:**
   moves turn N's report artifact (and turn-attributed trace/log records)
   to the target session, then rebuilds both ledgers by replaying their
   remaining per-turn artifacts through `UpdateLedgerFromTurn`. What cannot
   be moved is the ACP conversation's memory of the stray turn; the command
   therefore also clears the source session's `ACPSessionID`, so its next
   turn takes the ADR-0027 stale-session path — a fresh ACP session seeded
   from the now-corrected durable ledger. Existing machinery, reused: this
   is exactly the recovery shape ADR-0027 built for dead sessions, pointed
   at a deliberately-retired one.
4. **Daemon RPC `ghx.sidecar.Reroute`** exposing (3) to programmatic
   callers, so a main agent that notices a mis-route can correct it without
   shelling out.

Rebuild determinism becomes a stated invariant with a test: replaying a
session's `reports/` artifacts must reproduce its `ledger.json` (modulo
`UpdatedAt`). If implementation finds trace-derived entries that per-turn
report artifacts don't capture, the fix is to enrich the per-turn artifact,
not to weaken the invariant.

## D6. One matching primitive, two policies (relationship to anticipation)

Routing (B7) and anticipation serving (B9/M8, ADR-0031) share the
question-understanding layer: tokenization, normalization, weighted
vocabulary overlap against stored state. Implement it once (e.g.
`internal/sidecar/match.go`) with two consumers:

- **Routing** matches a question to a *session* and tolerates moderate
  confidence, because D5 makes mistakes recoverable and R5 is a safe
  fallback.
- **Anticipation serving** matches a question to a *stored answer* and
  needs much higher confidence plus a provenance/freshness gate (ADR-0031
  "similarity is a candidate gate, not an accept gate") — serving a wrong
  answer instantly is a trust failure with no R5 to fall back on.

Shared scorer, separate thresholds and separate accept logic. Routing ships
first and hardens the primitive under dogfood; 0031.1 inherits it rather
than inventing a second matcher. This also pre-commits the upgrade path: if
the lexical scorer ever gets replaced (embeddings, LLM tie-break), both
consumers upgrade together and both keep their own accept policies.

## D7. Observability and verification

**Every route decision is a logged, recomputable record** (visibility
tenet). Per turn:

```text
ghx.sidecar.route.source        # explicit|repo|continuation|overlap|new
ghx.sidecar.route.score         # best overlap score (R4 paths)
ghx.sidecar.route.margin        # best − runner-up
ghx.sidecar.route.candidates    # top-3 "session=score" pairs
ghx.sidecar.route.window_hit    # continuation window state (R3 paths)
```

emitted as trace attributes in the existing ADR-0030 D7 namespace, echoed
as a route record in the session's `logs.jsonl` and the daemon log, and
surfaced to humans via the CLI stderr line / artifacts footer (D5.2). Given
the record and the session states at decision time, the route must be
recomputable by hand — that is the falsifiable form of "explainable."

**Routing decision table unit tests.** Table-driven fixtures — question ×
on-disk session states → expected `(session, source)` — covering at
minimum: explicit wins over everything; repo slug unchanged; `owner/repo`
token detection in question text; continuation marker with one warm
session (hit), with two warm sessions (declines to R4/R5), with zero
(declines); overlap above threshold with clear margin; overlap above
threshold with thin margin (R5); OpenQuestions-hit outweighing
path-segment noise; short anaphoric question with no overlap (R3 or R5,
never R4 false-positive); punctuation-only question; window-expired
sessions excluded. The table doubles as the pinned specification of the
thresholds — changing a default means changing a visible test row.

**Dogfood protocol** (quality evidence, visible-not-citable, same stance
as ADR-0019.1 D5): one dogfood cycle with routing live, every repo-less
ask routed by the daemon. Weekly audit reads the route records and marks
each decision right/wrong; mis-routes and their kind (false join vs missed
join) go to FRICTION.md. Acceptance bar for D4 phase 2: **zero false joins
into explicitly-named sessions** (structurally guaranteed by R1/R2 — a
violation is a bug), no unexplainable route records, and at least a
handful of organic `continuation`/`overlap` hits proving the feature earns
its complexity. No live eval gate: routing is deterministic Go, and the
measurement stack is untouched; if implementation shows prompt-visible
behavior shifts (a follow-up landing in a ledger-rich session changes the
built prompt), a sidecar-only spot check per the standing eval cadence
applies at that time.

## Considered and rejected

- **LLM router in v1.** Rejected (as pre-registered in the task framing,
  and on the merits): routing runs before every turn, so it must be ~free
  and instant — a model call adds seconds and dollars to every ask to
  solve a problem the deterministic cascade handles for the common shapes.
  Worse, it fails the visibility tenet's falsifiable form: an LLM route is
  not recomputable from the logged inputs, so a disputed route can't be
  audited, and its failure modes don't shrink to a testable table. The
  evidence bar to revisit: dogfood route records showing a class of
  repo-less questions that R3/R4 systematically miss *and* whose correct
  session a human can identify from the same inputs — then an LLM
  tie-break confined to the ambiguous band (R4-declined, multiple warm
  candidates), fully traced with prompt and answer, per the escalation
  pattern of ADR-0024. Not before.
- **Embedding-similarity router.** Rejected for v1: new dependency
  (embedding model, local or API), the GPTCache failure modes ADR-0031
  documents (fixed thresholds serving semantically-wrong near-misses;
  model change invalidating all stored distances), and no evidence yet
  that lexical overlap is insufficient — ledgers are built from paths,
  patterns, and the model's own next-question forecasts, i.e. unusually
  literal vocabulary. Deferred behind the same evidence bar as the LLM
  router; if adopted, it lands inside the shared primitive (D6) so
  anticipation inherits it.
- **Status quo — question-slug per ask.** Rejected: it is the B7 gap
  itself. The SHA-256 suffix guarantees fragmentation of every repo-less
  conversation; follow-ups pay full cold cost and lose the ledger.
- **Sticky-last-session (route on recency alone).** Rejected: correct only
  for single-threaded callers. An agent interleaving two investigations —
  the normal case B6 was built for — would cross-pollute both ledgers.
  Recency gates candidates (R3 window, R4 decay); it never selects alone.
- **Per-caller routing identity (route within the connecting client's own
  recent sessions).** Rejected for v1: the daemon's entrypoints (CLI, MCP,
  future A2A) have no uniform caller identity, and inventing one adds
  protocol surface before dogfood shows cross-caller confusion actually
  happens. Noted as the natural refinement if it does.
- **Overlap-routing repo-scoped questions into same-repo named sessions.**
  Rejected for v1 (see D1/R2): named sessions are deliberate isolation;
  auto-joining them is the expensive failure mode. Revisit with dogfood
  evidence of lost context.
- **Merging sessions instead of routing between them.** Rejected: merge is
  destructive and unauditable; routing plus D5 reroute keeps every turn's
  provenance intact.
- **Dropping CLI `--session`.** Rejected permanently: operator control
  mirrors visibility (NORTH_STAR §3); it is also the correction lever D5
  depends on.
- **Confirmation prompt before routing ("did you mean session X?").**
  Rejected: re-introduces session awareness to the caller — the exact
  thing B7 removes; transparency-after (route provenance in the footer)
  plus cheap correction beats permission-before.

## V1 scope

In scope: the R1–R5 cascade in the daemon (replacing `ResolveSessionName`'s
fallback); continuation marker table; overlap scorer as the shared
primitive; route provenance in traces/logs/footer/stderr; decision-table
unit tests; ledger rebuild invariant + test; `sessions reroute` command and
`Reroute` RPC; recon tool/skill re-documentation (D4 phase 1); config knobs
(threshold, margin, windows) under the standard scope ladder and covered by
the daemon config digest (ADR-0030 D6).

Out of scope: LLM/embedding routing (rejected above, evidence bar stated);
anticipation serving (0031.1 — it consumes D6's primitive); `session`
parameter removal (D4 phase 3, evidence-gated); per-caller identity;
cross-`GHX_HOME` routing; any eval scoring, gate, or measurement-stack
change; daemonless-path behavior change (daemonless asks keep today's
resolution — routing state lives in the daemon by ADR-0030 D5, and the
fallback path stays dumb-but-correct).

## Implementation Notes (v1 slice 1, 2026-07-06)

Implemented per this ADR in `internal/sidecar/match.go` (D6 shared
primitive), `route.go` (D1-D3 cascade), `reroute.go` (D5 recovery), with
wiring in `runtime.go`, `daemon.go`, `emit.go`, and the CLI/MCP surfaces.
Decisions made while building, in the ADR-mandated "what actually happened"
form:

- **Pinned defaults (D3 "proposed at implementation"):** overlap threshold
  **0.5**, margin **0.25**, continuation window **30m** (= warm TTL),
  routing window **7d**, linear recency decay 1.0 → 0.5 across the window.
  Score = weighted overlap over UNIQUE question tokens (range [0,3]; one
  OpenQuestions hit in a 6-token question scores 0.5 — exactly at
  threshold). The decision table in `route_test.go` is the pinned spec;
  `TestOverlapScorePinned` keeps the arithmetic hand-checkable.
- **Named sessions are excluded from R3 and R4 candidacy**, not only from
  R2's preference. D7's acceptance bar ("zero false joins into
  explicitly-named sessions — structurally guaranteed") only holds if no
  auto-join rule can reach them; R1 is their single entry. To make that
  structural, `SessionMeta.NamedBy` now records the naming origin
  (`explicit|repo|question`) at InitSession; legacy metas are classified
  from the name shape (repo slug match, question-slug 8-hex suffix),
  defaulting to explicit — conservative in the no-auto-join direction.
- **The daemon routes before worker selection** (the pool is keyed by the
  resolved session), passing the RouteDecision into
  `AskWithTurnRunner(..., route)`; the daemonless path routes inside
  `askWithTurnRunner`. The stated out-of-scope item "daemonless-path
  behavior change" was overridden by the implementation task: daemonless
  asks now run the same cascade — both paths share one code path and one
  decision record, and `ResolveSessionName` is deleted (no dual paths,
  Engineering Tenets).
- **R2 token detection** ships with a versioned source-tree denylist
  (`repoTokenPathDenylist`) so "internal/sidecar" is not a repo; known v1
  limitation: an unlisted path like `foo/bar.go` can false-positive, and
  URLs are not parsed for repo tokens (multi-slash words never match).
  Both pinned in `TestDetectRepoToken`; extend from dogfood evidence. When
  R2 creates the session from a question token, `DetectedRepo` becomes the
  new session's `meta.Repo` — identical to a `--repo` creation — but the
  ask itself stays discovery-persona (repo scope from text alone must not
  change prompt semantics).
- **Rebuild determinism required enriching the per-turn artifact**, as the
  ADR predicted: ledger derivation consumes bare trace-derived command
  strings, while `ActualCommandLedger` stores decorated summaries
  ("execute: … (completed)"). `ReportArtifact.TraceCommands` now persists
  the exact strings (`TraceCommandLedger`), and `RebuildLedger` replays
  reports/ through the same `UpdateLedgerFromTurn`/`ApplyTraceCommands`
  path the live turn uses. The invariant holds for artifacts written from
  this version on; legacy flat `report-<ts>.json` files carry no turn
  attribution and are excluded from replay.
- **Reroute** is `ghx sidecar sessions reroute <session> <turn> <dest>`
  (positional dest; a nonexistent dest is created — that is the "--to new"
  shape, named by the operator). The moved artifact is renumbered to the
  destination's next turn and carries a `rerouted` provenance block
  (fromSession/fromTurn/at); source `ACPSessionID` cleared (ADR-0027
  path); turn counters re-anchored on surviving artifacts. Reroute targets
  are created `NamedBy: explicit` — operator-directed threads must not
  become auto-join candidates by accident. The daemon RPC
  `ghx.sidecar.Reroute` drops the source session's warm worker before
  touching disk; the CLI uses the daemon when healthy, disk otherwise
  (`RerouteViaDaemon`), shutting down a version-skewed daemon first.
  Turn-attributed trace/log records are NOT surgically moved in v1 — the
  rebuild invariant depends only on reports/; span moves are deferred.
- **D7 emission:** `ghx.sidecar.route.*` attrs ride the `sidecar.ask` span;
  a `sidecar.route` record (incl. `marker_table_version`) lands in
  logs.jsonl regardless of the content-capture setting (it carries no
  message content — the prior "no logs.jsonl when capture off" test pin
  was relaxed to "no GenAI content records"). Route line on CLI stderr and
  stdout footer and MCP recon text: `session: X (routed: repo
  gin-gonic/gin | overlap 0.62, next 0.21 | continuation, … | new)`.
- **Byte-identical pins:** with `--session`/`--repo` the CLI still
  pre-prints `session: <name>` and emits the unchanged footer/JSON
  envelope (the envelope gains `route` only on flag-less asks). The recon
  MCP tool deleted its local session defaulting (D4 phase 1) and passes
  parameters through verbatim; its `session` description is now the
  "advanced: … normally omit" wording. The recon skill document re-wording
  is deferred to the next slice.
- **Config:** `config.json` `route` object (overlapThreshold,
  overlapMargin, continuationWindowMinutes, routingWindowHours), included
  in the daemon config digest so knob changes restart the warm daemon.
- **Live smoke (2026-07-06, isolated `GHX_HOME`, 2 asks):** ask 1
  `--repo gin-gonic/gin` created `gin-gonic-gin` (stderr byte-identical);
  ask 2 with no flags ("In gin-gonic/gin, how are route path parameters…")
  routed R2-by-token into the warm session — stderr/footer showed
  `session: gin-gonic-gin (routed: repo gin-gonic/gin)`, and logs.jsonl
  carries the `sidecar.route` record with `route.source=repo`,
  `route.detected_repo=gin-gonic/gin`, `marker_table_version=1`
  (trace fa3d86bab3c92f57c38b7f9da374eff6).

Follow-up remaining: dogfood cycle + weekly route-record audit (D7),
organic `continuation`/`overlap` hits before D4 phase 2, recon skill
re-documentation, R4/R5 candidate visibility in `sessions show`, and the
ghx.sidecar.Reroute surface in the A2A story.
