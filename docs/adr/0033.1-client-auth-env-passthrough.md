# 0033.1. Client auth-env passthrough — the agent authenticates as the shell that asked

## Status

Accepted (orchestrator, 2026-07-06). Follow-up to ADR-0033: its diagnostics
made the founder's work-laptop failure visible; this ADR removes the failure's
cause. Presupposes the always-on daemon (ADR-0030).

## Problem

The spawned Claude agent authenticates through process environment
(Bedrock/Vertex/gateway env vars) or the SDK's own credential store — no ACP
session option pins auth (ADR-0033 research). On the daemon path the agent
inherits the **daemon's** environment, and the daemon's environment is frozen
at whatever context first auto-started it. Live failure (founder work laptop,
2026-07-06): session provenance showed `agentEnv: ["PATH", "HOME"]` — the
shell's Bedrock vars (`CLAUDE_CODE_USE_BEDROCK`, `AWS_REGION`, credential
hooks) never reached the adapter, which fell back to default Anthropic auth
and died with `-32000 Authentication required` on every turn. Nothing strips
the environment deliberately; ambient inheritance through a long-lived
process is simply nondeterministic. "Export the vars and restart the daemon"
is a footgun, not a design.

## Decisions

### D1 — Capture at the client, per ask

`AskViaDaemon` snapshots the asking process's environment through a curated
allowlist (`agentAuthEnvPassthrough`: ANTHROPIC_* auth/routing/custom-headers,
CLAUDE_CODE_OAUTH_TOKEN, Bedrock/Vertex provider selection + cloud
credentials, CLAUDE_CODE_EXECUTABLE/CLAUDE_CONFIG_DIR, proxy/CA transport)
and sends the "NAME=VALUE" entries in `AskRequest.AgentAuthEnv`. Excluded by
design: PATH/HOME (the daemon's own process context) and
GH_TOKEN/GITHUB_TOKEN (ghx's access, not the agent's). The rule becomes
deterministic and matches user intuition: **the agent authenticates as the
shell you ran `ghx` from.**

### D2 — Overlay at spawn; eval pins win

The runtime resolves the spawn environment once per ask: explicit
`Config.Env` (eval profiles pin whole environments — unchanged) > client
overlay merged over the daemon's `os.Environ` > nil (plain inherit). Merged
env feeds both the adapter spawn and the session provenance record, so
`sessions show` now reports the environment the agent *actually* saw.

### D3 — Warm workers respawn on auth change

Each warm worker stores a SHA-256 digest of its spawn environment. A turn
arriving with a different digest shuts the adapter down and respawns instead
of serving on stale credentials. Digest only — values are never retained on
the worker.

### D4 — Values never touch disk

`AgentAuthEnv` rides only the runtime-dir unix socket (0700) and process
memory. The daemon does not log request params; session metadata keeps the
ADR-0033 D5 names-only contract (now refreshed when the name set changes).
Test-pinned: the e2e daemon test asserts the forwarded value is absent from
persisted metadata.

### D5 — Doctor visibility

`ghx sidecar doctor` gains an always-pass `agent-auth-env` line naming the
vars the current shell would forward (or stating that the agent will use its
own adapter-login store). The auth-failure hint drops its "restart the
daemon" step — passthrough made it unnecessary.

## Consequences

- Bedrock/Vertex/gateway shells work on the daemon path with zero config;
  switching shells (or fixing an env) applies on the very next ask.
- A worker respawn costs one adapter cold start whenever consecutive asks
  come from shells with differing auth env — correct-over-warm by design.
- The adapter's ACP `gateway`/`gateway-bedrock` auth methods are now
  reachable purely through env passthrough; a first-class `ghx sidecar auth`
  flow remains open as a possible follow-up.
