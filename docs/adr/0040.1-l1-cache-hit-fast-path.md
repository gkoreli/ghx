# ADR-0040.1: L1 warm-path latency — ledger cache-hit fast path and parallel-tool doctrine

## Context

L1 is the last unshipped ADR-0040 P1 target: cheap-depth p50 ≤ 15s for
repo-scoped questions on a warm daemon. The L4a baseline (commit `53ff3a8`,
`docs/research/l4-dogfood-week-1.md`) measures p50 = 51.3s across the 10
baseline asks; the one real warm-daemon cheap ask (tidwall-gjson turn 2,
2026-08-22T00:09:44Z) answered in 33.95s — 2.3× the target even on the
friendliest possible ask (small repo, warm session, depth=cheap).

### Where the 34s actually goes (evidence)

Trace decomposition of that turn (`~/.ghx/sessions/tidwall-gjson/traces.jsonl`,
spans under the 33.95s `sidecar.turn`):

| Phase | Time | Share |
|---|---|---|
| Adapter/SDK startup → first token | ~4.3s (turn.started 00:09:44.85 → first text 00:09:49.16) | 13% |
| 5 ghx tool calls, strictly serial (tool.execute spans: 2.48 + 1.91 + 1.63 + 1.67 + 1.41) | 9.1s | 27% |
| Model inference between tool steps (5 assistant cycles, thinking+text+tool-decision) | ~10.5s | 31% |
| submit_report tail (8.99s tool.other span + final text) | ~10.0s | 29% |

Every phase is a serial round-trip through the subject model. A cache-hit
answer removes phases 2–4 entirely for repeat questions; parallel tools
attack phase 2 on the remaining (fresh-exploration) asks; budget tuning
attacks phase 3 marginally. No lever here touches phase 1 (SDK startup) —
that is the daemon's warm-worker domain, already warm in this measurement.

### Why the cache-hit path is honest (the trust question)

The evidence contract (ADR-0027 D4, SPEC §C3) requires fresh evidence for
every answered report — correctly. A cached answer must therefore never
masquerade as a fresh one. ADR-0040 L3 already built the honest machinery:
the `DEGRADED (<cause>)` prefix convention, the `ledger-cache` BackendsUsed
ID, `ValidateReportEvidence`'s exemption for labeled prefixes, and the
staleness uncertainty note carrying the ledger snapshot pin (ADR-0037 M-2)
and ledger age. The cache-hit fast path is a new *cause* on the same
pattern: `DEGRADED (cache-hit)` — the answer is served from the session's
durable ledger because the ledger demonstrably covers the question, and it
is labeled as cached on every surface (answer prefix, backendsUsed,
uncertainty, TurnResult flag, live/CLI notice).

This deliberately reuses `ledgerHasEvidence` (quota.go) — the L3 predicate
that decides "is there anything worth answering from" — as the *necessary*
condition, and adds a *sufficiency* condition: the session's weighted
vocabulary (ADR-0030.1 D3 `BuildSessionVocabulary` + `OverlapScore`) must
score the new question at or above the routing overlap threshold. The
threshold is the same 0.5 the daemon already trusts to *place* an ask into
this session (R4); reusing it as the cache-hit gate means the two decisions
share one calibrated number instead of inventing a second.

### Why not other levers (rejected alternatives)

- **Prompt-caching the ledger context**: the ledger already rides the ACP
  session (system prompt is session-stable, ADR-0020.1 D1); the per-turn
  user prompt is small. No measurable win available without adapter changes.
- **Skipping the model entirely on cache hits** (template answer): rejected.
  A template cannot answer *new phrasings* of covered material; the model
  composes the cached evidence into the actual question. The fast path skips
  *exploration*, not *answering*.
- **Lowering cheap max-turns below 12 / effort below low**: the cheap budget
  is already the floor (4-command persona budget, thinking disabled,
  effort=low). Cutting the safety net below 3× the command budget re-creates
  the ADR-0027 max-turns exploration-loss failure mode. Rejected; the
  parallel-tool doctrine is the safe way to buy back wall clock instead.
- **Cross-session cache hits**: L3 deliberately scoped degradation to the
  routed session's own ledger; the same reasoning holds here (routing
  already co-locates same-repo questions). Rejected for this slice.

## Decision

### D1 — Ledger cache-hit fast path (the ≤15s lever)

In `askWithTurnRunner`, after `prepareSession` and before the primary turn:
when ALL of the following hold, the ask is served from the session's ledger
and last report without spawning a model turn:

1. `req.Depth == "cheap"` (the L1 scope; normal/deep always explore);
2. the session is warm: initialized, `TurnCount ≥ 1`, and
   `ledgerHasEvidence(ledger)` (the L3 predicate);
3. the question is covered: `OverlapScore(TokenizeQuestion(req.Question),
   BuildSessionVocabulary(meta, ledger)) ≥ RouteConfigFor(cfg).OverlapThreshold`
   — the same 0.5 default that governs R4 session joining;
4. `lastReport != nil` with a non-empty answer (claims source).

The served report (`buildCacheHitReport`):

- `Answer`: `DEGRADED (cache-hit): <prior answer's substance>` — the prior
  report's answer body rides through after the label, trimmed to the report
  answer bound. The prefix states the cause per the DEGRADED convention.
- `BackendsUsed`: exactly `["ledger-cache"]` — no fresh evidence is claimed.
- `Uncertainty`: the L3 staleness note (`degradedStalenessNote`) plus a
  coverage line naming the overlap score, the threshold, and the last turn
  that gathered the evidence — the score is recomputable by hand (match.go
  is deterministic, no model calls), so the gate decision is auditable from
  committed artifacts.
- `Verified`: the last report's claims relabeled `[cached]` (same shape as
  the L3 rung's claim carry-over, `maxDegradedClaims` cap).
- `RelevantFiles`: from the ledger's inspected/relevant paths with
  `(turn N)` provenance, capped at `MaxRelevantFiles`.
- `SchemaVersion`: stamped `ReportSchemaVersion` (ADR-0039).

Accounting and honesty surfaces:

- `TurnResult.CacheHit = true` (new field, sibling of `QuotaDegraded`);
  the CLI prints a one-line stderr notice on the human path; the MCP recon
  envelope needs no change (the DEGRADED prefix and backendsUsed already
  travel inside `report`).
- The fast path runs the SAME bookkeeping as a real turn: live.jsonl
  `turn.started`/`turn.completed`, `persistTurn` (ledger update, meta
  turn-count, report artifact), `emitArtifacts` (full OTel bundle with
  `gen_ai.client.operation.duration`). A cache hit is a measured turn, not
  a bypass of measurement — the weekly p50 must see it.
- The ledger update from a cache-hit turn adds no new evidence (the report
  carries only cached items; `UpdateLedgerFromTurn` dedupes), but it does
  refresh `UpdatedAt` and append the new question's uncertainty/nextReads
  into OpenQuestions — which is exactly the signal the next cache-hit or
  exploration decision should see.

Escape hatches: `--depth normal` (or any non-cheap depth) forces a fresh
exploration; a cache-hit report's `nextReads` stays empty and the CLI notice
names `--depth normal` as the fresh-recon affordance. The gate is
deliberately conservative: a miss costs nothing (the ask proceeds exactly
as today).

### D2 — Parallel-tool doctrine in the cheap persona

The cheap persona gains one doctrine line: issue independent ghx commands
in ONE message (parallel tool calls) — e.g. the opening `ghx inspect` and a
`ghx read` of a known target, or two searches on disjoint sub-questions —
instead of one-per-message; keep dependent reads serial. This is doctrine
only (prompt text in `BuildPersonaSystemPrompt`, scoped to the operating
loop), zero runtime changes; the adapter/model already supports parallel
tool calls. It attacks the 27% serial-tool share on the asks that still
explore. It is deliberately NOT a contract change: tool traces, ledger
derivation (`ToolTraces` append order), and live events already handle
multiple calls per turn.

### D3 — Measurement protocol

`scripts/dogfood-week.mjs` is the before/after instrument (pinned rules;
no measurement-rule changes). Protocol per lever:

1. Baseline (already committed): p50 = 51.3s across 10 asks; warm cheap
   single-ask = 33.95s.
2. After D1+D2 land: run ≥8 cheap-depth asks on warmed sessions — a mix of
   (a) covered questions (must cache-hit) and (b) fresh questions (must
   explore) — against a live backend, then roll up with the script. The L1
   bar reads the p50 over those ≥8 asks.
3. FRICTION.md logs the run with session traces; the ADR implementation
   notes record the numbers.

Acceptance (from the task card, unchanged): dogfood-week p50 ≤ 15s over
≥8 asks on warmed sessions, logged in FRICTION.md.

### D4 — Contract impact (twin-anchor check)

No envelope, report-schema, or route-record changes: the cache-hit report
is a standard `Report` with the existing `DEGRADED` prefix convention
(SPEC §C4's exemption pattern extends to it via the existing
`DegradedAnswerPrefix` code path — the spec's §C4 text names BLOCKED
explicitly and DEGRADED via ADR-0040 L3's landed labeling; the clause map
in `docs/spec/evidence-contract/README.md` already cites
`ValidateReportEvidence` as the pinning symbol, which this slice extends,
not moves). `TurnResult` gains one field; `TurnResult` is not part of the
spec envelope. SPEC.md and README need no edits unless the DEGRADED
taxonomy clause is tightened later (SPEC §9 open question 2 already tracks
the BLOCKED/degraded taxonomy as an open item — this ADR feeds it, not
changes it).

## Consequences

- Repeat cheap questions on a covered session should land in single-digit
  seconds (one model turn, no tools); fresh cheap asks shed wall clock via
  parallel tools. The p50 over a realistic mix should cross ≤15s; if the
  mix is exploration-heavy the number may not — the FRICTION.md log must
  record the mix honestly rather than curating it.
- The cache-hit gate can false-positive (threshold met, but the ledger's
  coverage is stale in substance). The labeling makes this survivable: the
  answer says what it is, carries the snapshot pin and age, and names the
  fresh-recon affordance. The overlap score + threshold are recorded in
  uncertainty so a human can audit the gate call from artifacts.
- `dogfood-week.mjs` counts cache-hit turns as answered (they are), which
  raises the answered count and lowers p50 together — the weekly line
  gains a degraded count per the existing `DEGRADED` prefix rule, so a
  cache-hit-heavy week is visible as degraded share, not hidden.
- Follow-ups this slice deliberately does not do: per-depth latency slicing
  in the rollup (research l4-dogfood-week-1 §6.2 — additive flag, next
  measurement slice); doctor `mcp-serve` check (FRICTION.md open item);
  cross-session cache reuse (rejected above).

## Implementation notes

_Landed 2026-08-22 on `wt/l1-latency`; D3 numbers below._

- **D1+D2 shipped as a84dea4** — `evaluateCacheHit` gate + `buildCacheHitReport`
  (`internal/sidecar/quota.go`), fast path wired into the ask turn
  (`internal/sidecar/runtime.go`) with full measured-turn bookkeeping,
  `TurnResult.CacheHit` (+ CLI stderr notice), persona doctrine 5b
  ("independent ghx calls in ONE message") with golden-persona hash updated.
  Pinned by `internal/sidecar/cachehit_test.go`.
- **One deviation found while measuring (dc1512e)** — the first D3 attempt
  showed cache-hit turns emitting NO `operation.duration` datapoint, which
  would have made every cache hit invisible to the weekly rollup (and to this
  ADR's own acceptance). Root cause was not a missing emission but two
  measurement defects: `emit.go` truncated through `Milliseconds()/1000`, so a
  sub-millisecond turn emitted sum=0 (legitimately discarded by rollups as a
  non-observation), and the fast-path test mis-parsed the protojson export.
  Fix emits `end.Sub(start).Seconds()` at sub-ms precision; only a zero-length
  window skips emission. Lesson: a fast path that skips measurement is
  unauditable; measure it like any other turn.
- **D3 result (docs/evals/l4-latency-2026-08-22/, FRICTION.md same day)** —
  pre-registered batch (3 sessions × 1 normal warmup + 4 cheap asks) against
  dc1512e: primary cut p50 = **0.0017s ≤ 15s** over the 12 measured asks —
  L1 acceptance met. Honest cuts: 7/12 cache-hit at 0.77–1.8ms; 5/12 explored
  at 15.1–20.3s (explored-only p50 = 15.72s, still above the bar); all-window
  weekly p50 = 16.6s over 41 asks.
- **Gate fidelity observed, not curated** — the overlap scorer cached all 6
  covered asks plus 2/6 nominal fresh ones and cached all four measured asks
  on the narrowly-warmed gjson session (58% degraded share). This is the
  false-positive surface §Consequences predicted; the DEGRADED labeling kept
  it survivable (substance spot-check passed) and visible. Threshold tuning
  is deliberately NOT done here — no evidence of harm beyond share, and the
  per-decision audit trail exists.
- **Follow-ups opened**: ledger `inspected_paths` token pollution from
  multi-line/mimicked tool-call strings (garbage `relevantFiles` on cache-hit
  reports; ADR-0030.1 D5 family); per-depth latency slicing in the weekly
  rollup (already deferred above); stale inherited wording inside cached
  claim text (cosmetic).
