# 0016.12. Repo-Named Closed-Book Variant for H2

## Status

Accepted (orchestrator, 2026-07-06). Pre-registration for the TRUST.md H2
follow-up; drafted by a delegated worker, accepted before any repo-named
closed-book episodes are run, inspected, summarized, or used to update
TRUST.md. Orchestrator answers to the draft's open questions: artifact
naming stays as proposed; n = 5 trials/task stays (30 episodes total, the
registered cap — cheap `tools: []` completions, no live exploration);
subject model stays `claude-sonnet-5` for comparability with ADR-0016.9.
The run itself is scheduled separately and is not triggered by this
acceptance.

This is measurement-only. It changes no eval tasks, no scoring code, no
detectors, no gates, no sidecar persona, and no open-book baselines. The
measurement stack is frozen during the run: scorer, detector, task fixture,
adapter, wrapper, and subject-model identity must be recorded before the first
episode, and any mid-run scorer/detector change requires a superseding
pre-registration before rescoring. Results are committed even when negative
or inconvenient; no rerun-until-green.

## Context

ADR-0016.9 measured the first H2 memorization probe with the exact eval
question text and explicit `tools: []`. It found:

- closed-book corpus mean correctness `0.067` over 30 episodes;
- open-book pooled mean correctness `0.926` from
  `docs/evals/gate-run-2026-07-06-fixbatch`;
- no recall-dominated, low-exploration-signal, or memorization-risk task;
- five of six tasks labeled exploration-bearing;
- `flask-routing` at mean `0.40`, median `0.50`, max `0.50`, with partial
  recall of `add_url_rule` but stale path guesses rejected.

The audit's own README states the residual precisely: those closed-book
scores are a lower bound on memorization because the prompts generally did
not name the repository. Open-book profiles receive the repo identity through
the direct-profile preamble or `sidecar.Ask(Repo: ...)`, while the ADR-0016.9
closed-book subject mostly saw repo-less questions such as "Where are routes
registered...?" with no tools and no cwd. TRUST.md H2 therefore remains open:
a harder closed-book variant must isolate "knows the repo's internals from
weights once the repo is named" from "did not know which repo to answer
about."

This ADR pre-registers that harder variant.

## Decision

Run a repo-named closed-book variant over the same six ADR-0016.9 tasks:

- `express-router-location` / `expressjs/express`
- `flask-routing` / `pallets/flask`
- `ghx-mapengine` / `gkoreli/ghx`
- `gin-routing` / `gin-gonic/gin`
- `hono-middleware` / `honojs/hono`
- `openai-node-streaming` / `openai/openai-node`

The corpus is reused exactly from
`internal/sidecar/evals/testdata/tasks/*.json`; no task text, checks,
expected files, expected symbols, avoid paths, unacceptable claims, or judge
criteria are edited for this run.

## Prompt Construction

For every task turn, construct the prompt by prefixing the original turn text
with the task's committed repo slug:

```text
In <owner/repo>: <original task turn>
```

Examples:

```text
In pallets/flask: Where is the route() decorator implemented, and where do registered URL rules end up?
In gin-gonic/gin: Where are routes registered, and how are incoming requests matched to handlers?
In gin-gonic/gin: How are route parameters like :name captured during tree matching?
```

Rules:

- The repo slug is exactly `task.Repo` from the fixture.
- The original task turn text is otherwise byte-for-byte unchanged.
- Single-turn tasks send exactly one prefixed prompt.
- Multi-turn tasks send each prefixed `task.Turns[i]` as its own prompt in
  the same no-tool session, preserving the original turn order.
- No synthetic recap, hint, "do not use memory" instruction, sidecar persona,
  direct-profile preamble, repo metadata beyond the slug, file tree, README
  excerpt, or previous open-book answer is provided.

This variant tests whether naming the repository unlocks closed-book recall of
the same deterministic facts. It does not test exploration quality.

## Subject Invocation and Tool Enforcement

Tool enforcement is identical to ADR-0016.9. Use the existing ACP wrapper path
and subject model identity, pinned the same way as live evals
(`GHX_EVAL_SUBJECT_MODEL=claude-sonnet-5` unless the orchestrator explicitly
pins a successor before the run).

The ACP session is created with `_meta.claudeCode.options.tools` and
`allowedTools` both set to explicit empty arrays:

```json
{
  "claudeCode": {
    "options": {
      "settingSources": [],
      "strictMcpConfig": true,
      "tools": [],
      "allowedTools": [],
      "model": "claude-sonnet-5",
      "thinking": { "type": "disabled" }
    },
    "emitRawSDKMessages": true
  }
}
```

The run is invalid if `tools` is omitted rather than serialized as `[]`.
Report-sink tools, ghx tools, shell, gh, web, read, MCP tools, and sidecar
tools are unavailable. Any tool-call notification is a harness failure, not a
scoreable episode. The run summary must prove zero tool activity over the
committed artifacts, using the same check shape as ADR-0016.9.

## Scoring

Scoring is unchanged from ADR-0016.9:

1. Build an `evals.Episode` with profile value
   `"closed-book-repo-named"`, `TaskID`, `Repo`, snapshotted `Checks`, one
   `TurnRecord` per prefixed task turn, no actions, no observations, no
   report, and no tool calls.
2. Capture only assistant text.
3. Score with the same deterministic path:
   `ComputeRewards(task, ep)`.
4. Report `rewards.correctness` as the primary memorization-confound metric.

Other reward components may be persisted for recomputability, but they must
not be interpreted as exploration quality. No judge scorer is used for the
primary H2 decision; a future qualitative analysis may explain answer
patterns, but it cannot replace the deterministic gate in this ADR.

## Episode Budget and Artifacts

The episode budget is capped at **30 total episodes**:

- six tasks;
- `n = 5` trials per task by default;
- no replacement tasks;
- no top-up trials after seeing results.

If the orchestrator lowers the budget before the run, it must remain balanced
across tasks and the lower `n` must be recorded in the manifest. The run may
not exceed 30 episodes without a superseding ADR.

Committed artifacts land under a new directory, for example:

```text
docs/evals/memorization-audit-repo-named/
  README.md
  manifest.json
  closed-book-repo-named-summary.json
  episodes/
    <task-id>_closed-book-repo-named_trial-<n>.json
```

The manifest records at least:

- ADR id: `ADR-0016.12`;
- run id and timestamp;
- git commit;
- task corpus hash;
- wrapper SHA256;
- adapter name/version;
- subject model requested and adapter-reported subject model;
- number of trials per task;
- exact prompt transform;
- exact session options, including proof that `tools: []` and
  `allowedTools: []` were sent;
- scoring code commit;
- open-book reference run id from ADR-0016.9's summary.

The README must label the result as the repo-named closed-book variant and
must state whether it raises, lowers, or leaves unchanged the H2 residual risk.

## Pre-registered Decision Rule

For each task, apply ADR-0016.9's thresholds to the repo-named closed-book
mean, max, and open-book gap, using the same open-book reference means already
recorded in `docs/evals/memorization-audit/closed-book-summary.json`.

Verbatim decision rule:

> A task is flagged **recall-dominated** if mean repo-named closed-book
> correctness is `>= 0.80`.
>
> A task is flagged **low exploration signal** if mean repo-named closed-book
> correctness is within `0.10` absolute of the task's open-book pooled mean.
>
> A task is flagged **memorization-risk** if max repo-named closed-book
> correctness is `1.00` and mean repo-named closed-book correctness is
> `>= 0.60`.
>
> A task remains **exploration-bearing** if mean repo-named closed-book
> correctness is `< 0.40` and the open-book gap is `>= 0.30`.
>
> Any task flagged recall-dominated must be replaced before it is used in a
> future citable correctness gate; any task flagged low exploration signal must
> be replaced or rewritten before it is cited as exploration evidence; any task
> flagged memorization-risk may be kept only with an explicit caveat or
> replaced in the next corpus revision.

Corpus-level interpretation:

- If zero tasks flag recall-dominated, low-exploration-signal, or
  memorization-risk, H2 remains bounded more tightly than ADR-0016.9: repo
  identity does not materially unlock closed-book correctness under the
  current deterministic checks.
- If one or more tasks flag, H2 is updated with the exact flagged tasks and
  the affected tasks stop supporting citable exploration-correctness claims
  until replaced, rewritten, or explicitly caveated under the rule above.
- The corpus-level memorization-adjusted correctness remains diagnostic:

```text
memorization_adjusted_correctness = open_book_correctness - repo_named_closed_book_correctness
```

It does not retroactively rescore prior gate verdicts unless a future ADR
explicitly changes the gate.

## Expected Pattern Before Running

`flask-routing` is the leading candidate to rise. ADR-0016.9 already showed
known partial recall at mean `0.40`: the subject recalled `add_url_rule` in
four of five trials from weights, while stale pre-2.2 path guesses such as
`flask/scaffold.py` and `flask/app.py` failed the current file checks. Naming
`pallets/flask` may increase confidence and answer specificity, but the
current deterministic checks still require the modern `src/flask/sansio/*`
layout, so the pre-run expectation is:

- `flask-routing` may improve above its repo-less lower bound;
- it should not be presumed recall-dominated unless it crosses the
  pre-registered thresholds;
- stale-path hallucinations remain useful evidence that current repository
  inspection is needed even when concept recall exists.

The other five tasks scored `0.000` under ADR-0016.9. Repo naming may unlock
some famous-framework recall for `gin-gonic/gin`, `expressjs/express`,
`honojs/hono`, and `openai/openai-node`, but the exact magnitude is unknown
until measured. `gkoreli/ghx` is self-referential and must be watched for
contamination paths, but this run still uses the same frozen checks and
`contaminationPaths` handling from the fixture/scorer.

## TRUST.md H2 Update Rule

After the run is committed, update TRUST.md H2 in the same commit or a
follow-up docs commit with:

- run id and artifact directory;
- corpus mean repo-named closed-book correctness;
- open-book reference mean;
- per-task labels from the decision rule;
- whether any task became recall-dominated, low-exploration-signal, or
  memorization-risk;
- a plain-language residual-risk statement.

If the run is negative, say so directly and keep the artifacts. If it flags
tasks, name them directly and do not continue citing their correctness as
exploration evidence without the required caveat or replacement.

## Considered and Rejected

- **Changing task wording beyond adding the repo prefix.** Rejected. The
  purpose is to isolate repo identity, not author a new task corpus.
- **Adding "answer from memory" or "do not browse" instructions.** Rejected.
  `tools: []` already enforces closed-book; extra instructions create a new
  compliance variable and break comparability with ADR-0016.9.
- **Scoring with a judge.** Rejected for the primary H2 rule. Deterministic
  checks remain the frozen lower-level evidence; judge scoring belongs to the
  separate quality layer.
- **Running only the famous repositories.** Rejected. The corpus-level H2
  claim depends on applying the same transform to every ADR-0016.9 task.
- **Increasing trials after a surprising result.** Rejected. The budget is
  capped before running; surprising results are committed and interpreted, not
  chased mid-run.

## Verification Plan

- Harness test or dry-run assertion that every prompt equals
  `"In " + task.Repo + ": " + task.Turns[i]`.
- Session-meta test or manifest proof that `tools: []` and
  `allowedTools: []` serialize explicitly.
- Artifact audit proving zero tool calls/tool traces/violations across all
  episodes.
- Offline recompute of every summary number from committed episode JSONs.
- README records the exact command, env vars, wrapper identity, subject model,
  scoring commit, task-corpus hash, and decision-rule labels.
