# 0016.1. Sidecar Eval Implementation — Minimal Validation Kernel

## Status

Proposed. Phase 3 implementation notes are appended at the bottom as engineering
proceeds. This ADR narrows ADR-0016 to the smallest implementation that can
prove or disprove the sidecar thesis; it does not supersede ADR-0016's
training-data north star, it sequences it.

## Context

A read-only gap analysis (2026-07-03) of the sidecar thread found that the
validation question — *does the sidecar architecture genuinely improve code
reconnaissance?* — is currently unanswerable from the repository record:

1. **ADR-0016 is Decided but unimplemented.** `internal/sidecar/evals/` does
   not exist. No episode runner, no rewards, no tasks.
2. **No eval harness can drive the Go sidecar.** `packages/ghx-bench` runs
   agents through `acpx/runtime` (Node), and the migration commit `cd149aa`
   deleted the only concrete agent definitions (`benchmarks/agents.ts`), tasks
   (`benchmarks/tasks.ts`), and entry point (`benchmarks/bench.ts`). Nothing in
   the repo calls `runExperiment()`.
3. **No committed results back the "validated" claim.** ADR-0015 states the
   bench experiments "answered yes", but no trial artifact, score, or verdict
   file exists anywhere in the repo. The claim is unfalsifiable from the record.
4. **`internal/sidecar` has zero tests.** `ExtractReport`, `BuildPrompt`, and
   the session lifecycle are unverified.
5. **The memory pillar is structurally untested.** Follow-up continuity depends
   entirely on ACP `LoadSession` (`internal/sidecar/acp.go`), which agents may
   not support; the evidence ledger from ADR-0014.1 was never built.

This ADR defines the minimal eval kernel that converts the thesis from an
assertion into a reproducible, committed measurement — and pre-registers the
pass/fail thresholds **before** eval code is written, so the eventual verdict
cannot be fitted to the results.

## Scope

### In scope (this slice)

- Unit tests for the existing sidecar contract surface: report extraction,
  prompt construction, session lifecycle.
- `internal/sidecar/evals/`: episode schema, three profiles, deterministic
  checklist rewards, task registry, local artifact store, ACP episode runner.
- A mock ACP agent that exercises the full episode plumbing (spawn → ACP
  handshake → session → prompt → tool-call notifications → `<ghx-report>` →
  reward computation → artifacts) deterministically, with no LLM and no
  network. This keeps the harness itself testable in normal CI.
- Live-agent episodes behind the `agent_e2e` build tag, per ADR-0016.

### Deferred (explicitly out of scope for this slice)

- OpenTelemetry span emission (ADR-0016) — artifacts are JSON files first.
- SFT / preference-pair / training-data exports (ADR-0016 north star).
- LLM-as-judge scoring — deterministic rewards must come first; a judge is a
  secondary explainer, never the gate.
- Codemap or any backend escalation.
- Framework-contract standardization (versioned schema, MCP exposure, skills
  for main-agent delegation). That work gets a **new ADR number (0017)** and is
  gated on this ADR's verdict.
- The fate of `packages/ghx-bench` (delete vs. port). Recorded as follow-up;
  its judge rubric and burden model inform the reward design here.

## Decision

Build the minimal Go-native eval kernel in `internal/sidecar/evals/` comparing
exactly the three profiles from ADR-0016, reusing the production sidecar code
path (`sidecar.Ask`, `sidecar.RunTurn`) so the eval measures what users run.

### Profiles

| Profile | Runtime path | What it measures |
|---------|-------------|------------------|
| `plain` | ACP turn with a neutral prompt; agent may use its own shell/`gh` | Baseline: capable agent, common tools |
| `ghx` | ACP turn with ghx skill instructions injected; agent uses `ghx` directly | Value of ghx as a tool in the main agent's hands |
| `ghx-sidecar` | In-process `sidecar.Ask()` — the exact production code path | Value of the sidecar boundary: compression, evidence, memory |

### Permission model per profile (engineering decision)

The production `denyClient` rejects **all** permission requests. That is
correct for the sidecar contract but would cripple the `plain`/`ghx` baselines
if their agent requests permission to run read-only shell commands. The eval
package therefore owns a second ACP client for direct profiles that approves
execute/read permission options and rejects write options. The sidecar profile
keeps `denyClient` untouched — if a live sidecar run fails because the
downstream agent insists on permission for read-only shell, that is a **real
product finding** and must be recorded in results, not papered over by the
harness.

### Main-agent context accounting (the core metric)

- `ghx-sidecar`: main-agent context = the serialized `Report` JSON only.
  Internal exploration text and tool output are sidecar-internal chars.
- `plain` / `ghx`: main-agent context = the full turn transcript (all text the
  agent produced while exploring), because the main agent *is* the explorer.

This mirrors `MainAgentBurden` from `packages/ghx-bench/src/types.ts` and is a
modeled boundary, not a measured one. A main-agent-in-the-loop experiment (a
real harness delegating mid-task) remains the strongest test of the thesis and
is planned as a follow-up slice; the gates below are the controlled proxy.

## Reward Model (deterministic)

All rewards are in [0, 1], computed from the `Episode` struct with no LLM.

| Reward | Definition |
|--------|------------|
| `correctness` | mean of: fraction of `expectedFiles` identified (path suffix match against relevant files + answer text), fraction of `expectedSymbols` present, fraction of `requiredClaims` present (case-insensitive substring). 0 if any `unacceptableClaims` present. |
| `evidence` | mean of: fraction of verified claims carrying non-empty evidence, 1 if `commandsRun` non-empty else 0, fraction of relevant files carrying a non-empty reason |
| `trajectory` | 1 − penalties: duplicate command ratio, over-budget ratio (>8 commands per question), fraction of commands touching `avoidPaths`. Floor 0. |
| `compression` | 1 − (main-agent context chars ÷ total workflow chars). For direct profiles this is 0 by construction; the cross-profile gate (G3) compares absolute main-agent chars, not this ratio. |
| `memory` | multi-turn tasks only: 1 − repeat-read ratio across turns, ×0 if a follow-up turn failed to resume the session |
| `safety` | 1 if no write/terminal/permission-violation was attempted, else 0 |

## Pre-Registered Gates and Verdict Rules

A **gate run** is: ≥ 6 tasks across ≥ 3 repos, at least 2 tasks multi-turn,
5 trials per task × profile, identical agent configuration for all profiles,
artifacts committed under `docs/evals/<run-id>/`.

| Gate | Threshold |
|------|-----------|
| **G1 correctness** | mean(`ghx-sidecar`) ≥ 0.9 × mean(`ghx`) AND mean(`ghx-sidecar`) ≥ 0.60 absolute |
| **G2 evidence** | mean(`ghx-sidecar`) ≥ 0.70 |
| **G3 compression** | mean main-agent context chars for `ghx-sidecar` ≤ 0.35 × mean for `ghx` profile |
| **G4 memory** | follow-up turns resume successfully in ≥ 80% of multi-turn `ghx-sidecar` trials AND sidecar repeat-read ratio ≤ `ghx` profile's |
| **G5 safety** | 1.0 on every `ghx-sidecar` episode |

Verdict rules, fixed now:

- **Thesis SUPPORTED**: G1, G2, G3, G5 all pass.
- **Thesis NOT SUPPORTED**: G1 or G3 fails. Consequence: pause ADR-0017
  framework standardization; iterate prompt/model or record the honest
  negative in a status update to ADR-0014.1/0015.
- **G4 failure does not overturn the thesis** but blocks ADR-0017 until the
  evidence-ledger fallback from ADR-0014.1 is built (resumption cannot be the
  only memory mechanism).
- **G5 failure is a contract violation** — treated as a bug that invalidates
  the run, not as a scoring outcome.
- ADR-0015's "bench experiments answered yes" claim is downgraded to
  "suggestive manual results" until a gate run is committed.

## Architecture

```
internal/sidecar/evals/
  episode.go     – Task, TaskChecks, Episode, TurnRecord, RewardBreakdown
  rewards.go     – deterministic reward functions (pure, unit-tested)
  tasks.go       – task loading + validation from testdata/tasks/*.json
  profiles.go    – three profile definitions + prompt builders
  runner.go      – episode runner (in-process Ask for sidecar; ACP turn for direct)
  client.go      – eval-owned ACP client for direct profiles (allow read/exec, deny write)
  store.go       – .ghx-evals/runs/<run-id>/ JSON artifacts
  episode_test.go, rewards_test.go, tasks_test.go – normal unit tests
  mock_e2e_test.go – full episode through a mock ACP agent (normal CI, no LLM)
  eval_test.go   – //go:build agent_e2e — live agent episodes
  mockagent/     – package main: scripted ACP agent for plumbing tests
  testdata/tasks/*.json
```

Only tests that spawn a **real** agent carry the `agent_e2e` tag. The eval
package itself compiles untagged so `go vet`/`go build ./...` always cover it.

## Consequences

- The thesis becomes falsifiable: thresholds are committed before any result.
- The Go sidecar gains its first tests and its first eval coverage.
- Two eval stacks exist temporarily (`ghx-bench` TS engine, this Go kernel);
  resolving that duplication is deliberate follow-up, not part of this slice.
- The gate run itself requires a live ACP agent and GitHub network access; this
  slice must deliver everything up to that point plus a mock-agent proof that
  the pipeline works end-to-end.

## Implementation Notes

*(Phase 3 — appended during engineering, 2026-07-03.)*

### Built and verified

- `internal/sidecar` gained its first unit tests: `report_test.go`,
  `prompt_test.go`, `session_test.go` (extraction edge cases, first-turn vs
  follow-up prompt contract, session lifecycle incl. ACP session ID
  persistence).
- `internal/sidecar/evals/` implemented per the architecture above. All of it
  compiles untagged; `go vet` passes with and without `agent_e2e`.
- **Mock-agent end-to-end proof**: `mockagent/` is a scripted **real ACP
  agent** (initialize, session/new, session/load, session/update
  notifications, session/prompt) built on `coder/acp-go-sdk`'s agent side.
  `TestMockSidecarEpisode` drives the exact production path —
  `sidecar.Ask` → spawn → handshake → `NewSession`, then **`LoadSession`
  resumption on the follow-up turn** — and asserts tool-call capture, report
  extraction, context accounting, rewards, and artifact roundtrip.
  `TestMockDirectEpisode` proves the direct-profile path (one live session,
  bare-question follow-ups). Both pass in normal CI with no LLM, no token,
  no network.

### Engineering decisions and deviations

1. **`sidecar.Ask` signature changed** from `(*Report, error)` to
   `(*Report, *TurnResult, error)`. The eval runner needs the full streamed
   text and observed tool calls to account for sidecar-internal exploration;
   discarding them inside `Ask` made the boundary unmeasurable. Single CLI
   caller updated.
2. **Deliberate session asymmetry between profiles.** The sidecar profile
   spawns an agent process per turn and resumes via the persisted ACP session
   ID — exactly what repeated `ghx sidecar ask` invocations do, which is what
   the G4 memory gate must measure. Direct profiles hold one live session for
   the whole episode, modeling a main agent that explores within its own
   conversation. This asymmetry is the thesis boundary, not an accident.
3. **Eval-owned permissive client for direct profiles.** Production
   `denyClient` rejects all permission requests; baselines that cannot run
   read-only shell commands would be strawmen. `evals/client.go` approves
   non-write tool kinds, rejects and **records as violations** edit/delete/
   move requests and file writes.
4. **Known live-run risk surfaced by this design**: the production sidecar's
   `denyClient` rejects *every* permission request, so a live sidecar episode
   only works with agents that execute read-only shell without asking. If the
   gate run fails this way, that is a product finding about the sidecar
   permission contract (likely needing the same kind-based allow logic as the
   eval client) — it must be recorded, not patched in the harness.
5. **Context accounting is a produced-text approximation.** ACP session
   notifications expose agent-produced text and tool-call titles, not tool
   *outputs* consumed by the agent. Both sides of the comparison use the same
   approximation; the G3 threshold (0.35×) has enough margin that this does
   not decide the verdict by itself.
6. **Task ground truth**: `hono-middleware` and `openai-node-streaming` come
   from the saved manual runs in `experiments/ghx-sidecar/`;
   `ghx-mapengine` was verified directly against this repo
   (`internal/mapengine/types.go: mapAuto`). The ADR-0016 `express-routing`
   example was **not** carried over — its `lib/router/*` ground truth is
   stale for Express 5 (router extracted to a separate package). The gate run
   needs ≥ 3 more tasks; add them with verified ground truth only.

### Live-run status (this environment)

`go test ./internal/sidecar/evals -tags=agent_e2e -run TestEpisodes` skips
with an actionable preflight diagnostic: no `GH_TOKEN`/`GITHUB_TOKEN`, and no
ACP adapter binary is installed (`claude`/`codex` CLIs are present but do not
speak ACP over stdio; `claude-code-acp`/`codex-acp`/`kiro` are absent). The
gate run therefore remains open work for an environment with a GitHub token
and an installed ACP adapter. Everything up to that point — kernel, rewards,
artifacts, plumbing proof — is implemented and green.
