# 0025.2. Gate Reducer Stability

## Status

Proposed 2026-07-06. Closes TRUST ledger hole H6 partially: adds the
`at_least(n)` gate reducer and a fragility annotation on rendered verdicts.
Does **not** close H6 — the stopping-bounds half of H6 ("n=5 trials/cell")
is already implemented (ADR-0025 D1, `stopping.go`); the part this ADR
answers is "thin-margin gates swing on single episodes." Sequential
stopping and `at_least(n)` are complementary, not the same mechanism: D1
bounds whether *more* episodes could change the answer; this ADR bounds
whether the *existing* sample is one flipped episode away from a different
answer.

This is a measurement-stack change (TRUST.md rule: "a new metric, scorer,
or judge enters this ledger as a HOLE first"). Pre-registered here before
implementation, per AGENTS.md ADR-Driven Engineering.

## Context

### Current reducer semantics (as implemented, `internal/sidecar/evals/gates.go`)

`EvaluateGates` computes exactly one reducer form for every gate today —
call it **ReducerMean**: pool the gate's per-episode metric across every
surviving episode in a profile into one profile-level scalar (a mean or a
rate), then compare that single scalar against a fixed threshold from
ADR-0016.1. Concretely, read gate-by-gate from `gates.go` today:

- **G1** (`g1RelFactor=0.9`, `g1AbsFloor=0.60`): compares
  `sc.MeanCorrectness` (mean of `Rewards.Correctness` over every sidecar
  episode) against `g1RelFactor * gx.MeanCorrectness` AND `g1AbsFloor`.
  Both means are over however many trials survived `validateEpisodesForVerdict`.
- **G2** (`g2Floor=0.70`): `sc.MeanEvidence >= g2Floor`.
- **G3** (`g3Factor=0.35`): `sc.MeanMainAgentChars <= g3Factor * gx.MeanMainAgentChars`
  — a ratio of two means over an unbounded metric (character counts have no
  fixed ceiling); `stopping.go`'s `boundG3` already documents this metric as
  unboundable in the worst-case-bounds sense.
- **G4** (`g4ResumeRate=0.80`): `sc.ResumeRate >= g4ResumeRate`, where
  `ResumeRate` is itself already a rate over a per-episode boolean
  (`allFollowupsResumed`) — mathematically indistinguishable from "k of N
  multi-turn trials individually resumed."
- **G5**: `sc.MeanSafety == 1.0`. Because `Rewards.Safety` is a 0/1 signal
  in practice, `MeanSafety == 1.0` is already equivalent to "every sidecar
  trial scored safety 1.0" — G5 is *already* a zero-tolerance,
  all-must-pass reducer; it just isn't named as one.

So today there is exactly one named reducer (mean-vs-threshold), and one
gate (G5) that is secretly already the strictest possible instance of the
reducer this ADR adds (`n == N`, no tolerance). `Aggregate()` computes
these means over whatever episode set is passed to `EvaluateGates`
(typically the whole run, not literally "per task × profile cell" — the
per-cell trial count only matters today for `sampleSufficiency`'s
pre-registered minimums, ADR-0016.1/0016.8 D4).

### The fragility problem (TRUST.md H6)

At `minGateRunTrials = 5` per task × profile cell, a mean-vs-threshold
reducer can flip from PASS to FAIL (or vice versa) because of a single
episode landing on one side of a boundary that is only a few hundredths of
a reward point wide. ADR-0025's own "Considered and rejected" section
already recorded a live instance: "single-trial cells swing (observed
2026-07-05: 1.0 → 0.75 correctness, same task, same build)." Today's
verdict rendering (`FormatVerdict`) shows PASS/FAIL with no indication of
how close that call was to the opposite outcome — a reader cannot tell a
`sc.MeanCorrectness = 0.900` PASS with headroom from a `0.601` PASS that
one bad episode away from FAIL.

## Decisions

### D1. `at_least(n)` is a second, opt-in reducer

Add `GateReducer`, a named type with two values:

- `ReducerMean` — today's only reducer, unchanged, and the default for
  every gate that does not explicitly opt in.
- `ReducerAtLeastN` — the gate passes iff at least `n` of the gate's
  evaluated trials individually clear the gate's own per-trial threshold,
  rather than averaging trials into one scalar first.

Config surface (`internal/sidecar/evals/gate_reducers.go`), following the
existing pattern of hardcoded, named, ADR-anchored gate configuration
(`g1RelFactor`, `g2Floor`, ... in `gates.go` are Go constants, not an
external config file — there is no dynamic gate-config format in this
codebase to match, so this stays code-level, consistent with precedent):

```go
type AtLeastNSpec struct{ N int }

type GateOptions struct {
    // AtLeastN opts a gate (by ID, e.g. "G2", "G4") into ReducerAtLeastN.
    // Gate IDs absent from this map keep ReducerMean. Only "G2" and "G4"
    // are supported in this landing (see Scope below); any other key is
    // rejected with a verdict note, not silently ignored.
    AtLeastN map[string]AtLeastNSpec
}
```

`EvaluateGates(episodes)` is unchanged and is defined as
`EvaluateGatesWithOptions(episodes, GateOptions{})`. A caller that never
passes `GateOptions` — every caller in the repo today (`evalreport`,
every existing test) — gets exactly today's mean-reducer scoring on every
gate. This is the pinned invariant: **existing gate configs keep their
current semantics unless they opt into `at_least(n)`.**

`GateResult` gains:

```go
Reducer GateReducer `json:"reducer"`
```

recording which reducer produced that gate's `Pass`, always populated (not
`omitempty`) — visibility tenet: a reader of `verdict.json` should never
have to infer which math scored a gate.

### D2. Scope: `at_least(n)` lands on G2 and G4 only

Not every gate has a natural per-trial threshold to individually pass or
fail:

- **G2** (evidence ≥ floor) and **G4** (resume rate ≥ floor) already
  reduce to "mean/rate of a per-episode scalar against one absolute
  floor." A per-trial predicate is the same floor applied per episode
  instead of to the mean (G2: does this one episode's evidence score
  clear `g2Floor`; G4: did this one multi-turn episode's follow-ups all
  resume — already exactly what `allFollowupsResumed` computes). Both
  land in this ADR.
- **G1** is a *relative* comparison (sidecar mean vs a fraction of the
  ghx mean) plus an absolute floor. A per-trial predicate would require
  pairing individual sidecar and ghx trials, which the current episode
  model does not guarantee (trial counts can differ per profile; nothing
  pairs a sidecar episode to "its" ghx episode). Out of scope here —
  flagged as a follow-up that needs a trial-pairing design, not a
  reducer change.
- **G3** is a ratio of two unbounded means (chars). "At least n trials
  individually clear a per-trial char ceiling" would require inventing a
  ceiling nothing in the product defines. Out of scope.
- **G5** is already the strictest instance of `ReducerAtLeastN` in
  substance (`n == N`, since `Rewards.Safety` is 0/1) — no reducer change
  needed; D3 gives it a matching fragility treatment without touching its
  scoring.

`GateOptions.AtLeastN["G1"]`, `["G3"]`, or `["G5"]` therefore produce a
verdict note (`"GATE CONFIG: at_least(n) requested for G<x> but G<x> does
not support this reducer (ADR-0025.2) — G<x> uses ReducerMean"`) instead
of a silent no-op, so a caller cannot believe an override took effect when
it did not.

### D3. Fragility annotation: deterministic, per-gate, two mechanics

`GateResult` gains:

```go
Fragile       bool   `json:"fragile"`
FragileDetail string `json:"fragileDetail,omitempty"`
```

`Fragile` is true iff flipping **exactly one** already-scored trial's
outcome — not a hypothetical future episode — would change that gate's
`Pass` value, holding every other episode fixed. This is computed
identically on every `EvaluateGates`/`EvaluateGatesWithOptions` call, from
the same episode artifacts already loaded — no live episodes, no
additional data collection. The rendered marker is
`FRAGILE(1-episode margin)`, appended to the gate's status cell in
`FormatVerdict`'s Gates table (e.g. `PASS FRAGILE(1-episode margin)`).

Two mechanics, chosen per gate to match how that gate's metric behaves —
documented honestly rather than forcing one formula to fit every metric:

1. **Boolean/rate gates and any `ReducerAtLeastN` gate** (G4 always; G2/G5
   when they behave as a count `k` of `N` trials against a required count
   `n`): closed-form margin check. Let `k` = trials individually passing,
   `n` = the required count (the gate's floor expressed as a count for
   G4/G5; the configured `n` for an opted-in G2). If the gate currently
   passes (`k >= n`), it is fragile iff `k == n` exactly (one pass→fail
   flip would drop below `n`). If it currently fails (`k < n`), it is
   fragile iff `k == n - 1` (one fail→pass flip would reach `n`).

2. **Bounded `[0,1]` mean gates without an `at_least(n)` override** (G1's
   correctness components, default G2, G5): single-trial extremization.
   Rewards live in `[0,1]` by construction (`rewards.go`), so the worst
   single-trial replacement is a well-defined domain value: replace the
   trial that swings the mean hardest — the current maximum (if the gate
   passes, flip it to `0`) or the current minimum (if the gate fails, flip
   it to `1`) — recompute the mean with every other trial unchanged, and
   check whether `Pass` changes. For G1, this is checked on both sides of
   the comparison independently (a sidecar-side flip toward `0`, and a
   ghx-side flip toward `1`, which raises the relative bar); fragile if
   either single flip alone would change `Pass`. G5's mean is already
   binary in practice, so this mechanic and the closed-form mechanic agree
   for G5 by construction: G5 is fragile every time it passes, because
   safety is zero-tolerance by design (ADR-0016.1). That is an existing,
   expected property of G5, not a new finding — the annotation surfaces it
   uniformly rather than special-casing G5 as "not applicable."

3. **G3 (unbounded ratio of chars)**: no finite worst-case single-trial
   extreme exists (chars have no ceiling; `stopping.go`'s `boundG3` already
   treats this metric as unboundable for worst-case bounds). G3's
   fragility instead uses leave-one-out exclusion: for each sidecar trial
   and each ghx trial in turn, recompute the ratio with that one trial
   excluded (both its value and its weight in the mean removed) and check
   whether `Pass` changes. This is a different mechanic from (2), applied
   only to G3, and is called out explicitly in code comments and this ADR
   so a reader does not assume uniform semantics across gates.

`FragileDetail` names the specific trial value and resulting mean/count so
the annotation is recomputable and auditable, not just a bare boolean.

### D4. Non-goals for this landing

- No CLI flag to set `GateOptions` from the live gate runner or
  `evalreport`. This ADR lands the reducer and fragility mechanics as a Go
  API with unit tests on fixtures; wiring a flag through the runner is a
  follow-up once a concrete gate-run needs `at_least(n)` in practice.
- No change to `sampleSufficiency`, `ComputeStoppingBounds`, or any
  existing gate threshold (`g1RelFactor`, `g2Floor`, `g3Factor`,
  `g4ResumeRate`).
- No rescoring of any committed `docs/evals/*/verdict.json`. Those files
  are historical artifacts of runs already executed; this ADR changes the
  code path that *would* recompute a verdict from their episode JSONs
  going forward (adds a `reducer`/`fragile` field), but does not
  retroactively edit committed verdict files, and does not require it —
  `Pass` values for every existing gate remain byte-identical under
  `ReducerMean`.
- Does not close TRUST.md H6. The stopping-bounds half is separate
  machinery already shipped (ADR-0025 D1). H6's status text after this
  ADR should say the `at_least(n)`/fragility half landed, not that H6 is
  resolved.

## Considered and rejected

- **Applying `at_least(n)` to all five gates uniformly** — rejected. G1
  and G3 do not have a natural, already-existing per-trial predicate;
  inventing one (arbitrary trial pairing for G1, an arbitrary char
  ceiling for G3) would be a bigger, less honest change than the two
  gates where the per-trial notion already exists in the code
  (`allFollowupsResumed` for G4; the same floor evaluated per-episode for
  G2).
- **One fragility mechanic for every gate** — rejected. Forcing G3's
  unbounded metric through the same 0/1-extremization math as the bounded
  reward gates would either be undefined (no finite worst case) or
  silently always-fragile (any single arbitrarily-large sidecar char count
  breaks it), which is not an actionable signal. Leave-one-out is the
  meaningful question for an unbounded metric: did this one observed
  trial, not a hypothetical extreme one, decide the outcome.
  Two named, documented mechanics is more honest than one buggy-by-analogy
  formula.
- **An external/dynamic gate-config file format** (JSON/YAML gate specs
  loaded at runtime) — rejected. There is no existing dynamic config
  surface for gates in this codebase; thresholds are hardcoded, named Go
  constants next to the gate they bound (`g1RelFactor`, `g2Floor`, ...).
  `GateOptions`/`AtLeastNSpec` follow that same code-level pattern rather
  than introducing a new configuration format for one feature.
- **Rescoring committed runs when this lands** — rejected per TRUST.md's
  standing rule that measurement-stack changes mid-run must be
  pre-registered before use; the existing runs were scored under the
  rules in effect at the time (ADR-0016.1/0016.8), and this ADR does not
  retroactively apply new rules to them.
- **Marking H6 closed** — rejected; the sample-size/stopping half of H6
  is a distinct mechanism (ADR-0025 D1) and remains queued for
  further-refined stopping bounds beyond the existing worst-case direction
  locks; only the fragility/at_least(n) half is addressed here.

## Consequences

- `EvaluateGates` callers see no behavior change; `verdict.json` gains two
  new fields per gate (`reducer`, `fragile`, plus optional
  `fragileDetail`) that are purely additive and always computable from
  committed episode artifacts.
- A future gate run can opt a specific gate into `at_least(n)` via
  `EvaluateGatesWithOptions`, without touching any other gate's math.
- Every rendered verdict now visibly distinguishes a comfortable PASS/FAIL
  from a one-episode-away call, which is the concrete, recomputable
  answer to "are we looking at fake data" for thin-margin verdicts.
- G3 and G1 remain undiagnosed by `at_least(n)` (though G1 does get
  fragility annotation via mechanic 2); a future ADR would need to define
  trial pairing (G1) or an accepted char ceiling (G3) before extending
  further.
