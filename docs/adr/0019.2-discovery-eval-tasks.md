# 0019.2. Discovery-Class Eval Tasks

## Status

Proposed. Fulfills ADR-0019.1 D5: discovery quality must be measured by a
separate, pre-registered eval design before any discovery number is quoted.

## Context

ADR-0019.1 made `--repo` optional so the sidecar can answer the earlier
reconnaissance question: "which repos do X?" That product change deliberately
left `internal/sidecar/evals` untouched. The existing eval corpus is
repo-scoped by construction: `Task` requires `repo`, `turns`, and deterministic
`checks` (`expectedFiles`, `expectedSymbols`, `requiredClaims`,
`unacceptableClaims`, `avoidPaths`, `contaminationPaths`). `LoadTasks` reads
`testdata/tasks/*.json` deterministically, and `Task.Validate` enforces
ADR-0016.2's discoverable-check rule so agents cannot score by parroting the
question.

Discovery is a different task family. The answer is not "where in this repo is
X?" but "which repos appear to implement X?" Ground truth is a target set of
repositories, not a path/symbol checklist inside one repository. The scoring
problem also changes: a model may already know famous repos from training data,
especially for tasks like LiteLLM, Langfuse, Phoenix, or official MCP SDKs. A
named repo is therefore not enough evidence that exploration happened.

The 2026-07-06 fixbatch run adds a second warning: self-referential or
answer-bearing docs poison baselines. In that run, `ghx-mapengine` repeatedly
hit the `answer_doc_contamination` guard because a baseline agent could
legitimately read ghx's own ADRs containing the answer. Discovery tasks are
more exposed to that failure mode because their natural candidates are famous
repos with rich READMEs, docs, blog posts, and comparison pages.

## Decision

Add a separate discovery-task class and scorer. Do not retrofit discovery into
the repo-scoped `Task` shape and do not mix discovery scores into G1-G5.

### D1. Discovery task shape

A discovery task asks one or more turns shaped like:

> Which open-source repos do X?

The task fixture is a pre-registered JSON object, separate from the current
repo-scoped fixtures:

```json
{
  "id": "openai-compatible-ai-gateways",
  "kind": "discovery",
  "turns": [
    "Which open-source repos provide a self-hostable AI gateway or proxy with OpenAI-compatible APIs?"
  ],
  "checks": {
    "targetRepos": [
      {
        "repo": "BerriAI/litellm",
        "requiredEvidence": ["README.md", "litellm/proxy/"],
        "famous": true
      }
    ],
    "acceptableAlternates": [
      {
        "repo": "Portkey-AI/models",
        "policy": "accepted-extra",
        "reason": "Companion open-source model/pricing database used by Portkey gateway; not a gateway itself."
      }
    ],
    "excludedRepos": [
      {
        "repo": "openai/openai-node",
        "reason": "Provider SDK, not a gateway/proxy."
      }
    ],
    "contaminationPaths": [
      "docs/adr/",
      "docs/evals/",
      "comparison",
      "benchmark"
    ]
  }
}
```

`targetRepos` is the recall denominator. Each target is an `owner/repo` plus
optional required evidence hints. Evidence hints are not answer strings to
match in the final answer; they are pre-run freshness checks and verifier
anchors. For famous repos, at least one actual read path from inside the repo
is required before the target can count as verified.

`acceptableAlternates` are pre-registered before the run. They can be:

- `accepted-extra`: counts as non-penalized precision if verified, but does not
  increase target-set recall.
- `substitute-for:<owner/repo>`: counts for recall only when the named target
  has moved, renamed, or split and the substitute relation was pre-registered.
- `family-member`: counts as non-penalized precision for ecosystem repos that
  are useful but not the primary implementation.

No post-hoc acceptable alternates are allowed in a citable run. If a run
discovers a genuinely valid missing repo, the artifact records it as a finding,
then a later ADR/task update may add it before the next run.

`excludedRepos` are common false positives. Naming an excluded repo is a
precision penalty even if cited.

`contaminationPaths` generalize ADR-0016.8's answer-doc contamination guard.
They are repo-relative path prefixes, not global web URLs. If an episode reads
a target repo's own answer-bearing comparison page, benchmark page, or internal
"alternatives" page that directly lists the pre-registered target set, the
episode is flagged and excluded from discovery gate aggregates.

### D2. Famous-repo contamination and recall-vs-exploration split

Discovery tasks explicitly distinguish three states:

| State | Meaning | Counts for gate recall? |
|-------|---------|--------------------------|
| `verified-target` | Target repo is named and backed by a cited path that the episode actually read. | Yes |
| `named-only-target` | Target repo is named, but no matching read path exists in tool traces. | No |
| `search-only-target` | Target appears only in search results or repo listings. | No; inferred only |

Training-data familiarity is expected, not treated as cheating. The scorer
does not try to prove where the model learned a repo name. It only asks whether
the episode verified the claim during the run.

A repo is verified only when all are true:

1. The answer names the repo as `owner/repo` or an unambiguous project name
   mapped in the fixture.
2. The report cites at least one path under that repo, using `owner/repo:path`
   or a command source that resolves to that repo and path.
3. The tool trace shows a read-like operation for that path: `ghx read`,
   `gh api contents`, raw GitHub file fetch, or equivalent direct file
   inspection.
4. Search-result snippets, `gh search`, `ghx search`, repo metadata, stars,
   topics, and README excerpts returned by search count as inferred until a
   file is read.

For famous targets (`famous: true`), README-only evidence is sufficient only
when the task asks whether the repo publicly claims the capability. If the task
asks how the repo implements the capability, at least one implementation path
must also be read. The fixture records that distinction in `requiredEvidence`.

### D3. Scoring

Discovery scoring produces separate metrics; none reuse repo-scoped
`correctness` directly.

| Metric | Definition |
|--------|------------|
| `verifiedRecall` | verified target repos ÷ target repos |
| `namedRecall` | named target repos ÷ target repos |
| `verifiedPrecision` | verified accepted repos ÷ verified named repos, excluding `accepted-extra` from penalties |
| `namedPrecision` | named accepted repos ÷ all named repos, with excluded repos penalized |
| `evidence` | fraction of verified repo claims carrying a concrete cited read path, plus command trail presence |
| `inferenceHonesty` | 1 when search-only or metadata-only candidates are reported as inferred/unverified, else penalized |
| `compression` | same boundary model as ADR-0016.1: sidecar report chars vs direct transcript chars |
| `safety` | same as G5: no write or permission violations |

`namedRecall - verifiedRecall` is reported as the **familiarity gap**. A large
gap means the agent may know the right names but did not verify them. That is a
useful finding, not a pass.

Evidence rules inherit ADR-0019.1 D3: search-only equals inferred. A discovery
answer may include an unverified tail, but those repos must be labeled as
inferred or unverified and do not count toward verified recall.

### D4. Discovery gates are separate from G1-G5

Discovery gets its own pre-registered gates:

| Gate | Threshold |
|------|-----------|
| **D-G1 verified recall** | mean(`ghx-sidecar`) `verifiedRecall` >= 0.65 absolute and >= 0.90 × mean(`ghx`) |
| **D-G2 verified precision** | mean(`ghx-sidecar`) `verifiedPrecision` >= 0.70 |
| **D-G3 evidence honesty** | mean(`ghx-sidecar`) `evidence` >= 0.75 and `inferenceHonesty` >= 0.80 |
| **D-G4 familiarity gap** | mean(`ghx-sidecar`) (`namedRecall - verifiedRecall`) <= 0.25 |
| **D-G5 compression** | mean main-agent chars for `ghx-sidecar` <= 0.35 × mean for `ghx` |
| **D-G6 safety** | 1.0 on every `ghx-sidecar` discovery episode |

A formal discovery gate run is at least 4 discovery tasks, each with at least 3
target repos, 5 valid trials per task × profile, identical agent identity
across profiles, and committed artifacts under `docs/evals/<run-id>/`.

Discovery verdicts must label themselves separately:

- `DISCOVERY SUPPORTED`: D-G1 through D-G6 pass.
- `DISCOVERY NOT SUPPORTED`: D-G1 or D-G5 fails.
- `DISCOVERY EVIDENCE WEAK`: D-G2, D-G3, or D-G4 fails while D-G1/D-G5 pass.
- Any D-G6 failure invalidates the run as a contract bug.

Discovery metrics must never be averaged into G1-G5 repo-scoped aggregates.
A sidecar release can quote repo-scoped G1-G5 and discovery D-G* only as
separate claims.

### D5. Profile design

`plain` for discovery means a capable agent with raw GitHub tools, primarily
`gh search repos`, `gh search code`, `gh repo view`, `gh api`, and raw GitHub
file reads. It is not denied GitHub search; discovery without search would be a
strawman baseline.

`ghx` direct is meaningful and required. Discovery mode is exactly where ghx's
cross-GitHub primitives should matter: `ghx search`, `ghx repos`, `ghx read`,
and repo summaries can reduce the main agent's exploration burden. The
`ghx-direct` profile measures the tool value without the sidecar boundary.

`ghx-sidecar` is the production discovery path from ADR-0019.1: no repo scope,
discovery persona, ordinary session/report contract, and evidence citations
using `owner/repo` or `owner/repo:path`.

## Candidate task seeds

These are candidate fixtures, not yet accepted corpus entries. Target sets are
verified only at the repo-doc level from current public README/docs paths; each
needs a pre-run freshness check before use.

### Candidate A: OpenAI-compatible AI gateways

Question:

> Which open-source repos provide a self-hostable AI gateway or proxy with
> OpenAI-compatible APIs?

Pre-registered target set:

- `BerriAI/litellm` — verified from its README: it describes LiteLLM as an
  open-source AI Gateway and says it can call LLMs in OpenAI format
  ([README.md](https://raw.githubusercontent.com/BerriAI/litellm/main/README.md)).
- `Portkey-AI/gateway` — verified from its README: it describes an AI Gateway,
  local gateway URL, and an OpenAI-compatible client example
  ([README.md](https://raw.githubusercontent.com/Portkey-AI/gateway/main/README.md)).
- `Helicone/helicone` — verified from its README: it describes an AI Gateway
  through the OpenAI API and shows an OpenAI SDK `baseURL` pointed at Helicone
  ([README.md](https://raw.githubusercontent.com/Helicone/helicone/main/README.md)).

Famous-repo risk: high. LiteLLM and Helicone are likely in model training data.
A correct gate answer must cite read paths from each repo; a bare list of names
is named-only recall.

### Candidate B: MCP SDKs with Streamable HTTP support

Question:

> Which official Model Context Protocol SDK repos expose Streamable HTTP
> transport support?

Pre-registered target set:

- `modelcontextprotocol/typescript-sdk` — verified from README: ships server
  libraries with Streamable HTTP and middleware packages for Node, Express, and
  Hono
  ([README.md](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/README.md)).
- `modelcontextprotocol/python-sdk` — verified from README: says the SDK speaks
  every standard transport including stdio, Streamable HTTP, and SSE
  ([README.md](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/main/README.md)).

Unverified guess, not a target yet:

- `modelcontextprotocol/go-sdk` likely supports the full MCP spec, but the
  README evidence read for this ADR did not explicitly verify Streamable HTTP.
  It may become an acceptable alternate or target only after a direct docs/code
  read finds the transport implementation.

Famous-repo risk: high. Official MCP SDK names are likely familiar. Verified
recall requires reading transport docs or implementation paths, not only naming
the org repos.

### Candidate C: Open-source LLM evaluation and observability platforms

Question:

> Which open-source repos provide LLM application evaluation tooling, including
> LLM-as-judge, automated evals, or trace-backed experiment evaluation?

Pre-registered target set:

- `Arize-ai/phoenix` — verified from README: Phoenix is open-source AI
  observability for experimentation, evaluation, and troubleshooting, with LLM
  evals and eval packages
  ([README.md](https://raw.githubusercontent.com/Arize-ai/phoenix/main/README.md)).
- `langfuse/langfuse` — verified from README: Langfuse is open-source LLM
  engineering, supports evaluations including LLM-as-a-judge, code evaluators,
  feedback, manual labeling, and custom pipelines
  ([README.md](https://raw.githubusercontent.com/langfuse/langfuse/main/README.md)).
- `promptfoo/promptfoo` — verified from README: Promptfoo is a CLI/library for
  evaluating and red-teaming LLM apps, with automated evaluations and local eval
  runs
  ([README.md](https://raw.githubusercontent.com/promptfoo/promptfoo/main/README.md)).

Boundary note: this task intentionally mixes observability platforms and eval
tools. The fixture must define whether "platform" requires hosted/self-hosted UI
or whether CLI-only eval tooling is a target. If that boundary stays ambiguous,
`promptfoo/promptfoo` should move to `accepted-extra` rather than target set.

## Considered and rejected

- **Reuse repo-scoped `Task` with empty `repo`** — rejected. The current type's
  contract is a single subject repo plus path/symbol/claim checks. Discovery
  needs target-set domain objects, acceptable-alternate policy, named-only vs
  verified accounting, and famous-repo contamination metadata.
- **Count named target repos as correctness** — rejected. This would reward
  training-data recall and make famous repos dominate the score. Named recall
  is reported as a diagnostic, not a gate pass.
- **Require an exhaustive GitHub universe** — rejected. Discovery tasks measure
  recall against a pre-registered target set, not all possible repos. New valid
  discoveries become corpus updates for future runs.
- **Use only a judge scorer** — rejected. Discovery quality will benefit from a
  judge later, but the gate needs deterministic, recomputable target-set
  metrics first. Judge disagreement can explain misses after the deterministic
  layer exists.
- **Mix discovery into G1-G5** — rejected. Repo-scoped reconnaissance and
  cross-repo discovery answer different questions. Mixing them would hide
  regressions in either task family.
- **Disqualify famous repos entirely** — rejected. Famous repos are real user
  targets. The fix is to score explored-and-verified separately from
  named-only, not to make the corpus obscure for obscurity's sake.

## Consequences

Discovery can become citable without weakening the existing gate contract. The
new score answers: "Can the sidecar discover and verify the right repos with
less main-agent burden?" The old score continues to answer: "Can the sidecar
investigate a known repo with correct, evidenced, compressed reports?"

The implementation must add new task/domain types and scorer code under
`internal/sidecar/evals` without touching existing G1-G5 semantics. Any
measurement-stack change after this ADR must be pre-registered before a
discovery run is rescored.
