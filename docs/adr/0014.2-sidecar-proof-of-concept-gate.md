# 0014.2. `ghx` Sidecar Proof-of-Concept Gate

## Context

ADR-0014.1 defines the vision: `ghx` should remain a transparent GitHub evidence engine, while a cheap specialized sidecar agent performs bounded repository reconnaissance for the main coding agent.

This ADR defines the proof-of-concept gate before building architecture. The question is not whether a sidecar sounds useful. The question is whether manual sidecar experiments produce enough measurable signal to justify turning the idea into product work.

## Hypothesis

A specialized `ghx` sidecar agent can answer focused GitHub repository-navigation questions more consistently, cheaply, and auditably than asking the main coding agent to learn and operate `ghx` directly.

The cost thesis is central, not incidental. The sidecar is valuable because expensive exploratory uncertainty is moved out of the main agent's context window and into a cheaper specialized worker. The main agent should receive the compressed result: relevant files, verified evidence, uncertainty, and next reads. It should not spend premium tokens learning the repository, discovering false leads, handling broad search truncation, or remembering `ghx` doctrine.

The delegation thesis is equally central. The main agent should not need `ghx` skill files, CLI command grammar, flag semantics, search gotchas, or map/read doctrine in its context. It should communicate with the sidecar in ordinary task language: "find where streaming is implemented", "trace the auth path", "identify likely files". The sidecar owns the translation from English intent to `ghx` operations.

The distillation thesis completes the loop. The main agent should not need to read large repository docs, generated API files, broad trees, or many candidate source files just to locate the relevant implementation path. The sidecar should absorb that exploratory reading and return a distilled artifact: verified files, supporting evidence, rejected or suspected areas, uncertainty, and recommended next reads.

The backend-abstraction thesis extends this beyond remote `ghx` primitives. `ghx` can become the plain-English exploration facade over multiple code-understanding tools. The sidecar should start with cheap remote-only `ghx` exploration, then escalate to Codemap, local indexing, or other context-engineering tools only when the question requires deeper structure. The main agent still speaks English; the sidecar chooses the backend and reports what it used.

The sidecar is valuable if it lets the main agent delegate intent:

```text
Where is middleware composition implemented in honojs/hono?
```

Instead of forcing the main agent to manage exploration mechanics:

```text
Run explore.
Inspect tree.
Map candidate files.
Avoid unsupported search syntax.
Grep bounded paths.
Read only relevant line ranges.
Return evidence.
State uncertainty.
```

The main agent only needs to know one interaction pattern:

```text
Ask the ghx sidecar a repository question in English.
Receive a compact evidence report.
Use the report for judgment or implementation.
```

It should not need to consume broad repository context first.

It also should not need to know whether the answer came from remote `ghx`, Codemap, a local index, or a future backend. It only needs the backend trace in the final report so the result remains auditable.

In the OpenAI Node run, the sidecar spent many turns and commands exploring broad SDK streaming surfaces, correcting overclaims, narrowing Assistant/Threads routes, and classifying Realtime as suspected. That work is exactly the kind of exploratory token burn that should happen in the cheaper sidecar, not in the main coding agent.

## Experiment Goal

Prove whether a manual `ghx-sidecar` prompt is useful enough to justify the next phase.

The goal is not to prove ACP, `acpx`, Codex `app-server`, Codex `mcp-server`, Codemap integration, fine-tuning, or a daemon. Those are architecture candidates. They are out of scope until the sidecar behavior itself passes this gate.

## What Success Means

The proof of concept succeeds if the sidecar repeatedly produces a compact, evidence-backed reconnaissance report that the main agent can use without knowing `ghx` command grammar or exploration doctrine.

The sidecar does not need to be perfect. It must be materially useful and measurably better than ad hoc main-agent exploration.

## Test Unit

One test case is:

```text
repo + focused repo question + optional follow-up
```

Examples:

```text
honojs/hono
Where is middleware composition implemented?
Follow-up: How do errors propagate through that path?
```

```text
openai/openai-node
Where are streaming responses implemented or exposed?
Follow-up: Which public APIs route into that implementation?
```

```text
modelcontextprotocol/typescript-sdk
Where is server transport setup implemented?
Follow-up: Which transports share the same setup path?
```

## Measurable Goals

| Goal | Measurement | Pass threshold |
|------|-------------|----------------|
| Find relevant files | Sidecar returns 1-5 files that plausibly answer the question | At least 4 of 5 test cases |
| Evidence quality | Claims are tied to symbols, snippets, grep hits, maps, line ranges, or command output | At least 4 of 5 test cases |
| Command transparency | Exact `ghx` commands are listed | 5 of 5 test cases |
| Bounded exploration | No clone, no repo dump, no broad full-file reading unless justified | At least 4 of 5 test cases |
| Budget discipline | Initial question uses max 8 `ghx` commands; follow-up uses max 5 additional commands | At least 4 of 5 test cases |
| Memory reuse | Follow-up explicitly reuses prior facts and avoids restarting from zero | At least 3 of 5 follow-up cases |
| Main-agent usability | Main agent can identify next files or next action from the report without knowing `ghx` syntax | At least 4 of 5 test cases |
| Main-context savings | Main agent receives compact evidence instead of spending its own context on broad exploration, false leads, and command choreography | At least 4 of 5 test cases |
| Tool-doctrine isolation | Main agent does not need `ghx` command grammar, skill docs, search gotchas, or map/read rules in context | At least 4 of 5 test cases |
| Repository-context compression | Main agent receives a distilled artifact instead of reading broad repo docs, generated files, trees, and candidate source files | At least 4 of 5 test cases |
| Backend abstraction with visibility | Sidecar can choose remote `ghx` first and identify when Codemap/local indexing would be needed, while reporting backend choices explicitly | At least 4 of 5 test cases |
| Uncertainty discipline | Report states what was not checked or what could require deeper analysis | At least 4 of 5 test cases |
| Role discipline | Sidecar does not implement, refactor, commit, or become the main coding agent | 5 of 5 test cases |
| Backend honesty | Report says which backend was used and whether Codemap/clone/local index was not used | 5 of 5 test cases |

## Scoring Rubric

Each test case gets a score out of 10:

| Point | Criterion |
|-------|-----------|
| 1 | Finds 1-5 relevant files |
| 1 | Identifies the primary file or path correctly |
| 1 | Provides concrete evidence tied to files/symbols/lines/commands |
| 1 | Lists exact commands run |
| 1 | Stays within command budget |
| 1 | Avoids clone and broad repo dump |
| 1 | States uncertainty |
| 1 | Output is directly usable by the main agent |
| 1 | Compresses repo exploration into a concise artifact and hides `ghx` command choreography behind natural-language delegation |
| 1 | Does not overstep into implementation or unsupported claims |

Memory reuse remains a measured goal, but the 10-point rubric now treats main-context savings as the more central scoring dimension. Follow-up behavior should be recorded separately when a test includes a persistent session.

## Decision Thresholds

| Result | Decision |
|--------|----------|
| Average score below 6.5 | Stop architecture work. Keep only a prompt or documentation note. |
| Average score 6.5-7.9 | Continue prompt iteration. Do not build runtime architecture yet. |
| Average score 8.0 or higher, with at least 4 of 5 cases passing core goals | Move to MVP phase 2: structured prompt/report schema, sidecar preflight, and repeatable evaluation. |
| Average score 8.5 or higher across two different model/runtime configurations | Begin architecture comparison: manual Codex session vs Codex `app-server` vs ACP/`acpx` vs MCP. |

Core goals are:

- relevant files
- evidence quality
- command transparency
- bounded exploration
- main-agent usability
- main-context savings
- tool-doctrine isolation
- repository-context compression
- backend abstraction with visibility
- role discipline
- backend honesty

If any core goal fails in more than 1 of 5 cases, the POC does not pass regardless of average score.

## What The First Test Shows

The first saved sidecar run is in `experiments/ghx-sidecar/SIDECAR_ANSWERS.md`.

Test case:

```text
repo: honojs/hono
question: Where is middleware composition implemented?
follow-up: How do errors propagate through the middleware composition path?
```

Observed positives:

- The sidecar found the likely primary files: `src/compose.ts`, `src/hono-base.ts`, and `src/middleware/combine/index.ts`.
- It backed claims with concrete facts: `compose(...)`, `dispatch(i)`, `onError`, `onNotFound`, `#handleError`, and `compose(matchResult[0], this.errorHandler, this.#notFoundHandler)`.
- It listed commands run.
- It used remote `ghx` backends only.
- The follow-up reused previous facts instead of restarting from zero.
- The output was useful to the main agent as a next-read guide.

Observed negatives:

- The first answer exceeded the 8-command budget.
- It ran `ghx read --help`, which is setup noise and should not count as useful investigation.
- It formatted remote GitHub paths as local workspace links, which is misleading.
- It did not explicitly identify the repository snapshot or commit.

Initial judgment:

```text
Useful smoke test: yes.
Architecture proof: no.
Move beyond manual MVP: not yet.
Continue to measured POC: yes.
```

## What The OpenAI Node Deep Test Shows

The OpenAI Node sidecar run is saved separately in `experiments/ghx-sidecar/SIDECAR_ANSWERS_OPENAI_NODE.md`.

Test case:

```text
repo: openai/openai-node
question: Find where streaming responses are exposed and implemented. Identify public API methods that route into streaming, the shared runtime implementation, and suspected but unverified streaming surfaces.
```

This test became more valuable than the first smoke test because it stressed ambiguity, broad-search truncation, confidence calibration, and self-audit.

Observed positives:

- The sidecar found the major streaming implementation layers: `src/core/streaming.ts`, `src/streaming.ts`, `src/lib/responses/ResponseStream.ts`, and `src/lib/AssistantStream.ts`.
- It found concrete public streaming routes across multiple API surfaces: Responses, Chat Completions, Audio Transcriptions, Beta Threads, and Beta Thread Runs.
- It separated verified routes from suspected surfaces instead of claiming exhaustive coverage.
- It narrowed previously suspicious Assistant/Threads areas instead of trusting broad truncated grep output.
- It treated Realtime as suspected rather than verified because it had only map-level/event-shaped evidence.
- It reused prior memory from the same named session and continued the investigation rather than restarting from zero.
- It produced a report that a main agent could use without understanding `ghx` command grammar.
- It isolated exploratory token burn from the main agent. The sidecar absorbed broad search, truncation handling, Assistant/Threads narrowing, Realtime suspicion, and confidence correction, then returned a compact report.
- It translated an English repo question into `ghx` exploration without requiring the main agent to carry `ghx` flags, search limitations, or map/read rules in context.
- It compressed a large SDK investigation into a small artifact. The main agent did not need to read README streaming docs, broad `src/resources` trees, generated resource files, `ResponseStream`, `AssistantStream`, and `core/streaming` just to know where to look next.

Observed negatives:

- The stronger result required a more explicit prompt telling the sidecar to self-audit, separate verified/inferred/unverified claims, and treat truncation as incomplete evidence.
- The manual workflow still required the human to notice that the first OpenAI answer overclaimed confidence and ask for a better self-audit.
- The sidecar did not report a repository snapshot or commit.
- Some evidence remained file-level rather than line-range-level.
- The command budget is only a proxy for boundedness; the better product requirement is purposeful exploration, not a magic command count.

Judgment:

```text
Useful deep POC: yes.
Vision has merit: yes.
Manual workflow proves product need: yes.
Full architecture proof: no.
Next justified step: thin harness that removes human babysitting.
```

Approximate score:

```text
OpenAI initial answer: 7.2/10
OpenAI self-audit follow-up: 8.2/10
OpenAI deep self-auditing prompt: 8.3/10
```

The important result is not only that the sidecar found files. The important result is that the sidecar can perform a real evidence-quality loop when instructed:

```text
broad signal -> detect truncation -> narrow suspicious areas -> classify verified/inferred/unverified -> calibrate confidence -> return compact report
```

That is the core `ghx-sidecar` product behavior.

The cost result is equally important:

```text
The main agent did not need to spend its own context budget on the exploration loop.
```

The sidecar can burn cheap tokens on reconnaissance, false starts, narrowing, and self-audit, while the main agent receives only the compressed evidence artifact. This is a primary reason the architecture is worth considering.

The delegation result is also important:

```text
The main agent only needed English task intent, not ghx operational knowledge.
```

This reduces prompt and context burden. Instead of injecting `internal/skilldoc/SKILL.md`, command examples, search caveats, and exploration doctrine into every main-agent session, the system can put that doctrine inside the cheap specialized sidecar.

The distillation result is the user-facing artifact:

```text
The sidecar turns broad repo exploration into a compact evidence packet.
```

For the OpenAI Node case, the useful output was not the raw traversal. It was the final compressed map of verified streaming routes, implementation files, suspected Realtime surface, uncertainty, and next reads.

The backend-abstraction result is the future product shape:

```text
English repo question -> ghx sidecar -> remote ghx first -> optional Codemap/local escalation -> auditable evidence packet
```

Codemap is not a competitor in this model. It is a possible deeper backend behind the sidecar. The product boundary is that escalation must be visible: the report should say whether evidence came from remote API reads, maps, grep, Codemap, local index, clone, or another backend.

The failure mode is also clear:

```text
If the main agent or human must repeatedly ask audit follow-ups, the sidecar has failed its purpose.
```

Therefore the sidecar prompt and eventual harness must make self-audit mandatory before final output.

## Revised Test Strategy Before Architecture

The original plan required five broad test cases before architecture. The OpenAI Node run showed that one deep ambiguous investigation is more informative than several easy file-finding tasks.

The revised strategy is:

1. Keep the Hono test as the easy calibration case.
2. Use OpenAI Node streaming as the hard case.
3. Do not continue manual copy-paste testing unless it answers a new product question.
4. Move the next experiment into a thin harness so the sidecar can be tested as a delegated worker rather than as a human-operated chat.

The hard case should continue to test:

- Ambiguous repo questions
- Broad signal followed by narrowing
- Truncated output handling
- Verified versus inferred versus unverified claims
- Confidence calibration
- Memory reuse inside a named session
- Main-agent context savings
- Natural-language delegation without `ghx` doctrine in the main agent
- Distilled artifact instead of broad repo docs/source in the main agent
- Backend abstraction that can start remote and escalate to Codemap/local tools when justified
- Compact final reports useful to a main agent

## Experiment Protocol

For manual tests:

1. Start or reuse a sidecar session with the `ghx-sidecar` prompt.
2. Ask one focused repo question.
3. Save the full sidecar answer in `experiments/ghx-sidecar/SIDECAR_ANSWERS.md`.
4. Ask one follow-up when the case is meant to test memory.
5. Save the follow-up answer.
6. Score the case with the rubric in this ADR.
7. Compare against a direct main-agent exploration for at least 2 of the 5 cases.

The sidecar must not be manually coached during the test beyond the standard prompt, repo, question, budget, and backend constraints.

For the next phase, the protocol should change:

1. The main agent or human submits one high-level task.
2. The sidecar internally explores, narrows, self-audits, and calibrates confidence.
3. The sidecar returns one final report.
4. The evaluator checks whether the report needed external babysitting.

The product succeeds only if the sidecar owns the evidence-quality loop.

## Main-Agent Comparison

For at least 2 cases, ask the main agent the same repo question without the sidecar report.

Compare:

- Time to first relevant file
- Number of commands or tool calls
- Whether it over-read
- Whether it used unsupported GitHub search assumptions
- Whether it produced concrete evidence
- Whether it preserved uncertainty
- Amount of main-session context consumed

The sidecar is worth productizing only if it reduces main-agent context burden while preserving or improving evidence quality.

The comparison should count not only command count, but also where the token burn happens. A sidecar can be useful even if it performs several exploration steps, as long as those steps happen in a cheaper worker and the main agent receives a compact, auditable result.

It should also count doctrine isolation. If the main agent still needs to know when to use `ghx tree`, `ghx read --map`, `--grep`, `--lines`, search caveats, truncation handling, and backend escalation rules, then the sidecar has not earned its place. The main agent should ask in English and evaluate the returned evidence.

Finally, it should count repository-context compression. If the main agent still needs to read broad README sections, generated API files, large resource modules, or many candidate source files after delegation, the sidecar has not compressed enough. The sidecar should return the smallest artifact that preserves trust.

The long-term comparison should also count backend abstraction. If the main agent has to know when to use Codemap versus remote `ghx` versus a local clone, the sidecar has not fully absorbed the context-engineering burden. The sidecar should own that decision and expose the decision trace.

## Phase Gate

Do not build full protocol architecture until this ADR's POC gate passes.

Allowed before the gate passes:

- Improve the sidecar prompt
- Improve the report schema
- Add README guidance for Codex users running `ghx`
- Add a local `ghx doctor` or `ghx sidecar doctor` preflight if it directly reduces experiment friction
- Keep using manual Codex sidecar sessions
- Build a minimal local harness if it only removes manual copy-paste and tests the sidecar loop

Not allowed before the gate passes:

- Build a persistent sidecar daemon
- Build a `ghx` ACP adapter
- Build custom `acpx` orchestration
- Depend on Codex `app-server`
- Add Codemap auto-escalation
- Fine-tune a model

## Next Phase If Gate Passes

The OpenAI Node deep test is enough to justify MVP phase 2, but not enough to justify full product architecture.

MVP phase 2 should build the smallest repeatable harness:

- A canonical sidecar prompt
- A strict report schema
- A `doctor` preflight for token, network, `ghx` binary, sandbox, and memory path
- A scorecard file for test cases
- A lightweight way to preserve named session evidence memory
- A one-command way to ask a named sidecar a high-level repo question and capture the final report

Only after that should the project compare runtimes:

- Manual Codex sidecar
- Codex `app-server`
- Codex `mcp-server`
- `codex-acp` plus `acpx`
- Future native `ghx sidecar`

## Decision

Use ADR-0014.2 as the explicit gate between vision and architecture.

The project should stop expanding manual copy-paste experiments. The Hono and OpenAI Node runs show enough merit to continue, but the next test must be closer to the real product shape: one delegation, internal sidecar iteration, final auditable report.

Proceed to a minimal harness and canonical prompt/report schema. Do not build full sidecar infrastructure, ACP integration, app-server dependency, Codemap escalation, or model training yet.
