# 0017.1. Training-Data Exports Decision

## Status

Accepted as architecture; build opens with M9 (after the current
confirmatory re-run's verdict and the judge scorer's calibration, which
supplies trajectory-quality labels — ADR-0023.1 sequencing). Grounded in
ADR-0017 (research memo, 2026-07-05). Open-source-leverage tenet applies
throughout: official formats exactly, harness-neutral, nothing invented.

## Decisions

### D1. Canonical SFT export: TRL conversational JSONL

One episode turn → one record: `{"messages": [...], "tools": [...]}`
with `tool_calls` on assistant messages and `"role": "tool"`
observations — the shape TRL's SFTTrainer consumes natively and the
OpenAI fine-tuning JSONL is a mechanical transform away from
(`arguments` re-encoded as a JSON string). Captured thinking exports as
a `<think>…</think>` prefix in assistant `content` — the
Qwen3/DeepSeek-R1 convention, the strongest small-reasoning-model
families and therefore the most portable training path for
`TurnRecord.Thinking`. The persona/system prompt exports as the system
message exactly as the session ran it (ADR-0020.1 D2 makes it a single
stable string — a training bonus the eval design already paid for).

### D2. Exports are chat-template-agnostic; the template binds at train time

We store canonical messages, never pre-rendered templates. vLLM requires
training and serving to share one chat template, and the base-model
choice (Qwen/Llama/Hermes-class) is an M10 decision — so baking any
template into exports today would bake in a dead end (ADR-0017 Q5).
Rendering happens in the training pipeline, not the exporter.

### D3. Preference/reward ladder: KTO → DPO → GRPO

- **KTO first**: unpaired binary labels per episode — our gates and
  reward floor produce them for free. Lowest-friction preference export.
- **DPO pairs second**: the gate-run design already produces 5 trials
  per task×profile; same-task episode pairs ranked by (deterministic
  reward, then calibrated judge score per ADR-0023.1) become chosen/
  rejected pairs. Export blocked on judge calibration for the
  judge-ranked variant; reward-ranked pairs may ship earlier, labeled as
  such.
- **GRPO** (open-weight RL with our deterministic reward functions
  wrapped for the trainer) is the M10-era path; noted, not built.
- Step-level process rewards (per-turn PRM labels from ToolCallTrace):
  deferred until outcome-level training shows signal.

### D4. Quality filters (pre-registered, applied at export)

In order: anomaly exclusion (existing `ExclusionReasons` + breaking
anomalies), safety == 1.0 hard requirement, overall-reward floor 0.6
(tunable per export, recorded in the export manifest), dedup,
13-gram decontamination of training records against the eval task
corpus — **no eval task may leak into training data, or the benchmark
is dead** (ADR-0016.2 validity discipline extended to training). Every
export ships a manifest: source episodes, filters applied, counts
in/out, exporter version — recomputable like everything else.

### D5. Sources and consent

Eval episodes over public repos: exportable, no consent issue
(synthetic tasks, our own agent). Founder dogfood sessions under
`~/.ghx`: exportable with an explicit config opt-in
(`training.exportSessions: true`), never by default. Non-founder user
sessions: excluded until an explicit consent + opt-out mechanism exists
(pre-registered gate; not designed today). The existing 2048-byte
`OutputExcerpt` cap stays — it keeps third-party code in training
records at citation scale.

### D6. The converter is ours, thin, and Go

No existing tool converts our Episode JSON / OTel JSONL to training
JSONL (ADR-0017 Q4 — distilabel/LLaMA-Factory et al. start from
datasets, not agent traces). A small Go exporter under the evals
package (episodes in, JSONL + manifest out) is the minimum custom code;
it reads only committed artifacts, so it can be built and tested
entirely offline against the two existing gate-run directories.

## Considered and rejected

- **OpenAI RFT as the reward path** — cleanest grader mapping but locks
  training into OpenAI's stack; contradicts the open-weight P4 endgame.
  Revisit only if M10 targets a hosted fine-tune.
- **Anthropic fine-tuning** — no public API path (Bedrock Haiku only);
  not load-bearing for P4.
- **Pre-rendered chat templates in exports** — D2 rationale.
- **Training on raw session transcripts** (skip Episode structure) —
  loses the filter/label machinery and the compact tool summaries that
  make trajectories trainable; Episode JSON is the curated form.

## Sequencing

1. Confirmatory re-run verdict lands (episodes become candidate corpus).
2. Judge calibration (ADR-0023.1 D5) → quality labels.
3. Exporter build (delegable; offline; golden-file tests against
   committed gate-run artifacts).
4. First corpus cut + manifest committed under `docs/evals/` or an
   exports dir; M9 opens.

## Implementation Notes

2026-07-06 SFT slice (`sft-trl-conversational-v1`):

- Implemented the converter in `internal/sidecar/evals/training_export.go`
  and exposed it through hidden CLI
  `ghx sidecar evals export --format sft --run <dir> --out <file>`.
  This keeps the domain logic with the Episode schema and gives automation a
  stable binary entrypoint without making training export an end-user command.
- The exporter writes template-agnostic TRL conversational JSONL plus a
  sibling `<out>.manifest.json`. The manifest records source episodes,
  included record hashes, exporter version, filters, and exclusion counts.
  Its timestamp is frozen so repeated exports over unchanged artifacts are
  byte-identical.
- One emitted record represents one trainable turn. For turn `N`, the message
  sequence contains the reconstructed conversation through turn `N`, so
  multi-turn episodes produce multiple SFT records while preserving prior
  conversational context for follow-up turns.
- Prompt reconstruction uses the same code paths as the eval runner:
  direct profiles use `directPrompt`, and sidecar records use
  `sidecar.BuildPersonaSystemPrompt` as the system message plus
  `sidecar.BuildPrompt` as the user message. Tool calls are reconstructed from
  `TurnRecord.ToolTraces`; tool observations use the committed bounded
  `OutputExcerpt`.
- Filters implemented for this slice: `Invalid`, `ExclusionReasons`, plain
  profile ghx-use compliance invalidation, safety `< 1.0` or violations,
  overall reward `< 0.6`, breaking anomalies, `answer_doc_contamination`, and
  exact record dedup.
- Decontamination boundary: because this first requested corpus is itself
  made from eval episodes, literal 13-gram removal against the eval task
  prompts would exclude every record at the user-message layer. This slice
  therefore enforces the committed answer-document contamination guard and
  records the prompt-decontamination caveat in the manifest. A future export
  from dogfood/production sessions still needs full task-corpus n-gram
  decontamination before training.
