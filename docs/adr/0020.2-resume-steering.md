# 0020.2. Resume Steering

## Status

Accepted on merge. Pre-registers the fix for TRUST.md hole **H8**
("resumed turns run unsteered"), discovered by the ADR-0016.10 build and
logged in its D2 note as a separate measurement-conditions thread. This is
that thread.

## Problem

Every `RunTurn` spawns a fresh adapter process (`RunTurnWithOptions`,
`internal/sidecar/acp.go`), and the ACP `session/load` request carried no
`_meta.claudeCode.options` — only, since ADR-0016.10 D2, the raw-channel
audit flag in eval mode. The shipped adapter (claude-agent-acp@0.55.0)
builds its SDK session options from the request meta
(`loadSession` → `getOrCreateSession` forwards `params._meta` into
`createSession`, acp-agent.js:2647–2670; options spread at 2768–2801,
verified for ADR-0020.1/0016.10), so a resumed turn's session fell back to
adapter defaults for the entire ADR-0020.1 D2 steering surface:

- **persona system prompt** (`systemPrompt`) — turn 2+ ran without the
  sidecar doctrine at the system level;
- **isolation** (`settingSources: []`, `strictMcpConfig: true`) — the
  ADR-0016.3 isolation gap re-opened on resume: host settings inheritance
  came back;
- **tools allowlist** (`tools: ["Bash","Read"]`) and the submit_report
  auto-approve (`allowedTools`);
- **budgets** (`maxTurns`, `thinking`, `effort`) — including
  `thinking.display: "summarized"`, which is why resumed turns showed no
  thinking;
- **model pin** (`model`) — the ADR-0020.1 D4 wrong-model guard vanished
  on turn 2+.

Affected paths, all of which resume via LoadSession on a fresh (or
reconfigured) adapter:

1. turn 2+ of multi-turn eval episodes (`sidecar.Ask` per turn, evals
   runner);
2. production follow-up asks — both the daemonless path and the daemon
   worker (`daemon_worker.go configureSession`, whose two LoadSession
   calls carried **no meta at all**, not even the raw-audit flag);
3. the ADR-0027 D1 wrap-up recovery turn and the ADR-0021 D2 corrective
   retries (their `RunTurnOptions.SessionMeta` was forwarded only as the
   raw-audit subset).

## Decision

### D1. LoadSession carries the same session-options meta NewSession sends

One meta map, both concerns. `BuildSessionMeta`
(`internal/sidecar/session_options.go`) already builds a single
`_meta.claudeCode` bag holding the full steering options **and** (in eval
mode) the sibling `emitRawSDKMessages` audit flag. The fix forwards that
same map — `RunTurnOptions.SessionMeta`, built once per Ask — verbatim on
**both** `session/new` and `session/load`:

- `RunTurnWithOptions` (`acp.go`): `LoadSessionRequest.Meta =
  opts.SessionMeta` (was `RawSDKLoadSessionMeta(opts.SessionMeta)`).
- `AgentWorker.configureSession` (`daemon_worker.go`): both LoadSession
  paths (fresh-worker resume of a persisted ACP session ID; warm-worker
  reload for the report-sink refresh) gain `Meta: opts.SessionMeta`.
- NewSession behavior is byte-identical to before.

The raw-SDK audit meta from ADR-0016.10 is not clobbered: it was never a
separate map — `RawSDKLoadSessionMeta` merely *extracted* the audit flag
from the one `BuildSessionMeta` bag. Forwarding the whole bag is a strict
superset, so the audit channel keeps working exactly as registered and
`RawSDKLoadSessionMeta` is deleted as dead code (AGENTS.md engineering
tenets: no kept-but-unused shims).

Adapter-side safety, from the sources verified in ADR-0016.10 D2: the
session fingerprint excludes `_meta` (acp-agent.js:55–58), so carrying
options on load cannot fork the session; `getOrCreateSession` applies the
meta when it (re)creates the SDK session — precisely the fresh-process
resume case H8 is about.

### D2. Wrap-up and retry turns are covered by the same change

The ADR-0027 wrap-up recovery turn and the ADR-0021 corrective retries
already carry `SessionMeta` on their `RunTurnOptions` (added by
ADR-0016.10 for the audit flag). With D1 their LoadSession now forwards
the full steering — the recovery turn that salvages a capped exploration
runs under the same persona, allowlist, budgets, and model pin as the
turn it recovers.

### D3. Validity note — past verdicts stand, unrescored

Every committed multi-turn episode to date had turn 2+ **partially
unsteered**: system persona, tools allowlist, budgets, isolation, and
model pin were adapter defaults on resumed turns (the raw-audit flag was
restored by ADR-0016.10; everything else was not). Per the Visibility and
Truthfulness tenet:

- **Past verdicts are NOT rescored.** The artifacts honestly record what
  ran; the measurement stack that scored them is frozen history.
- **The effect direction is unknown.** Unsteered resumes could have made
  the subject look better (no turn cap, unrestricted tools) or worse (no
  persona doctrine, no thinking). No claim either way is made here; the
  delta gets measured by the next pre-registered run that includes
  multi-turn tasks under the fixed conditions.
- The same honest note lands in TRUST.md H8, which moves to
  fixed-with-commit while keeping the caveat about historical episodes.

Single-turn episodes (one NewSession, no resume) are unaffected: their
steering was always complete. Direct-profile eval episodes keep one live
session for all turns (ADR-0016.10 D2) and are likewise unaffected.

## Considered and rejected

- **A separate "steering subset" extractor for LoadSession** (symmetric
  to `RawSDKLoadSessionMeta`): pointless indirection — the NewSession bag
  is already exactly what a resumed session must re-assert. One map, sent
  twice.
- **Forwarding meta only in eval mode:** H8 explicitly covers production
  follow-up asks; a production resume without persona/isolation/allowlist
  is the same defect. Production LoadSession now carries the meta too.
- **Rescoring or annotating historical episodes:** rejected per D3 — the
  detector/scorer stack is frozen for committed runs, and there is no
  per-episode signal in old artifacts that could separate steered from
  unsteered turns retroactively without guessing.

## Implementation notes (2026-07-06, same day)

Implemented exactly as registered (commit `726db98`). Shape notes:

- `RunTurnWithOptions` LoadSession sends `Meta: opts.SessionMeta`; both
  `AgentWorker.configureSession` LoadSession paths send the same. NewSession
  code is untouched.
- `RawSDKLoadSessionMeta` and its unit test deleted; a breadcrumb comment in
  `rawsdk.go` points here.
- Test wire evidence: the mockagent now logs `NEW_META`/`LOAD_META` JSON
  (sorted keys, so byte-comparable). `acp_steering_test.go` pins
  NewSession == LoadSession meta byte-identical through two real ACP
  processes, with full field assertions (persona, tools `[Bash Read]`,
  `allowedTools` submit_report, maxTurns 24, thinking enabled/2048/
  summarized, effort medium, model pin, settingSources `[]`,
  strictMcpConfig, eval audit flag) plus a production-mode variant (no
  audit flag, options still present). `TestAskWrapsUpOnMaxTurns` asserts
  the wrap-up turn carries the identical SessionMeta;
  `TestMockSidecarEpisodeMaxTurnsWrapUp` asserts the wrap-up's
  `LOAD_META` on the wire contains systemPrompt/tools/audit-flag/maxTurns.
- Verification ran as planned: `go vet ./...` clean, `go test ./...`
  green, `-race` green on `internal/sidecar` and `internal/sidecar/evals`.
- **Live spot check (2026-07-06, fresh `dev` build, isolated
  `GHX_HOME=/tmp/ghx-h8-spot/home`, pinned adapter
  claude-agent-acp@0.55.0):** session `h8spot`, ask then daemon restart
  then follow-up ask on the same session — meta.json kept
  `acpSessionId f9022edb…` across both turns (genuine LoadSession
  resume) and the daemon log shows two distinct adapter node processes
  (60531, 60663), so turn 2 ran on a fresh adapter. Turn 2 steering
  evidence from the session artifacts: `sidecar.turn` span carries
  `gen_ai.usage.reasoning.output_tokens: 124` and logs.jsonl holds a
  `reasoning` output part — impossible under the adapter default
  `display: omitted`, which drops thought chunks before ACP; tool
  activity was Bash-executed `ghx` plus the auto-approved
  `submit_report` only; and the fresh adapter's startup stderr printed
  the `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` warning for
  `mcp__ghx-report-sink__submit_report` on the resumed session — the
  adapter echoing that it accepted the `allowedTools` option from the
  LoadSession meta.
