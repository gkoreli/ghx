# 0016.4. OTel Trace Emission Architecture for Eval Episodes

## Status

Proposed 2026-07-04. Deferred out of ADR-0016.3 because trace emission needs
its own architecture decision. Implementation is sequenced **after** the
ADR-0016.3 V0 slice lands (capture completeness first; the V0 worker was
explicitly scoped away from OTel).

## Context

ADR-0016 chose OpenTelemetry as the portable trace format; ADR-0016.1's
minimal kernel deferred it; ADR-0016.3 made episode-JSON capture complete so
no live token is wasted regardless of trace architecture. The remaining
question: how to emit and consume OTel traces, natively in Go, open source,
local-first, no service dependency.

Landscape facts (verified 2026-07-04):

- The official Go SDK `go.opentelemetry.io/otel` is the CNCF-governed,
  Apache-2.0, native-Go implementation — there is no credible alternative
  SDK for Go, and none is needed.
- OTel **GenAI semantic conventions** now define agent, workflow, tool, and
  model spans plus token-usage attributes (semconv ≥ 1.41). The ecosystem
  (LangChain, CrewAI, AutoGen; Datadog, Honeycomb, New Relic; Langfuse,
  Phoenix, LiteLLM) is converging on `gen_ai.*`. Caveat: the conventions
  carry **Development stability** — attribute names can change without a
  major version bump, so the semconv version must be pinned and recorded on
  every trace.
- OTel specifies an **OTLP JSON File format** (one top-level `TracesData`
  JSON object per line). Writing `traces.jsonl` in that format is therefore
  a spec-compliant open format, not a homegrown schema. The Go SDK ships no
  official file exporter, but a custom `sdktrace.SpanExporter` marshaling
  through the official OTLP protos (`go.opentelemetry.io/proto/otlp` +
  `protojson`) is ~100 lines and lossless.
- Open-source local viewers that accept OTLP and need no account: **Jaeger**
  (all-in-one, general-purpose), **Arize Phoenix** (LLM-native — renders
  gen_ai spans, prompts, tool calls, token usage; ELv2, free self-host),
  **otel-tui** (terminal UI, Go). All consume the same OTLP stream.

## Decision

1. **SDK**: use the official `go.opentelemetry.io/otel` SDK for in-process
   span emission during eval episodes. Spans: episode → turn → tool call,
   plus reward computation. This realizes ADR-0016's original span list.
2. **Naming**: adopt the GenAI semantic conventions — `gen_ai.*` attributes
   and the agent/tool/model span shapes — so ghx trajectories are readable
   by the LLM-observability ecosystem without translation. Pin the semconv
   version; record `otel.semconv_version` on the resource; expect renames
   while the conventions are in Development.
3. **Primary export**: a small custom `SpanExporter` writing the OTLP JSON
   File format to `<run-dir>/traces.jsonl`. The file is the durable,
   replayable artifact next to episode JSON (episode JSON remains the
   source of truth per ADR-0016; traces are the interoperable view).
4. **Secondary export**: honor the standard `OTEL_EXPORTER_OTLP_ENDPOINT`
   env (via `otlptracehttp`) so an engineer can stream the same spans live
   into Jaeger, Phoenix, or otel-tui while a run executes. Off by default;
   zero services required.
5. **Viewer guidance (docs, not deps)**: Phoenix for LLM-native inspection
   of gen_ai spans; Jaeger all-in-one for general trace debugging; otel-tui
   for terminal-only sessions. None is a dependency; `traces.jsonl` exists
   regardless.
6. **Dependency isolation**: OTel packages are imported only by the eval
   code (dev-only, `agent_e2e`-tagged paths and the `evalreport`-style
   cmds). The shipped `ghx` binary must not link OTel; `go.mod` grows, the
   product binary does not. Enforced by keeping imports out of
   `internal/ghx`, `internal/cli`, `internal/sidecar` production paths.
7. **No secrets in spans**: same rule as episode JSON; span attributes carry
   commands, sizes, timings, models — never tokens or credentials.

## Rejected alternatives

- **Hand-rolled OTLP JSON without the SDK**: avoids the dependency tree but
  reimplements span/trace-id semantics, sampling, and clock handling that
  the SDK already gets right; the dependency-weight argument evaporates once
  OTel is confined to dev-only eval code.
- **Offline exporter only (episodes → OTLP after the fact)**: still viable
  as a fallback and for back-converting pre-OTel episodes, but reconstructed
  spans lose live timing fidelity, and the in-process SDK path costs little
  once the version is pinned. Live emission plus the file exporter gives
  both real spans and the offline artifact.
- **OpenLLMetry / instrumentation frameworks**: Go support is immature and
  aimed at instrumenting LLM client libraries; ghx's episodes are already an
  explicit event stream — direct SDK spans are simpler and dependency-lighter.
- **Self-hosted trace platforms as a requirement (Langfuse, Uptrace)**:
  violates the local-first, no-service tenet; they remain optional OTLP
  destinations via (4).

## Consequences

- Every eval run yields `traces.jsonl` (OTLP JSON File format) alongside
  episode JSON — evaluable by open tooling, exportable to any OTLP backend,
  usable as training-data provenance.
- Development-stability semconv means occasional attribute renames; pinning
  plus the recorded semconv version keeps old traces interpretable.
- go.mod gains the OTel SDK tree (dev-only linkage); binary size and
  production dependency surface are unchanged.
- Implementation follows the ADR-0016.3 economics ladder: built and verified
  at V0 (mock episodes produce valid `traces.jsonl`; validated with a local
  viewer), no live tokens needed to prove it.
