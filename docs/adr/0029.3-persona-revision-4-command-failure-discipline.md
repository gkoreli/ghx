# 0029.3. Sidecar Persona Revision 4 — Failed-Command Discipline

## Status

Pre-registered before implementation; accepted on merge.

Like ADR-0029 and ADR-0029.1, this ADR is **pre-registered before the next
run; never mid-run**. Persona wording changes the subject under measurement,
so it may land only between runs, must never be introduced while a gate run
is in progress, and must never be used to rescore existing episodes. At
authoring time no gate run is in progress
(`internal/sidecar/evals/.ghx-evals/runs/` holds only the July runs; newest
run dir mtime 2026-07-04) and mainline sits at `cf925c5`.

This ADR does **not** change eval scoring, detectors, rewards, gates,
thresholds, episode definitions, or ground truth. It changes only sidecar
persona doctrine in `internal/sidecar/prompt.go` plus its pinning test.

This is the **persona half** of Research 007's F5 finding, deliberately split
from the code half. Research 007's ranked list assigns the F5 *code* surface
(validate the `owner/repo` slug at session/route time in
`internal/sidecar/route.go` + `session.go`) to the parallel A2-fixbatch task;
that wiring gap stays theirs. What remains for the persona is the agent
*behavior* the traces exposed — behavior that survives even after the code
fix, because ghx has many other teaching errors (`unknown depth`, bad glob
patterns, nonexistent paths) and the agent needs a general rule for how to
react to any of them.

## Context

Research 007 mined three production sessions under `~/.ghx/sessions/`. Two of
them (`badslugnoslash`, `badslugnoslash2`) were created with repo names that
are not `owner/repo`. ghx rejects such slugs instantly with a teaching error
(`internal/ghx/repo.go:28`: `invalid repo %q: expected owner/repo, e.g. ghx
explore gkoreli/ghx`) that names both the defect and the correct form. The
agent ignored it, at real cost:

- **~90 seconds of paid agent time** rediscovering what the first error line
  already stated (`badslugnoslash2/reports/1-*.json`, `2-*.json`: both turns
  BLOCKED; turn-2 answer repeats turn-1's diagnosis nearly verbatim).
- **Shell decoration as a retry strategy**: the turn-1 evidence ledger
  records `ghx explore badslugnoslash2` failing, then
  `ghx explore badslugnoslash2 2>&1 | head -40`, then
  `ghx inspect … ; echo "---"; ghx search … | head` — the same doomed
  commands re-run with pipes and separators as if output plumbing were the
  problem.
- **Cross-turn repetition**: turn 2 re-ran explore/inspect against the same
  invalid slug despite the session ledger already carrying turn-1's
  `invalid repo … expected owner/repo` entries.
- Both final reports' `uncertainty` quotes the identical `invalid repo`
  teaching error four times — proof the agent *had* the diagnosis and still
  spent the session acting around it.

The persona is silent on all of this. Its only failure-handling text governs
submit_report *validation* errors ("read it, fix exactly what it names") and
the ghx-*unavailable* BLOCKED path ("first run `ghx version`", ADR-0016.7
RC1). Nothing tells the agent what to do when a ghx command itself fails: the
natural LLM reflexes are exactly the observed ones — retry the same command,
decorate it with shell plumbing hoping for different output, and carry the
failed command set into the next turn.

The north-star filter: this removes paid-but-useless turns from sidecar
sessions (cheaper reconnaissance), shortens trajectories used as training
data (better training trajectories), and costs ~190 tokens of system-prompt
budget once instead of recurring per-session waste. It advances NORTH_STAR
B8 (persona proficiency revisions, each pre-registered).

## Decision

**D1 — Add a "When a ghx command fails" doctrine section to the persona**
(`BuildPersonaSystemPrompt`, placed directly after the existing "Failure
mode" section). Deliberately a separate section rather than a new
operating-loop step: it keeps all failure doctrine grouped (unavailability /
command failure / report-validation are three different failure classes),
avoids renumbering steps that ADR-0029.2 and downstream docs cite by number,
and is purely additive. Four rules:

1. **Read the error before reacting.** Most ghx failures are deterministic
   input errors whose message names the exact fix (canonical example: the
   `expected owner/repo` slug error from `internal/ghx/repo.go:28`). Fix the
   named cause in one corrected command — never re-run the identical failed
   command unchanged.
2. **No shell-decoration retries.** Re-running a failing command through
   `2>&1 | head`, pipes, redirects, or separators does not change a rejected
   input; decorations change how output is displayed, not whether the input
   is valid.
3. **One corrected attempt, then change approach.** If the corrected command
   fails again with the same error, stop retrying: record every command
   tried and the exact errors in uncertainty, then either gather the
   evidence another way or submit BLOCKED stating why. Do not probe around
   a deterministic failure.
4. **Failures persist across turns via the evidence ledger.** Never re-run,
   in a later turn, a command whose failure is already recorded there —
   cite the recorded error instead.

The section ties back to the existing BLOCKED contract (ADR-0016.7) without
redefining it: a failure that blocks the entire ask exits honestly as
BLOCKED with the captured error, consistent with ADR-0034.1's
never-reconstruct-exit-codes rule.

Exact persona bytes added (rendered; inserted immediately after the
"Failure mode" section's `uncertainty:` example line and before `return`):

```text
## When a ghx command fails

Most ghx failures are deterministic input errors whose message names the
fix (e.g. invalid repo "name": expected owner/repo). When a ghx command
fails:
1. Read the error before reacting. Fix the named cause in one corrected
   command. Never re-run the identical failed command unchanged.
2. Never retry a failing command through shell decorations (2>&1 | head,
   pipes, redirects, command separators). They change how output is
   displayed, not whether the input is valid.
3. If the corrected command fails with the same error, stop: record every
   command tried and the exact errors in uncertainty, then either gather
   the evidence another way or submit BLOCKED stating why. Do not probe
   around a deterministic failure.
4. Failures persist across turns via the evidence ledger: never re-run,
   in a later turn, a command whose failure is already recorded there —
   cite the recorded error instead.
```

Nothing else in the persona changes (ADR-0029 non-goal: no broad prompt
rewrite). Like ADR-0029.2 D1 this is deliberately doctrine-level, not
runtime enforcement; once the A2 fixbatch's route-time slug validation
lands, most invalid-slug sessions die at spawn and this section governs the
remaining deterministic-failure classes.

**D2 — Golden persona hash updated deliberately in the same commit**, per
the ADR-0029 family pattern (0029.1/0029.2 precedent): the new SHA replaces
the old constant in `TestRepoScopedPersonaByteStable`, and the comment above
it names this ADR as the reason. The discovery persona inherits the change
automatically (`BuildDiscoveryPersonaSystemPrompt` = base + discovery
doctrine); its extension test pins prefix equality, not bytes, so no second
hash update is needed.

**D3 — Contract-test additions in `prompt_test.go`**: the persona contract
test gains assertions for each D1 rule's anchor phrase, mirroring how
ADR-0029.1 pinned inspect-first wording and ADR-0029.2 pinned tier-2 /
citation wording.

## Alternatives considered

- **Code-only fix (validate slugs at route time) without persona work** —
  necessary but insufficient: it closes only the invalid-slug entry point.
  The behavioral waste generalizes to every teaching error ghx can emit.
  Rejected as the whole fix; owned by A2-fixbatch as the complementary half.
- **Operating-loop step insertion with renumbering** (new step 7, tier-2 → 8,
  honesty → 9). Rejected: renumbers doctrine that ADR-0029.2 and its test
  assertions reference, for no behavioral gain over a grouped failure section.
- **Per-error cookbook in the persona** (enumerate known teaching errors and
  their fixes) — rejected: duplicates `internal/ghx` knowledge in prose, rots
  as messages evolve, and blows the persona's token budget. The general
  read-the-error rule subsumes the cases.
- **Hard stop after first failure** (never retry anything) — rejected:
  transient network failures legitimately warrant one corrected attempt, and
  forbidding retries outright would trade wasted turns for false BLOCKED
  reports. Rule 1 preserves that distinction: the *corrected* command is the
  one allowed attempt.
- **Runtime rejection of decorated retries** (parse `commandsRun` for
  `2>&1 |` patterns and warn). Rejected for this revision: it belongs to the
  A2 fixbatch's code-side surface (report-sink validation family), needs its
  own false-positive analysis, and persona-first keeps this slice
  measurement-clean. May be pre-registered later if spot checks show the
  doctrine alone is insufficient.
- **Extending the Failure-mode section instead of adding one.** Rejected:
  that section owns the ghx-unavailable BLOCKED path (ADR-0016.7);
  overloading it would blur two different failure classes.

## Consequences

- The stable persona grows by ~190 tokens; the per-turn prompt is untouched
  (persona lives in the session-level system prompt, ADR-0020.1 D1), so
  cache-stability and the SPT relief goal are unaffected beyond the one-time
  size delta.
- Trajectories produced after this landing should show fewer duplicate
  command entries in session ledgers; that is observable in the next
  dogfood/mining pass but is **not** claimed as a measured result here.
- No historical episode may be rescored against the new persona;
  comparisons across the boundary are between-persona observations only.

## Eval-measurement rule

- These persona changes are pre-registered here **before the next run** and
  must never land or change **mid-run**. At authoring time no gate run is in
  progress (checked via run-dir listing and process table) and mainline sits
  at `cf925c5`.
- After merge, verification follows the ADR-0029.2 spot-check rule: a
  sidecar-only live spot check (≤1 episode, e.g. an ask scoped to a
  deliberately malformed repo name) checked for whether the trail shows the
  new doctrine (one corrected attempt at most, no decorated retries, BLOCKED
  with the captured error). A negative finding is committed as such, not
  retried until it looks good. Budget permitting only; otherwise this ships
  honestly unmeasured.
- No existing episodes are rescored.
