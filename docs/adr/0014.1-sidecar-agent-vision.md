# 0014.1. `ghx` Sidecar Agent Vision

## Distilled View

`ghx` should become two things with a clean boundary:

1. **Evidence engine**: the CLI exposes transparent, composable GitHub exploration primitives: `explore`, `tree`, `read`, `read --map`, `read --grep`, `search`, and `code`.
2. **Reconnaissance sidecar**: a cheap specialized agent knows how to use those primitives, optionally escalates to deeper backends such as Codemap, and returns compact, auditable evidence to the main agent.

The sidecar is not a one-shot subprocess. It should be a persistent, addressable specialist with evidence-shaped memory. A follow-up question should not restart exploration from zero. The sidecar should remember which repo, commit, paths, globs, grep patterns, files, backends, false leads, and uncertainties have already been investigated.

The main coding agent should not need to know the `ghx` command grammar, GitHub search limitations, map-level semantics, parser fallback behavior, or exploration doctrine. It should delegate a repo question to the `ghx` sidecar and receive a report that preserves full visibility:

```text
question
answer
relevant files
evidence snippets
commands run
backends used
uncertainty
suggested next reads
```

The sidecar handles procedure. The main agent handles judgment.

## Problem Space

### The current agent burden

Direct `ghx` usage is powerful, but it asks every main agent to learn a lot:

- When to use `explore` versus `tree`
- When to map before reading
- How to narrow globs before reading too much
- How `--map`, `--kind`, `--level`, `--grep`, and `--lines` compose
- Why GitHub's public code search differs from GitHub.com
- Why `symbol:`, regex, `OR`, and `NOT` are unsafe through the legacy public code-search API
- When remote evidence is enough
- When to escalate to local indexing, Codemap, or a full clone

That knowledge is real context overhead. It also does not belong in every coding session.

### The specialization opportunity

GitHub exploration is repetitive:

```text
understand question
normalize repo or URL
explore repo
inspect tree
map candidate files
grep bounded paths
read snippets
preserve evidence
state uncertainty
stop before over-reading
```

A smaller specialized model with the `ghx` skill and a constrained toolset can do this more cheaply and more consistently than a general coding model. The advantage is not only cost. It is operational specialization.

### The memory opportunity

Repo reconnaissance is not naturally one-shot. It is conversational:

```text
Where is middleware composition?
Now trace error propagation through that path.
Which files should the main agent read next?
Did we already inspect tests?
Do we need Codemap yet?
```

A sidecar with no persistent session repeats work and loses the value of previous observations. A sidecar with memory becomes a reusable working notebook for a repo/task. The memory must be evidence-shaped, not vibes-shaped: paths inspected, commands run, symbols found, snippets read, false leads rejected, backend state, and open uncertainty.

### The blackbox risk

The sidecar must not become an opaque "repo analyst" that hides its reasoning. That would recreate the same trust problem as bad agent summaries: plausible output with no audit trail.

The correct design is not:

```text
main agent -> ghx sidecar -> "Read these files because they matter"
```

The correct design is:

```text
main agent -> ghx sidecar -> answer + observations + commands + backend trace + limits
```

`ghx` should remove the cost of looking. It should not remove the need for reasoning.

## Evidence

### Existing `ghx` evidence

- ADR-0002 established the original gap: agents need efficient GitHub repository access without MCP schema overhead, clone-first workflows, or raw `gh` call chains.
- ADR-0010 established codemode: one local program can compose multiple `ghx` operations in a single round-trip.
- ADR-0013 established parser-backed mapping as the durable path: fetch through documented GitHub APIs, parse locally, render compact structural maps, and avoid unsupported GitHub.com internals.
- ADR-0014 established demand vocabulary from Search Console: Codemap, code search engine, search syntax, `repo:`, `path:`, `symbol:`, regex, and GitHub URL import.
- `README.md` and `internal/skilldoc/SKILL.md` already show the burden: to use `ghx` well, an agent must understand command selection, map-before-read discipline, search gotchas, and codemode composition.
- The `ghx` output model is already evidence-oriented: tree entries, maps, grep hits, line ranges, matching context, parser engine selection, and explicit search gotchas. That makes it a good substrate for durable evidence memory.

### Industry evidence

The surrounding tool ecosystem has clear boundaries:

| Tool or protocol | What it optimizes for | Why it matters for this ADR |
|------------------|-----------------------|-----------------------------|
| GitHub MCP | Broad GitHub tool access through MCP | Rich but heavy for "inspect this repo" tasks; broad schemas are not specialization |
| `gh` CLI | General GitHub command-line access | Powerful but low-level; agents must remember API paths, headers, quoting behavior, and search limitations |
| Codemap | Deep local structural mapping, references, call graphs | Strong backend candidate after remote reconnaissance proves local indexing is warranted |
| Aider repo map | Context selection inside an active Aider coding session | Shows that maps are most useful when tied to a workflow, not as neutral dumps |
| Gitingest | Prompt-friendly repo digest | Useful when the desired artifact is a full digest, but premature when the agent is still deciding what matters |
| Repomix | Full-featured repo packing and compression | Strong packer, different cost model; best after the user chooses to send broad context |
| `ghx` CLI | Remote GitHub evidence without cloning | Best primitive substrate for pre-clone reconnaissance |
| `ghx code` | Local orchestration of multiple `ghx` operations | Useful execution backend for the sidecar's repeatable exploration plans |
| ACP | Standardized editor-agent interoperability | Natural interface for "any main agent or editor can delegate to the ghx sidecar" |
| `codex-acp` | ACP adapter around Codex CLI | Lets existing ACP clients run Codex as the sidecar agent without `ghx` building an adapter |
| `acpx` | Headless ACP client and session manager | Lets agents or scripts talk to ACP agents with persistent named sessions instead of scraping PTYs |
| Codex `mcp-server` | Exposes Codex through stdio MCP | Possible integration point when the main harness already speaks MCP, but MCP is primarily a tool protocol |
| Codex `app-server` | Experimental Codex-native app protocol over stdio, Unix socket, or WebSocket | Richest native Codex sidecar surface: threads, turns, steering, approvals, tool calls, skills, plugins, and streaming notifications |
| MCP | Tool protocol for exposing commands to agents | Useful for direct tool access, but not sufficient by itself for specialized delegated work |

ACP is especially relevant because it separates the editor/client from the agent implementation. ACP-compatible clients can talk to ACP-compatible agents over a standard protocol, similar in spirit to how LSP separated editors from language servers. A `ghx` sidecar exposed through ACP can become an interchangeable GitHub reconnaissance worker for Claude, Codex, Kiro, Zed, JetBrains, or any other compatible client.

### ACP component roles

`codex-acp` and `acpx` are not competing tools. They sit on opposite sides of the ACP connection.

| Component | Role | Layer |
|-----------|------|-------|
| `codex-acp` | Exposes Codex as an ACP-compatible agent | Agent adapter |
| `acpx` | Talks to ACP agents from the command line, manages sessions, queues prompts, and supports named parallel workstreams | Headless client/orchestrator |
| `ghx` | Provides the GitHub evidence commands the sidecar uses | Tool substrate |
| `ghx-sidecar` | The specialized agent persona/instructions that run inside Codex or another ACP agent | Reconnaissance harness |

The experiment stack should therefore be:

```text
main agent or human
  -> acpx as the headless ACP client
    -> codex-acp as the Codex ACP adapter
      -> Codex sidecar session with ghx-sidecar instructions
        -> ghx CLI evidence commands
```

This matters because `ghx` should not build protocol infrastructure before validating the sidecar behavior. Existing ACP infrastructure can host the experiment.

### Codex-native server surfaces

Codex also exposes native server modes that may reduce the need for ACP in Codex-only experiments:

| Codex surface | Local command | What it gives | Fit for `ghx-sidecar` |
|---------------|---------------|---------------|-----------------------|
| Non-interactive execution | `codex exec` | One turn with optional JSON output and schema | Good for smoke tests, bad for a persistent sidecar |
| MCP server | `codex mcp-server` | Codex exposed over stdio MCP | Useful if the parent harness only knows MCP, but less obviously a durable agent-session API |
| App server | `codex app-server` | Experimental JSON-RPC app protocol over `stdio://`, `unix://`, or `ws://`; generated schema includes `thread/start`, `thread/resume`, `turn/start`, `turn/steer`, `thread/list`, `thread/read`, approvals, MCP tool calls, skills, plugins, shell commands, and streaming notifications | Strongest Codex-native sidecar candidate if we are willing to depend on a Codex-specific experimental protocol |
| ACP adapter | `codex-acp` | Codex exposed as a standard ACP agent | Best when interoperability with ACP clients matters |
| Headless ACP client | `acpx` | Persistent named sessions, prompt queueing, cancellation, structured output against ACP agents | Best when a main agent or script needs to manage sidecar sessions without building protocol code |

The conclusion is not that one surface replaces all others. The distinction is:

- Use `codex exec` for one-shot smoke tests.
- Use `codex app-server` for a Codex-native sidecar runtime if Codex-only is acceptable.
- Use `codex-acp` plus `acpx` when interoperability and reusable ACP session management matter.
- Use `codex mcp-server` only if the parent environment is already MCP-native and the sidecar can be modeled cleanly as an MCP-exposed agent.

### MVP runtime lesson: sidecars need explicit environment contracts

The first manual Codex sidecar experiment exposed a practical issue that is directly relevant to the product design: a sidecar agent is not only a prompt. It is a runtime with tool access, network policy, credentials, sandboxing, and session state.

This is not a `ghx` product failure. `ghx` is a normal CLI. The failure was that Codex shell commands did not initially behave like the user's unconstrained interactive terminal. For `ghx` to work inside a Codex sidecar, two things must be true:

1. A GitHub token must be visible to the shell process.
2. The shell sandbox must be allowed to resolve and reach `api.github.com`.

Observed failure modes during the MVP:

| Symptom inside Codex | Meaning | Fix |
|----------------------|---------|-----|
| `failed to create GraphQL client: authentication token not found for host github.com` | `ghx` cannot find a usable token through `GH_TOKEN`, `GITHUB_TOKEN`, or `gh` auth config | Provide `GH_TOKEN`/`GITHUB_TOKEN` to Codex shell commands |
| `gh auth status` says the saved account token is invalid, while a normal terminal says `(keyring)` login is valid | Codex shell cannot access the macOS Keychain-backed `gh` credential in the same way the interactive terminal can | Derive `GH_TOKEN` from `gh auth token` before launching or through a repo-local `.envrc` |
| `GH_TOKEN is present but ghx fails with lookup api.github.com: no such host` | Auth is fixed, but Codex shell network/DNS is blocked by sandbox policy | Enable network access for `workspace-write` sandbox |

The resolved local setup for Codex users is:

```toml
# ~/.codex/config.toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[shell_environment_policy]
inherit = "all"
ignore_default_excludes = true

[sandbox_workspace_write]
network_access = true
```

And a repo-local token bridge:

```bash
# .envrc
if command -v gh >/dev/null 2>&1; then
  export GH_TOKEN="$(gh auth token 2>/dev/null || true)"
  if [ -n "${GH_TOKEN:-}" ]; then
    export GITHUB_TOKEN="$GH_TOKEN"
  else
    unset GH_TOKEN GITHUB_TOKEN
  fi
fi
```

Run once per `.envrc` content change:

```bash
direnv allow
```

Validation inside Codex:

```bash
printenv GH_TOKEN >/dev/null && echo token-present
curl -I https://api.github.com
ghx explore honojs/hono
```

This should become README guidance for Codex users. The important product lesson is broader than Codex: every sidecar runtime must declare its environment contract up front. A `ghx` sidecar needs:

- A GitHub token source
- Network access to GitHub APIs
- A known `ghx` binary on `PATH`
- A sandbox policy compatible with read-only remote reconnaissance
- A session identity and evidence-memory location

The sidecar should validate these requirements at startup and report environment failures as runtime diagnostics, not as confusing exploration failures.

### Persistent evidence memory

The persistent sidecar session should maintain a compact evidence notebook. This is product behavior, not only implementation state.

Example session state:

```yaml
session: ghx-hono-middleware
repo: honojs/hono
commit: default-branch-head-at-first-inspection
scope: middleware composition
backends:
  remote: true
  codemap: false
inspected_paths:
  - src/compose.ts
  - src/hono-base.ts
mapped_globs:
  - "src/**/*.ts"
grep_patterns:
  - "compose"
  - "middleware"
  - "dispatch"
relevant_files:
  - src/compose.ts
  - src/hono-base.ts
rejected_paths:
  - examples/
  - test/
open_questions:
  - how errors propagate through compose()
commands_run:
  - ghx tree honojs/hono src --depth 3
  - ghx read honojs/hono "src/**/*.ts" --map --kind func
  - ghx read honojs/hono --grep "compose|middleware|dispatch" "src/**/*.ts"
```

The sidecar may summarize this memory for the main agent, but it should preserve enough trace to answer follow-ups without rediscovering the same facts.

## Insights

- The future product is not "teach every agent `ghx`." The stronger product is "teach one cheap specialized `ghx` agent GitHub exploration extremely well, then let every main agent delegate to it."
- The CLI should remain transparent, boring, and composable. The sidecar can be opinionated because the evidence trace is visible.
- The sidecar's unit of work is not "summarize this repo." It is "answer this repo question with bounded evidence."
- Codemap is not a competitor to avoid. It is a possible backend to invoke when local structural indexing is the right instrument.
- The main agent should not spend context learning operational mechanics that can live in a specialized worker.
- Model cost matters, but specialization matters more. A small model with the right harness can beat a larger general model on a narrow, repetitive exploration protocol.
- Full visibility means showing commands, snippets, files inspected, backend choice, snapshot identity, and uncertainty. It does not mean dumping every token of intermediate output into the main context.
- The sidecar should know when to stop. Its output should make the next read obvious without doing implementation work itself.
- Persistence is part of the product contract, not only a runtime convenience.
- Sidecar memory must be evidence-shaped, not vibes-shaped.
- Named sidecar sessions let the main agent address specialist workstreams directly: `ghx-sidecar:hono-middleware`, `ghx-sidecar:openai-streaming`, `ghx-sidecar:ghx-map`.
- The MVP setup pain clarified a missing requirement: the sidecar runtime must have a preflight check for auth, network, `ghx` availability, and memory/session location before it accepts exploration work.

## Rationale

### Why not just improve the CLI?

Improving the CLI helps humans and direct agent users, but it does not solve the main-agent context problem. The better the CLI becomes, the more doctrine exists around using it correctly.

The direct-agent mode still requires instruction:

```text
Use map before read.
Avoid web-only search qualifiers.
Prefer bounded grep.
Use codemode for multi-step workflows.
Escalate to clone only after evidence says so.
```

That belongs in a specialized worker.

### Why not hide everything behind the sidecar?

Because hidden repo analysis is not trustworthy. The sidecar should produce conclusions, but every conclusion should be backed by evidence the main agent can inspect.

The sidecar should return:

- The exact files it considered relevant
- The command trace or equivalent backend operations
- The snippets or symbols that support the answer
- The backend used for each claim
- The limits of the investigation

This keeps the system auditable.

### Why allow Codemap under the hood?

Because "you don't always need Codemap" does not mean "never use Codemap." It means Codemap should be used when the question requires local structural indexing.

`ghx` can start remote and escalate:

```text
Tier 0: remote facts
Tier 1: remote maps and bounded grep
Tier 2: temporary local snapshot plus Codemap
Tier 3: hand off to main agent for full clone or implementation work
```

If Codemap is used, the report must say so.

### Why ACP?

ACP is the right shape for interoperability. The goal is not a `ghx` integration for one IDE or one agent. The goal is a delegated GitHub exploration worker that can be used from many agent clients.

The main agent should need one capability:

```text
delegate a GitHub repo question to ghx
```

The `ghx` sidecar owns the rest.

### Why persistent named sessions?

Because the value of a specialist grows across turns. A persistent session can carry:

- Repo identity and resolved default branch or commit
- Paths already explored
- Globs already mapped
- Grep patterns already tried
- Files already read
- Evidence already accepted
- False leads already rejected
- Backend state such as remote-only versus Codemap-indexed
- Open uncertainty and next investigation threads

That lets the main agent ask follow-ups without forcing the sidecar to restart:

```text
Ask ghx-sidecar:hono-middleware to trace error propagation now.
Ask ghx-sidecar:openai-streaming whether the streaming API is exposed in the public client.
```

This is the "memory type beat" version of the product: not chat memory as vibes, but a durable evidence notebook operated by a cheap specialist.

## Vision Bullets

- `ghx` becomes the transparent GitHub evidence engine for agents.
- `ghx-sidecar` becomes the cheap specialized reconnaissance agent that knows how to use `ghx`.
- ACP becomes the preferred interoperability layer for clients that want to delegate GitHub exploration without learning `ghx`.
- MCP remains useful for direct tool exposure, but not the only integration story.
- Codemode becomes the sidecar's local orchestration substrate for multi-step exploration.
- Codemap becomes an optional escalation backend, not a default dependency and not hidden magic.
- Existing ACP infrastructure should be reused before `ghx` builds its own agent adapter.
- `codex-acp` can host the first Codex-based sidecar; `acpx` can manage durable named sidecar sessions.
- Codex-native server modes should be evaluated before building `ghx` orchestration: `app-server` may be enough for Codex-only sidecars, while ACP remains better for cross-agent interoperability.
- Persistent named sessions are core to the sidecar model.
- Sidecar memory should track evidence state: commands, inspected paths, mapped globs, snippets, relevant files, rejected paths, backend state, and open questions.
- Runtime preflight is part of the sidecar contract: token source, network access, `ghx` binary, sandbox mode, and memory path must be explicit.
- Reports are compact, structured, and auditable by default.
- Every backend escalation is visible.
- Every answer includes uncertainty.
- The sidecar stops at reconnaissance and hands back evidence; it does not become the coding agent.

## Proposed Shape

### CLI layers

```text
Layer 1: Evidence primitives
explore, tree, read, search, repos

Layer 2: Structural evidence
read --map, future map, read --grep, read --lines

Layer 3: Local orchestration
code

Layer 4: Delegated reconnaissance
delegate, sidecar

Layer 5: Protocol adapters
Codex app-server, ACP via existing adapters, MCP
```

The existing source-of-truth rule from ADR-0010 should remain: core capabilities live in `internal/ghx`; frontends wrap the same core.

### Sidecar contract

Input:

```json
{
  "session": "ghx-plugin-loading",
  "repo": "owner/repo",
  "question": "Where is plugin loading implemented?",
  "budget": "cheap",
  "backend": "auto",
  "visibility": "evidence"
}
```

Output:

```text
Question:
Where is plugin loading implemented?

Answer:
Plugin loading is likely centered in src/plugins/loader.ts and src/runtime/plugin-host.ts.

Relevant files:
- src/plugins/loader.ts
- src/runtime/plugin-host.ts
- src/config/plugins.ts

Evidence:
- src/plugins/loader.ts defines loadPlugin, resolvePlugin, and normalizePluginConfig.
- src/runtime/plugin-host.ts imports loadPlugin and invokes it during runtime initialization.
- src/config/plugins.ts defines the plugin config shape consumed by normalizePluginConfig.

Commands run:
- ghx tree owner/repo src --depth 3
- ghx read owner/repo "src/**/*.ts" --map --kind func,type
- ghx read owner/repo --grep "loadPlugin|plugin" "src/**/*.ts"
- ghx read owner/repo src/plugins/loader.ts --lines 1-180

Backends used:
- ghx remote tree
- ghx remote map
- ghx remote grep
- ghx remote read

Uncertainty:
- Did not run code.
- Did not inspect tests.
- Did not build a complete reference graph.

Suggested next reads:
- ghx read owner/repo src/plugins/loader.ts
- ghx read owner/repo src/runtime/plugin-host.ts --lines 1-220
```

### Session contract

Each sidecar session should have a stable name and scope:

```text
ghx-sidecar:<repo-or-topic>
```

Examples:

```text
ghx-sidecar:hono-middleware
ghx-sidecar:openai-node-streaming
ghx-sidecar:ghx-map-engine
```

Session memory should include:

| Memory field | Purpose |
|--------------|---------|
| `repo` | The GitHub repo under investigation |
| `commit` | The snapshot or default-branch head used for evidence |
| `scope` | The question family the session is exploring |
| `commands_run` | Audit trail and duplicate-work prevention |
| `inspected_paths` | Paths already examined |
| `mapped_globs` | Structural scans already performed |
| `grep_patterns` | Search attempts and query vocabulary already used |
| `relevant_files` | Files the sidecar believes matter, with evidence |
| `rejected_paths` | Paths ruled out, with reason |
| `backends` | Whether evidence came from remote `ghx`, Codemap, clone, or another backend |
| `open_questions` | Follow-up uncertainty carried across turns |

The memory is not a hidden chain-of-thought store. It is an evidence ledger.

### Backend modes

| Mode | Behavior | Use when |
|------|----------|----------|
| `remote` | GitHub API plus `ghx` primitives only | The question can be answered by tree, map, grep, and snippets |
| `codemap` | Fetch a local snapshot and run Codemap-backed structural analysis | The question requires references, call relationships, or deeper local indexing |
| `auto` | Start remote, escalate only when required | Default mode for delegated exploration |
| `plan` | Return proposed commands without executing expensive escalation | The user wants approval before clone/index work |

### Visibility levels

| Level | Output | Use when |
|-------|--------|----------|
| `brief` | Answer, relevant files, uncertainty | Human wants a quick lead |
| `evidence` | Answer, files, snippets, commands, backends, uncertainty | Default |
| `full` | Evidence plus expanded command outputs and artifacts | Debugging or high-stakes investigation |

### Example delegated flows

Auth investigation:

```text
main agent asks:
Find where authentication sessions are created and invalidated in owner/repo.

sidecar path:
remote tree -> map src auth/session/security paths -> grep session/auth/login/logout -> read snippets

possible escalation:
Codemap only if remote grep/map cannot establish references between handlers and session functions.
```

Library evaluation:

```text
main agent asks:
Does this library support streaming responses?

sidecar path:
explore -> inspect README/package manifests -> grep stream/readable/iterator -> map candidate files -> read only matching API surface

output:
yes/no/unclear, files that expose the API, evidence snippets, uncertainty about runtime behavior.
```

Dependency audit:

```text
main agent asks:
Where does this package call OpenAI APIs?

sidecar path:
tree -> grep openai/client/responses/chat/completions -> read snippets -> map files containing API wrapper symbols

output:
API wrapper files, direct call sites, config/env files, and whether usage is first-party or adapter-based.
```

## Decision

Pursue `ghx` as a layered product:

1. Keep the CLI as the transparent evidence engine.
2. Add a sidecar agent harness for delegated GitHub reconnaissance.
3. Reuse existing runtime infrastructure first: manual Codex session, Codex `app-server`, Codex `mcp-server`, `codex-acp`, or `acpx`, depending on the harness being tested.
4. Keep MCP as a direct tool interface, not the whole product story.
5. Allow optional backend escalation to Codemap with full visibility.
6. Make persistent named sessions part of the product contract.
7. Make report evidence, command trace, backend trace, memory state, and uncertainty part of the output contract.
8. Make runtime preflight part of the sidecar contract so auth, network, binary availability, sandbox policy, and memory location fail clearly before exploration begins.

## Non-Goals

- Do not turn `ghx` into a full coding agent.
- Do not hide Codemap or clone/index work behind silent automation.
- Do not make repo-wide summaries the default output.
- Do not replace Codemap, Aider, Repomix, Gitingest, or GitHub MCP in their natural domains.
- Do not optimize for SEO-driven feature parity with search terms.
- Do not make the main agent depend on knowing `ghx` command internals.

## Consequences

### Positive

- Main agents spend less context on tool doctrine.
- A cheap specialized model can perform repetitive GitHub exploration consistently.
- `ghx` keeps its transparent CLI foundation while gaining a higher-level delegated mode.
- ACP gives the project a route to many clients without bespoke integrations.
- `codex-acp` and `acpx` let the project validate the sidecar idea before building protocol infrastructure.
- Codex `app-server` may provide a richer native sidecar runtime than ACP for Codex-only deployments.
- Codex `mcp-server` may make sidecar delegation available to MCP-native parent agents without ACP.
- Persistent memory lets the sidecar answer follow-ups without repeating tree/map/grep work.
- Evidence-shaped memory improves auditability because the sidecar can show what it already knows and why.
- Runtime preflight turns frustrating environment problems into actionable diagnostics.
- Codemap can be used where it is strongest without confusing the `ghx` product boundary.

### Negative

- A sidecar introduces another runtime surface: model configuration, session handling, protocol adapter, and report schema.
- Codex `app-server` is experimental and Codex-specific, so building on it too early could reduce portability.
- Persistent memory introduces lifecycle questions: naming, expiration, compaction, stale commit detection, privacy, and cleanup.
- "Auto" backend escalation can become surprising if cost and visibility are not strict.
- A weak sidecar prompt could produce blackbox summaries unless the evidence contract is enforced.
- Runtime setup can distract from product value unless the sidecar gives sharp diagnostics and README guidance.

### Neutral

- This does not require immediate model fine-tuning. Start with a harness, fixed instructions, cheap model, strict tools, and a report schema.
- The CLI remains valuable even if the sidecar never ships.
- The sidecar can be local-only first; remote hosted execution is a separate decision.

## Build Path

1. Define the sidecar report schema in docs before implementation.
2. Define the evidence-memory schema: repo, commit, scope, inspected paths, mapped globs, grep patterns, relevant files, rejected paths, commands, backends, open questions.
3. Define runtime preflight: `ghx` binary, GitHub token visibility, GitHub API network access, sandbox mode, and session-memory location.
4. Document the resolved Codex local setup in README: `~/.codex/config.toml`, optional `.envrc`, `direnv allow`, and validation commands.
5. Run the first experiment manually by pasting the sidecar definition into a second Codex session, then ask at least one follow-up that depends on memory.
6. Test Codex-native persistence through `codex app-server`: start a thread, inject the sidecar definition, run multiple repo questions, and inspect turn/thread behavior.
7. Test MCP-native delegation through `codex mcp-server` only if the parent harness can treat the MCP server as an agent sidecar rather than only a tool provider.
8. Test ACP infrastructure with `acpx` as client/session manager and `codex-acp` as the Codex adapter, specifically validating named sessions and parallel sidecars.
9. Compare the three runtime paths: manual, Codex-native app-server/MCP, and ACP.
10. Add evidence trace capture expectations: commands, outputs summarized, files inspected, snippets selected, limits.
11. Only after repeatable success, add a `ghx delegate --plan` prototype that returns planned `ghx` commands for a repo question.
12. Add `ghx delegate --execute --backend remote` using a configured sidecar runner.
13. Add `--backend codemap` behind an explicit flag or `--backend auto --allow-local-index`.
14. Build a `ghx` ACP adapter only if existing adapters cannot express the needed sidecar UX.
15. Keep MCP direct tools for users who want primitive access.

## Open Questions

- What cheap default model is acceptable for local sidecar execution?
- Should the sidecar be a separate binary, a `ghx sidecar` subcommand, or both?
- Is Codex `app-server` stable enough to use as the first native sidecar runtime?
- Can Codex `mcp-server` model a sidecar agent well enough, or does it collapse the sidecar into a tool call?
- Is `acpx` sufficient as the durable sidecar session manager, or does `ghx` eventually need a native session layer?
- Is `codex-acp` sufficient for Codex-based sidecars, or does `ghx` need an adapter only for non-Codex runtimes?
- Should Codemap integration use a sparse clone, archive download, or existing local checkout?
- What is the default budget: max API calls, max files mapped, max files read, max local index time?
- How should sensitive/private repository handling be surfaced in the report?
- Should sidecar sessions be stateless by default, or cache repo snapshots by commit SHA?
- Should `ghx` ship a `doctor` or `sidecar doctor` command that validates token, network, binary path, and runtime assumptions before starting delegation?
