# 0016.6. Signal per Token — Measuring the North-Star Objective

## Status

Proposed 2026-07-04, while gate run `gate-run-2026-07` is in flight.
Deliberately **observational, not a gate**: measurement code for G1–G5 is
frozen during the run; SPT is computed read-only over stored artifacts and
introduces no new pass/fail criterion. Promoting SPT to a gate, if ever,
is a future pre-registered change.

## Context

The north star names signals per token as the optimization target (NORTH_STAR
"The Moat"): every unit of context should carry maximum reconnaissance
signal — for the main agent (so it stays good at engineering) and for the
sidecar brain (so it gets better at exploration, and eventually trains on
it). A target that is not measured is a slogan. Every episode already stores
both halves of the ratio: reward signal (`correctness`, `evidence`) and
context cost (`mainAgentChars`, `sidecarInternalChars`,
`totalWorkflowChars`).

## Decision

**Definition.** For an episode, `signal = correctness × evidence` (both in
[0,1]; the product demands claims that are both right and cited — signal
without evidence is vibes, evidence without correctness is noise). Tokens
are estimated as `chars / 4` (the ADR-0002 industry-standard estimate) until
real usage counts are available. SPT is reported at three levels, scaled
per 1,000 tokens:

| Level | Formula | What it measures | Who optimizes it |
|-------|---------|------------------|------------------|
| **Main-agent SPT** | signal ÷ (mainAgentChars/4) × 1000 | Signal density of what the customer agent pays for — the product's headline metric | The sidecar boundary (report contract, compression) |
| **Sidecar-internal SPT** | signal ÷ (sidecarInternalChars/4) × 1000 | Exploration efficiency of the brain — the future training objective (M10) | The sidecar brain (doctrine, ledger, escalation) |
| **Workflow SPT** | signal ÷ (totalWorkflowChars/4) × 1000 | Honest whole-system density, no hiding cost in the sidecar | The architecture as a whole |

For direct profiles, main-agent SPT and workflow SPT coincide (all context
is main-agent context); sidecar-internal SPT is undefined.

**Reporting.** `evalreport` prints per-profile SPT at all three levels with
episode counts; verdict artifacts include an informational SPT table. All
computation is read-only over episode JSON — nothing in rewards.go or
gates.go changes.

**Token-count upgrade path.** When the adapter exposes real usage
(`gen_ai.usage.input_tokens/output_tokens` — the OTel GenAI semconv slots
already exist in our spans), record it in episode identity/turn data and
prefer it over chars/4, keeping the chars/4 value alongside for continuity.

**Runtime SPT (M6).** Eval SPT has ground truth; runtime (dogfood) sessions
do not. When the shared SAF/SAFE trace infrastructure lands, runtime proxies
(follow-up rate, ledger citation rate, report acceptance without re-ask)
become the runtime signal estimate — designed there, not here.

**Anticipation accounting (M8, pre-committed).** Speculative exploration
spends tokens with zero realized signal until an anticipated question is
actually asked. Anticipation-era SPT must count unclaimed speculative spend
in the denominator — anticipation styles are budgets precisely so this
ratio stays honest.

## First measurement (2026-07-04, 17 episodes, informational)

Over v1/v2 smokes plus in-flight gate-round episodes: main-agent SPT ×1000 —
sidecar **0.97** vs ghx 0.05 / plain 0.06 (~16–19× signal density for the
customer agent); workflow SPT — sidecar 0.08 vs 0.05/0.06 (whole system
still ahead of direct exploration). Mixed-sample caveat applies; the gate
run will produce the citable numbers.

## Consequences

- The north-star objective becomes a number on every run report, trendable
  across product changes — ergonomics, ledger, escalation, anticipation,
  and eventually the trained model all move a measured needle.
- A second product story emerges for marketing: not only "35× less context"
  but "16× more signal per token for your agent."
- SPT is deliberately not a gate; G1–G5 remain the verdict.
