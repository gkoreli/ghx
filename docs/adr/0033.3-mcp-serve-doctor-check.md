# 0033.3. mcp-serve doctor check — verify the served-MCP surface

## Status

Accepted (2026-08-22). Follow-up to ADR-0033 / 0033.1 / 0033.2 in the
sidecar-runtime thread; closes the FRICTION 2026-08-22 soft item "`sidecar
doctor` has no check for the served-MCP path the founder actually uses" found
during L4 dogfood week 1.

## Problem

Doctor validated token, network, ghx binary, tier-2 tools, the ACP agent
handshake, and the report sink — but nothing exercised the served-MCP surface:
the `ghx serve` command line Claude Code spawns from the global
`~/.claude.json` `mcpServers.ghx` entry. When that surface breaks (stale npm
install, mis-wired config block, a serve mode without recon), every doctor
check passes while MCP recon calls fail inside Claude Code. The founder-daily
verification required a hand-rolled JSON-RPC probe (`scripts/
mcp-recon-probe.mjs`) — the one surface L4 depends on was the one surface
doctor did not check.

## Decisions

- **D1 — Resolution mirrors the client, with an env escape hatch.**
  `ResolveMcpServeCmd` returns the command line exactly as an MCP client would
  launch it: `GHX_MCP_SERVE_CMD` first (explicit override; the hatch for
  non-Claude MCP clients and probing alternate installs), else the
  `~/.claude.json` `mcpServers.ghx` argv joined verbatim. Resolution failures
  name the missing wiring so the failure is immediately attributable
  (ADR-0028.1 ergonomics style).
- **D2 — Doctor-path-only, like `--live`.** The check spawns a real process
  and can resolve the network, so it runs only in `sidecar doctor`, not in the
  parallel preflight registry shared by eval runs (`RunPreflightForAgent`
  stays hermetic). Same posture as `CheckLiveTurn` (ADR-0033 D4).
- **D3 — Real MCP client, not a hand-rolled JSON-RPC probe.** The check uses
  the already-vendored `mark3labs/mcp-go` stdio client (initialize +
  tools/list) instead of duplicating the node probe script; the script stays
  as the cross-language reference implementation.
- **D4 — Recon presence is the contract.** The default serve mode must expose
  the single `recon` tool (ADR-0019.3 D1); a server that initializes but does
  not list `recon` fails the check with the observed tool list plus
  remediation. Timeout bounded at 30s so a wedged server fails rather than
  hanging the doctor.

## Implementation

- `internal/sidecar/preflight_mcpserve.go`: `ResolveMcpServeCmd`,
  `CheckMcpServe`, `toolListOrNone`.
- `internal/cli/sidecar.go`: doctor prints the probe result as its own
  single-check preflight block ("Probing served-MCP surface") and folds it
  into the exit-code-3 gate.
- Tests (`internal/sidecar/preflight_mcpserve_test.go`): resolver unit tests
  (env override, claude-config parse, error naming) plus two binary-build
  stdio probes — pass against `<bin> serve` (recon listed) and fail against
  `<bin> serve --direct` (MCP-speaking but recon-less).

## Verification

- `go test ./...` green (exit 0), including both stdio probes.
- End-to-end on the founder machine: doctor run resolved the real
  `~/.claude.json` wiring (`npx -y @gkoreli/ghx serve`), completed initialize
  against the published server (ghx 2.10.1), and passed with `tools: recon`.

## Alternatives considered

- *Fold into RunPreflight registry* — rejected: eval-shareable preflight must
  stay hermetic (D2).
- *Ask-path probe (one real recon ask)* — rejected for doctor default: costs
  tokens and tens of seconds; `scripts/mcp-recon-probe.mjs` remains the
  deep-verify tool when an ask-level check is wanted.
