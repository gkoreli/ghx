# 0031.1. Anticipation v1 — off/warm/prefetch, gated on measured predictor value

## Status

Accepted (orchestrator, 2026-07-06). Decision memo over ADR-0031's research
for NORTH_STAR §2 / B9 / M8. Presupposes the shipped daemon (ADR-0030) and
session routing (ADR-0030.1). Nothing here changes scoring of existing runs;
the one measurement artifact this ADR introduces (D1 miner) is a new,
deterministic, offline analysis committed under `docs/evals/`.

## The forcing constraint

The research's `eager`/`aggressive` tiers serve *speculative model answers*.
The visibility tenet makes quality parity a serving precondition — an
anticipated answer must score indistinguishably from a fresh one — and the
instrument for that comparison is the calibrated judge (ADR-0023.1), which is
κ-blocked on founder labeling (TRUST H1). Building answer-serving tiers before
the parity instrument exists would ship exactly the failure the semantic-cache
literature warns about: instant, confident, unmeasurably wrong. So v1 is the
tiers that spend **zero LLM tokens** and whose value is measurable with
deterministic instruments today.

## Decisions

### D1 — Measure the predictor before building the machinery

`nextReads` is the trigger seed (ADR-0031 finding 1), but its predictive value
is an empirical claim we can test offline for free: committed multi-turn eval
episodes and dogfood sessions under `~/.ghx` already contain, for every turn
N, the report's `nextReads` and the files actually read at turn N+1 (tool
traces).

Build a deterministic miner (no LLM) that computes, over every available
multi-turn pair: **predictor recall** (fraction of turn-N+1 actually-read
files that appeared in turn-N `nextReads`, path-normalized) and **predictor
precision** (fraction of turn-N `nextReads` actually read at N+1). Commit the
analysis to `docs/evals/anticipation-predictor-2026-07/`.

**Gate:** the D4 prefetch build proceeds only if recall ≥ 0.30 on the
available corpus. Below that, prefetching `nextReads` is warming the wrong
files; the follow-up work is then a better trigger (ADR-0031 candidates 3/5),
not a build. Rationale for 0.30: prefetch cost per path is a single cached
GitHub read (near-zero marginal cost), so even a one-in-three hit rate
converts to real turn-time evidence savings — the Speculative Actions result
(55% accuracy → 20% latency win) had far more expensive speculation.

### D2 — The v1 ladder is `off` / `warm` / `prefetch`

Semantics exactly as ADR-0031's table:

- **off** — nothing. Hard guarantee, and the **non-negotiable default for
  eval runs**: measured turns are never contaminated by speculative state.
- **warm** — machinery only: daemon idle worker TTL (already ADR-0030 D4)
  plus prompt-cache keepalive pings during the idle window (aider's
  `--cache-keepalive-pings` pattern), count and cadence configurable.
- **prefetch** — deterministic evidence prefetch, zero model turns (D4).

`eager` and `aggressive` are **deferred to ADR-0031.2**, which may not be
written before (a) the judge is calibrated (κ ≥ 0.6 on founder labels) and
(b) D5 hit-rate data from prefetch exists. This is Chrome's upgrade
philosophy applied to the roadmap itself: ship the cheap tier, upgrade on
measured confidence.

Eagerness and depth stay separable axes in config design (style names bind
depth; trigger thresholds bind eagerness) so 0031.2 extends rather than
reshapes the surface.

### D3 — Scope resolution

Anticipation style resolves through the existing config ladder: global config
→ per-session override → per-ask override, smart default **warm** for
production (it is nearly free), **off** for anything driven by the evals
runner (enforced in code, not convention). The daemon config digest
(ADR-0030 D6) covers the anticipation settings so a style change cycles the
daemon like any other config change.

### D4 — Prefetch mechanics (built only if D1 gates pass)

- **Trigger, mechanical only:** top-N `nextReads` paths (N ≤ 5) from the
  just-accepted report, plus the ledger frontier (referenced-but-uninspected
  paths). No LLM calls anywhere in the trigger path.
- **Action:** in the daemon's idle window after a turn, run ghx CLI
  reads/maps for those paths; stage outputs under
  `<session>/anticipation/` with an `index.json` recording trigger source,
  creation turn, per-path repo HEAD SHA at fetch time, and byte sizes.
- **Isolation:** staged bundles are invisible to ledger derivation and to
  every eval artifact until consumed.
- **Consumption:** the next real turn's per-turn prompt gains a short
  "Prefetched evidence" section — path, freshness SHA, staged location —
  instructing the agent to use the staged copy and cite the repo path. This
  is a per-turn prompt change, not a persona change (no golden-hash impact);
  it is pre-registered by this ADR.
- **Invalidation:** on consumption, re-check repo HEAD (one API call).
  Unchanged → serve. Changed → drop the bundle and record a demotion; the
  turn proceeds cold. TTL backstop 24h. Any persona revision, model change,
  or ghx version change drops all staged bundles (config-digest rule).
- **Preemption:** prefetch runs are plain CLI subprocesses — a real ask on
  the session cancels them immediately (Hadoop lesson: cancel promptly,
  account the waste). Foreground p95 must not regress; that is a SAFE gate,
  not an aspiration.

### D5 — Observability and SAFE measurement

Web-prefetch vocabulary, no invented names: **hit rate** (prefetched paths
actually read next turn), **precision/waste** (staged bytes and API calls
never used before invalidation), **cost per useful hit**, **staleness
correctness** (zero consumed bundles with invalid provenance), and the
**foreground-degradation guard** (real-ask p95, anticipation on vs off).
Trace attributes in the ADR-0030 D7 namespace:
`ghx.sidecar.anticipation.style|trigger|staged|hit|age_ms|demoted`. Multi-turn
eval tasks with pre-registered hidden follow-ups (ECIR 2024 simulation recipe)
are the measurement vehicle and land with the D4 build, as their own
pre-registered eval-corpus addition.

## What this rejects, explicitly

- No question embeddings and no semantic cache in v1 (GPTCache failure modes;
  new infra for a serving tier we are not building yet).
- No LLM follow-up generation in v1 (spend belongs behind measured demand).
- No anticipated-answer serving of any kind until 0031.2's preconditions.

## Sequencing

1. D1 miner + committed analysis (delegable now; zero live episodes).
2. If gate passes: D4 build + D5 instrumentation + the multi-turn follow-up
   eval tasks, as one slice.
3. 0031.2 (eager tiers) blocked on judge calibration + D5 data.
