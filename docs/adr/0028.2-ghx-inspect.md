# 0028.2. ghx inspect — One-Shot Budgeted Concern Inspection

## Status

Proposed. This is the batch-2 design pass explicitly deferred by
ADR-0028.1: `ghx inspect <repo> <query>` for defect 4 in
`docs/evals/mining-2026-07-06/CLI-FINDINGS.md`.

North-star filter: this command removes token-expensive reconnaissance chains
from the main agent by replacing `search -> read result files`,
`map -> line reads`, and `explore -> tree -> read` with one ranked,
budgeted response. It advances NORTH_STAR workstream A2/A4 and supports the
sidecar's CLI-layer tool surface without duplicating the future Tier-2 local
analysis work from ADR-0024.

## Evidence Reviewed

- `docs/adr/0028.1-cli-ergonomics-batch.md`: `inspect` deferred because it is
  the highest-value but largest batch-1 surface.
- `docs/adr/0028-agent-facing-cli-research.md`: prior art from aider repomap,
  semgrep, ast-grep, Sourcegraph `src`, and Anthropic's consolidated workflow
  tools. Two hard requirements carry forward: budgeted from birth; truncation
  carries next-step hints.
- `docs/evals/mining-2026-07-06/CLI-FINDINGS.md`: defect 4 observed
  `map -> line reads` in 77 runs, `explore -> subdir explore/tree -> read` in
  63 runs, and `search -> read result files` in 46 runs.
- `docs/adr/0024-escalation-tiers-research.md`: Tier 2 is local-clone
  structural analysis (`codemap`, stack-graphs, importers, blast radius). This
  command must remain remote-first Tier 1 and must not pretend to provide
  cross-file reference intelligence.
- `internal/ghx/read.go`: existing batched file fetch, glob expansion, grep,
  line slicing, map fallback, and per-file budget behavior.
- `internal/ghx/search.go`: existing GitHub code search with text matches,
  result limits, fragment truncation, and approximate output budget.
- `internal/ghx/tree.go` and `internal/ghx/glob.go`: existing recursive tree
  fetch and doublestar glob matching.
- `internal/mapengine/types.go`, `goast.go`, `treesitter.go`: existing
  per-file structural maps for Go, TS/TSX, JS/JSX, Python, Rust, and regex
  fallback. Current mapengine extracts file-level symbols; it does not build a
  repo-wide reference graph.

## Decision

Add:

```text
ghx inspect <owner/repo> <query>
```

`inspect` answers "show me the most relevant files and evidence for this
concern" in one call. It returns ranked files, structural maps, bounded
snippets, and next-step hints inside one shared `--budget`.

Initial flags:

```text
--budget N      approximate total output budget in characters, default 12000
--limit N       candidate search limit before ranking, default 30, max 100
--lang LANG     pass-through language qualifier for repo-first search
--glob GLOB     pass-through path qualifier and tree-filter hint
--path PATH     prefer or constrain a subtree
--json          structured output for sidecar/tool callers, when JSON support lands
```

`--budget` is the controlling dial. `--limit` controls candidate discovery, not
final verbosity. There is no `--full` for `inspect` in the first version:
unbounded concern inspection would recreate the exact multi-command verbosity
defect at a higher level. Agents that need more evidence raise `--budget` or
follow the narrowing hints.

Examples:

```text
ghx inspect gkoreli/ghx "flag error suggestions"
ghx inspect gin-gonic/gin "routing middleware" --lang go
ghx inspect openai/openai-node "streaming responses" --glob "src/**/*.ts"
```

## Output Contract

Default text output is optimized for agent consumption, not human browsing.

Shape:

```text
inspect: <repo> "<query>"
budget: <used>/<budget> chars
ranked files:
1. <path> score=<score> reasons=<reason,reason>
   map:
     <structural map lines>
   snippets:
     <line range>: <bounded snippet>
     <line range>: <bounded snippet>
   next:
     ghx read <repo> <path> --lines A-B
2. ...
truncation:
  <what was omitted>
  <specific next command>
```

Rules:

- Rank before truncating. Never return the first N search results merely
  because they arrived first.
- Spend the budget in tiers:
  1. compact header and total-match metadata
  2. ranked file list with score reasons
  3. structural map for each included file
  4. one or more bounded snippets per included file
  5. truncation footer with next-step hints
- Per-file sections may be omitted only from the bottom of the ranked list.
  Within an included file, prefer keeping the map plus the best snippet over
  printing many snippets without structure.
- Snippets are bounded by line count and characters. The first version should
  use semgrep-like small snippets: matching line plus limited surrounding
  context, not whole functions by default.
- Every truncation must explain what to do next:
  `raise --budget`, narrow with `--glob`, narrow with `--path`, constrain with
  `--lang`, or read a specific file/range.
- Output must include enough line anchors that the next agent step can call
  `ghx read <repo> <path> --lines A-B` without guessing.

## Ranking Decision

Use a hybrid ranker.

Rejected as the primary ranker:

- **Pure import-graph centrality**: attractive for "important files", but ghx
  does not currently have a repo-wide import graph. Building one remotely would
  require fetching many files and would duplicate ADR-0024 Tier-2 local tooling.
  It also tends to over-rank hubs that are central but not query-relevant.
- **Pure search relevance**: cheap and query-directed, but GitHub code search
  returns line fragments, not a structural answer. It also misses files that
  are important because of symbol/path relationship to the query rather than a
  direct textual hit.

Recommended hybrid:

1. Start with GitHub code search candidates using existing `Search`.
2. Deduplicate by file path and preserve search-order evidence as the base
   relevance signal.
3. Fetch only the top candidate files, using existing batched `Read`.
4. Run `mapengine.Map` on fetched content.
5. Score each file from explicit, auditable features:
   - search rank and match count
   - exact query-term hits in path
   - exact query-term hits in symbol names/signatures
   - language/path/glob constraints
   - candidate-local import mentions when already visible in fetched files
   - small positive boost for files referenced by several other fetched
     candidates
6. Emit score reasons, not opaque numbers alone.

This is "hybrid remote Tier 1": search relevance finds the concern, structural
maps explain the files, and candidate-local centrality is allowed only when it
comes from data already fetched inside the budgeted inspection. Whole-repo
importers, blast radius, call graphs, definition/reference graphs, and local
clone indexes remain Tier 2 per ADR-0024.

## Reuse vs Build

Reuse:

- `internal/ghx.Search` for candidate discovery.
- `internal/ghx.Read` and its GraphQL batching for candidate file fetches.
- Existing `--lang`, `--glob`, `--path`, `--limit`, and `--budget` CLI
  conventions from ADR-0028.1.
- `internal/mapengine.Map` for file-level structural maps.
- Existing tree/glob machinery for path filtering and hints.
- Semantic exit-code plumbing from `internal/cli/errors.go`.

Build:

- `internal/ghx/inspect.go` with named domain models:
  `InspectOptions`, `InspectResult`, `InspectCandidate`, `InspectFile`,
  `InspectSnippet`, `InspectHint`, and `InspectTruncation`.
- A small `InspectRanker` service that owns scoring features and reason
  strings.
- A `BudgetWriter` or equivalent presentation allocator shared by the text and
  future JSON presenters so truncation behavior is deterministic and tested.
- Snippet extraction that turns search fragments and file content into line
  ranges with bounded context.
- CLI command wiring in `internal/cli/ghx.go`.

Do not add anonymous map-heavy plumbing for ranking or output assembly. The
ranker and result types are the domain model; tests should assert their
behavior directly.

## Sidecar Relationship

`inspect` is a CLI-layer tool the sidecar should call before escalating to
deeper backends. The design target is signal per token:

- The main agent should not need to know whether to call `search`, `read
  --map`, `read --lines`, or `tree` first.
- The sidecar may call `inspect` as its first Tier-1 concern-localization tool.
- `inspect` must report its limitations honestly. If the output suggests
  "need importers", "need call graph", or "need blast radius", the next-step
  hint should name Tier 2 rather than faking that answer remotely.
- Future sidecar reports should record `inspect` as a remote backend tool call,
  not as local structural analysis.

This keeps the CLI useful directly while preserving the NORTH_STAR end state:
the main agent reaches for the sidecar brain; the sidecar reaches for ghx tools.

## Verification Plan

Unit tests:

- Ranking fixtures where search rank, path match, symbol match, and
  candidate-local import mentions produce deterministic order and score
  reasons.
- Budget tests proving the output never exceeds `--budget` except for a small
  documented formatting tolerance.
- Truncation tests proving every omitted file/snippet carries a next-step hint.
- Snippet tests for line range extraction and bounded context.
- CLI tests for command shape, flag parsing, bad repo/query errors, and
  semantic exit codes.

Integration smoke tests:

```text
ghx inspect gkoreli/ghx "flag error suggestions" --budget 6000
ghx inspect gin-gonic/gin "routing middleware" --lang go --budget 6000
ghx inspect openai/openai-node "streaming responses" --glob "src/**/*.ts" --budget 6000
```

Mining verification:

- Re-run the defect-signature miner against fresh traces after adoption.
- Success signal: the three defect-4 command-chain signatures shrink:
  `map -> line reads` (baseline 77), `explore -> subdir explore/tree -> read`
  (baseline 63), and `search -> read result files` (baseline 46).
- This does not require a full gate run to continue engineering. Per
  AGENTS.md and ADR-0028.1, full-rigor runs re-ground citable numbers; they do
  not block product work.

## Considered and Rejected

- **`ghx focus` instead of `ghx inspect`**: "focus" is shorter, but "inspect"
  better describes a read-only diagnostic command and matches the miner's
  recommendation. Use the name agents already saw in the design corpus.
- **Making `inspect` an alias over `search` plus `read --map` in the CLI
  presenter**: rejected because ranking, budgeting, truncation, snippets, and
  hints need one domain model. Stringing commands together would preserve the
  hidden complexity instead of removing it.
- **Whole-repo import PageRank in v1**: rejected because it requires fetching
  and parsing broad repo content remotely, duplicates ADR-0024 Tier-2 local
  tooling, and risks turning a one-shot inspection into an expensive indexer.
- **Pure aider-style repo map**: rejected for v1 because ghx does not yet have
  a repo-wide definitions/references graph. The lesson to copy is budgeted
  ranking, not the exact implementation.
- **Unbounded `--full`**: rejected because `inspect` exists to eliminate
  verbose multi-command exploration. Raising `--budget` and following hints is
  the explicit escalation path.
- **LLM-generated summaries inside `inspect`**: rejected. ghx is a deterministic
  evidence tool. The sidecar or main agent can summarize; the CLI should return
  ranked evidence with auditable line anchors.

## Open Questions

- Exact default budget: start with the shared ADR-0028.1 default of 12000
  characters unless implementation tests show the minimum useful inspect output
  needs a different default.
- JSON output timing: `--json` should exist once the repo has a shared JSON
  output contract. If that contract is not implemented in the first patch,
  keep the typed `InspectResult` ready and defer the flag.
- Candidate-local import scoring: useful for Go/TS/Python modules, but only if
  it can be implemented from already fetched files without expanding scope.
  If it complicates v1, ship search+path+symbol hybrid first and add the import
  feature in a follow-up ADR or implementation note.
