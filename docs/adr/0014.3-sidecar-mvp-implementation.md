# 0014.3. `ghx-sidecar` MVP Implementation Architecture

## Context

ADR-0014.2 authorized MVP phase 2 after the Hono and OpenAI Node sidecar experiments passed
the PoC gate. The authorized scope was:

> A canonical sidecar prompt, a strict report schema, a `doctor` preflight, a lightweight
> evidence session store, and a one-command way to ask a named sidecar a high-level repo
> question and capture the final report.

This ADR records what was actually built, the architectural decisions that shaped the
implementation, the reasoning behind the final design, insights from the path taken, and a
cross-reference table mapping each design decision back to source code evidence.

## What Was Built

`packages/ghx-sidecar` is a named, persistent ACP sidecar harness for `ghx` repository
reconnaissance. It is an ESM TypeScript package that ships as both a CLI binary
(`ghx-sidecar`) and a public library API (`@gkoreli/ghx-sidecar`).

### Module Structure

```
packages/ghx-sidecar/src/
  index.ts           – CLI entry + public library re-exports
  acpx.ts            – ACP runtime bridge (acpx/runtime SDK)
  schema.ts          – SidecarRequest, SidecarReport, Claim, Evidence, RelevantFile
  core/
    config.ts        – GhxSidecarConfig, loadConfig, saveConfig, detectAgents
    preflight.ts     – runPreflight, formatPreflight (doctor checks)
    prompt.ts        – createSidecarPrompt (system prompt factory)
    session.ts       – disk-backed SessionMeta, initSession, recordTurn, saveReport
```

### CLI Surface

```
ghx-sidecar [--session <name>] [--repo <owner/repo>] [--no-wait] <question>
ghx-sidecar sessions list | show <name> | clear <name>
ghx-sidecar config show | init | set <key> <value>
ghx-sidecar doctor
```

### Runtime Stack

```
ghx-sidecar CLI
  → acpx/runtime SDK (createAcpRuntime, ensureSession, startTurn)
    → ACP JSON-RPC 2.0 over stdio
      → codex-acp | claude | kiro (whichever agent the user has installed)
        → ghx CLI (evidence commands: explore, tree, read, search)
          → GitHub REST / GraphQL API
```

The sidecar does not implement ACP. It is an ACP client. The downstream agent (Codex,
Claude, Kiro) holds the LLM subscription and processes the injected sidecar prompt.

## Architectural Decisions

### Decision 1: ACP Client, Not ACP Server

The first implementation built `ghx-sidecar` as an ACP server: `AgentSideConnection` from
`@agentclientprotocol/sdk`, an HTTP transport layer using Hono, and a Claude API runner that
called Anthropic directly.

That was wrong in both directions.

`ghx-sidecar` is not a server. It does not serve ACP requests from IDE clients. Its role is
to send a repo question to an ACP agent and receive the response. The correct layer is
`ClientSideConnection`, not `AgentSideConnection`. More precisely, `ghx-sidecar` is an ACP
client that drives an existing ACP agent session.

The Claude runner was equally wrong. The whole point of ACP is to reuse the engineer's
existing LLM subscription — their locally installed Codex, Claude CLI, or Kiro. Building a
direct Anthropic API runner inside `ghx-sidecar` duplicated that subscription and bypassed
the engineer's actual configured runtime.

**Corrected design**: `ghx-sidecar` is a thin ACP client that prepends the sidecar persona
prompt on first use of a named session, then delegates all subsequent turns to whatever ACP
agent the engineer has installed.

### Decision 2: acpx/runtime SDK, Not Subprocess Spawning

The second implementation wrapped the `acpx` CLI as a subprocess:

```typescript
const proc = spawn(acpxBin, [agent, '--session', session], {
  stdio: ['pipe', 'inherit', 'inherit'],
});
proc.stdin.write(prompt, 'utf8');
proc.stdin.end();
```

That was the right direction — reuse acpx rather than build ACP protocol code — but the
wrong layer. Subprocess wrapping inherits all of its costs:

- Quoting and escaping issues on complex prompts
- No typed access to the event stream
- No ability to intercept individual events for artifact saving
- Parsing session state from CLI stdout strings
- Coupling to CLI flag names and output format, not the SDK contract

`acpx` ships a public TypeScript module export at `acpx/runtime` that exposes:
`createAcpRuntime`, `createFileSessionStore`, `createAgentRegistry`, `ensureSession`,
`startTurn`, and an `AsyncIterable<AcpRuntimeEvent>` event stream. The SDK surface is
exactly what a thin client harness needs.

**Corrected design**: `acpx.ts` imports `acpx/runtime` directly. No subprocess. The
`acpxBin` config field was removed from `GhxSidecarConfig` as it reflected the old
subprocess mindset.

### Decision 3: Two-Layer Persistence

Session persistence has two separate concerns that must not be conflated.

**Layer 1 — ACP session store** (`~/.ghx-sidecar/acp-store/`): managed by `acpx/runtime`
via `createFileSessionStore`. Stores ACP protocol state: session record IDs, backend session
handles, turn continuity. This is opaque to `ghx-sidecar` logic.

**Layer 2 — ghx-sidecar evidence store** (`~/.ghx-sidecar/sessions/<name>/`): managed by
`core/session.ts`. Stores reconnaissance artifacts: `meta.json` (repo, scope, turn count,
timestamps), an `initialized` marker file (written on first turn), and
`report-<ts>.json` files (saved evidence reports per completed turn).

The two stores exist for different reasons:

- The ACP store ensures session continuity at the protocol level — the agent's persistent
  in-context state across turns.
- The evidence store preserves ghx-sidecar-specific artifacts that survive session restarts,
  feed into follow-up context via `buildPriorContext`, and can be inspected by the engineer
  without connecting to an ACP agent.

The `initialized` marker file is the join between the two layers: it signals that the
sidecar persona prompt has been sent and the ACP session is already conditioned, so
subsequent turns should skip the persona injection and send the question directly.

### Decision 4: Prompt Injection on First Turn

The sidecar agent role cannot be assumed to persist across cold-started sessions. Rather
than relying on a pre-configured system prompt in the ACP agent, `ghx-sidecar` injects the
full persona on first use of each named session.

On first turn, `createSidecarPrompt(request)` produces a complete agent definition
containing role, repo, session, question, depth, allowed backends, operating loop, tool
discipline, budget, output schema, and failure mode. This is prepended to the first question:

```
<agent definition>

---

Question: <first question>
```

On subsequent turns, the ACP session already carries the injected role in its context
window, so `ghx-sidecar` sends the question text directly without re-injecting the persona.

This approach is stateless at the prompt layer and stateful at the ACP session layer. The
correct design for both:

- Correctness: the agent definition is always present on first use, regardless of whether
  the ACP agent was cold-started or had the sidecar role in prior configuration.
- Economy: follow-up turns do not re-send the full agent definition, which would waste
  tokens and risk overriding any accumulated session context.

### Decision 5: deny-all Permission Mode

`ghx-sidecar` is a read-only reconnaissance tool. It should never approve file writes,
commits, shell mutations, or any side effects initiated by the downstream ACP agent.

The `acpx/runtime` permission model enforces this through `permissionMode` and
`nonInteractivePermissions`:

```typescript
createAcpRuntime({
  permissionMode: 'deny-all',
  nonInteractivePermissions: 'deny',
  ...
})
```

`deny-all` means no permissions are auto-approved. `nonInteractivePermissions: 'deny'`
means approval requests that cannot prompt interactively are silently denied rather than
failing the turn. Combined, these settings enforce the reconnaissance-only contract at the
runtime level, not only in the prompt text.

This matters because the sidecar prompt alone cannot prevent a permissive downstream agent
from attempting writes if the runtime sandbox allows them. The permission mode is a hard
enforcement layer, not a courtesy hint.

### Decision 6: Single Binary and Library Package

`ghx-sidecar` is both a CLI tool (invoked as `ghx-sidecar <question>`) and a TypeScript
library that exports all of its core functions. This gives downstream tooling (the main
`ghx` binary, IDE extensions, scripts) access to `createSidecarPrompt`, `runPreflight`,
`acpxSend`, session management functions, and typed schemas without shelling out.

The dual role is implemented through a single `src/index.ts` with a guard:

```typescript
if (import.meta.url === `file://${process.argv[1]}`) {
  await cli(process.argv.slice(2));
}
```

All exports above the guard form the public library API. All CLI-specific logic lives inside
the `cli()` function which is only called when the file is run directly.

## Implementation Journey

### First Build: Over-Engineering Trap

The first implementation included:
- `src/transport/StdioTransport.ts` and `src/transport/HttpTransport.ts`
- `src/runner/ClaudeRunner.ts` calling the Anthropic API directly
- `src/server.ts` creating a full ACP server via `AgentSideConnection`
- Hono as an HTTP framework for routing ACP requests
- Custom ACP type definitions duplicating what `@agentclientprotocol/sdk` already provides

None of this was needed. The over-engineering came from starting with "how do I implement
an ACP endpoint" instead of "how does the engineer's existing agent receive a prompt."

The corrected mental model: `ghx-sidecar` is not in the ACP server business. It is in the
"send a structured question to the right running agent and collect the answer" business.

### Discovery: @agentclientprotocol/sdk Already Exists

After building custom ACP types, the official `@agentclientprotocol/sdk` (Apache-2.0,
v0.20.0) was discovered. It provides `AgentSideConnection`, `ClientSideConnection`,
`ndJsonStream`, Zod-validated ACP types, and all JSON-RPC 2.0 message shapes. The custom
type file was deleted entirely.

This confirmed the more important realization: if the official SDK already models the
protocol, `ghx-sidecar` should be working with the protocol as a client, not re-implementing
it as a server.

### Discovery: acpx/runtime SDK

Subprocess wrapping of the `acpx` CLI was the obvious first pass: `spawn(acpx, ...)`,
write the prompt to stdin, inherit stdout/stderr. It worked, but at the cost of all the
limitations described in Decision 2 above.

The `acpx` npm package (v0.6.1) exports `acpx/runtime` with a complete TypeScript SDK:
`AcpxRuntime`, `AcpRuntimeHandle`, `AcpRuntimeTurn`, `AcpRuntimeEvent`, and factory
functions. The session store and agent registry are pluggable. The event stream is a typed
`AsyncIterable`. This is exactly the right integration surface.

The `acpx/runtime` discovery removed the rationale for subprocess wrapping entirely.

### The acpxBin Code Smell

The original `GhxSidecarConfig` included an `acpxBin: string` field pointing to the path
of the `acpx` CLI binary on disk. That field was a structural symptom of the subprocess
mindset: the only reason to configure a binary path is because you are going to spawn it.

Once the implementation moved to `acpx/runtime` imports, `acpxBin` had no role. It was
removed from the config type. Its removal also simplified `formatConfig` output and
eliminated a potential source of misconfiguration (a wrong path silently falling back to
the default `"acpx"` string).

A config field should model an intention, not an implementation artifact. `acpxBin` modeled
the implementation artifact of subprocess spawning, not any user-facing intention.

### preflight.ts: Environment Contract Made Explicit

ADR-0014.1 identified the MVP runtime lesson: a sidecar that silently fails auth or network
checks produces confusing exploration failures. The `doctor` subcommand implements the
explicit environment contract described in that ADR.

`runPreflight` runs three checks in parallel: `GH_TOKEN`/`GITHUB_TOKEN` presence, HEAD
request to `api.github.com` with a 5-second timeout, and `ghx --version` via exec. The
`doctor` CLI handler adds a fourth check: `acpxDoctor(config.agent)` calls
`runtime.doctor()` to probe whether the configured ACP agent is reachable.

The four checks map directly to the four hard runtime requirements from ADR-0014.1:

| ADR-0014.1 requirement | Doctor check |
|------------------------|-------------|
| GitHub token source | `checkGhToken`: GH_TOKEN / GITHUB_TOKEN |
| Network access to GitHub APIs | `checkNetwork`: HEAD api.github.com |
| ghx binary on PATH | `checkGhxBinary`: exec `ghx --version` |
| Agent runtime available | `acpxDoctor`: `runtime.doctor()` |

### Session Naming Convention

Named sessions use the `ghx-sidecar:<name>` prefix as the ACP `sessionKey`. This scopes
them in the acpx session store — they are visible and distinguishable from any other ACP
sessions the engineer may be running — and makes their purpose clear in `sessions list`
output.

The default session name is `"default"`, producing `ghx-sidecar:default`. Engineers can
create topic-scoped sessions: `ghx-sidecar:hono-middleware`, `ghx-sidecar:openai-streaming`,
`ghx-sidecar:ghx-map-engine`. Follow-up questions addressed to the same session name reuse
the accumulated ACP in-context state without re-injecting the persona.

## Insights

- **Protocol role clarity is prerequisite to architecture.** The first build was fully
  functional in isolation (Hono, AgentSideConnection, ClaudeRunner compiled and ran) but
  modeled the wrong role. Identifying that `ghx-sidecar` is an ACP client, not an ACP
  server, eliminated the entire transport, runner, and server layers in one step.

- **Subprocess wrapping is always a temporary abstraction.** `spawn(acpx, ...)` was a
  reasonable first pass but created a structural ceiling: every future capability (event
  interception, artifact saving, typed session state, cancellation) would require either
  parsing CLI output or giving up. The SDK was the right integration surface from the start.

- **Config field presence encodes architectural assumptions.** `acpxBin: string` existed
  only because the implementation would spawn the binary. When the implementation changed,
  the field had no meaning. Removing it was not cleanup — it was the correction of a
  structural lie about how the system worked.

- **Two-store separation is load-bearing.** If the ACP session store and the evidence store
  were merged, the initialized-marker pattern would not exist and prompt injection would
  require either ACP introspection (fragile) or a flag in config (env-coupled). The
  separation lets each store own its concern without either leaking into the other.

- **The persona injection problem is a cold-start problem, not a config problem.** Solving
  it by writing the sidecar persona to an ACP agent's system-prompt config file would tie
  `ghx-sidecar` to how each ACP agent handles initial configuration. The injection-on-first-
  turn pattern is universal: it works for any ACP agent without touching that agent's config.

- **Permission mode is evidence contract, not prompt politeness.** The sidecar prompt says
  "do not edit files, do not make commits." The `deny-all` permission mode enforces that
  contract regardless of what the downstream agent decides. Both are necessary. The prompt
  shapes behavior; the permission mode prevents accidents.

- **The report schema is the real product contract.** The CLI, the prompt, and the session
  store are all infrastructure. The evidence report — `SidecarReport` with its `verified`,
  `inferred`, `unverified`, `relevantFiles`, `commandsRun`, `uncertainty`, and `nextReads`
  fields — is what the main agent receives and acts on. Every other design decision serves
  that contract.

- **`acpx/runtime` absorbs all ACP protocol complexity.** Session management, binary
  lifecycle, turn sequencing, ACP JSON-RPC framing, and event parsing are all handled inside
  `acpx`. `ghx-sidecar` only needs to express intent: new session with this agent, send
  this prompt, iterate events, await result. The SDK contracts this down to four method calls.

## What Was Not Built

Per ADR-0014.2 phase gate constraints, the following were explicitly excluded:

- **ACP adapter for `ghx`**: `ghx-sidecar` reuses existing ACP agents; `ghx` does not
  expose its own ACP server surface.
- **Codemap auto-escalation**: `allowedBackends` defaults to `['remote']`; Codemap
  escalation is encoded as a prompt constraint, not an automatic runtime behavior.
- **Event-driven report capture**: `saveReport` exists and the `SidecarReport` schema is
  defined, but the current implementation does not parse `submit_report` tool calls from the
  event stream and auto-save them. That wiring is the next milestone.
- **Daemon or background process**: the runtime is per-invocation; `acpx` owns any
  persistent agent process lifetime.
- **Fine-tuning or model selection**: the sidecar uses whatever model the engineer's ACP
  agent runs; no model-selection logic exists in `ghx-sidecar`.

## Open Questions

- Should `acpxSend` intercept `tool_call` events for `submit_report` and automatically
  call `saveReport`, or should that be wired in the CLI handler?
- Should `sessions show` display the final evidence from the latest report in a structured
  format rather than raw JSON?
- Should `sessions list` show a summary derived from the most recent `SidecarReport` fields
  (`answer`, `relevantFiles`) rather than just turn count and timestamps?
- How should the evidence store handle session name collisions across different repos? The
  current design allows `ghx-sidecar:default` to be pointed at different repos in
  successive invocations, which silently overwrites the scope.
- Should `inferRepo` be removed in favor of requiring explicit `--repo`? Silent inference
  from question text can match false positives in `owner/repo` pattern.
- When a session is cleared via `sessions clear`, should the corresponding ACP session in
  `~/.ghx-sidecar/acp-store/` also be evicted, or is cross-store consistency out of scope?
