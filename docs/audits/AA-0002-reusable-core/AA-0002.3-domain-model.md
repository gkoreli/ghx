# AA-0002.3 — Domain modeling at the SAF↔SAFE seam

Read-only audit answering the charter's domain-modeling question directly:
**of the nouns that flow across the runtime↔evals seam — `Report`, `TurnResult`,
`ToolCallTrace`, session/ledger, `Episode`, the OTel trace/artifact — which are
ONE canonical type with one authoritative owner, and which are parallel copies
re-interpreted on each side that silently drift?** Every finding cites
`file:line`, ties to a named tenet, and is re-priced for our context:
groundability (a named type with one owner) is the currency of trust for an
agent fleet; a concept captured twice and re-parsed at each call site is
un-findable and diverges without anyone noticing.

This audit is orthogonal to the shipped `docs/audits/architecture-vision/domain-model-2026-07-07.md`
(that one is about at-rest/in-motion nouns *inside* core — `ghx.Repo`,
`Snapshot`, `RouteDecision` flowing core→sidecar→report→frontend). **My axis is
the eval↔runtime seam specifically** — the shared-kernel question of AA-0002. No
overlap; I extend, I do not re-litigate.

## Executive summary

**The seam already contains the right pattern and the wrong pattern side by
side, and the answer to the charter's headline question is a single noun.**

- **The wrong pattern:** `ToolCallTrace` (and its `ToolStatusTransition`) is
  defined **twice** — once in the runtime (`turnresult.go:79-94`) and once in
  evals (`episode.go:183-197`) — with **byte-identical struct bodies, doc
  comment included.** Two bidirectional converters bridge the copies
  (`convertSidecarTrace`, `trace.go:12`; `hostLiveTraces`, `host_episode.go:296`),
  and the ACP-notification→trace *capture logic* that builds each copy is also
  written twice (`denyClient.SessionUpdate`, `denyclient.go:230`; `evalClient.SessionUpdate`,
  `client.go:124`). The duplication has **already drifted**: `convertSidecarTrace`
  drops the `Locations` field, and the two capturers disagree on what `Locations`
  even *means* (union vs. replace). This is the exact anti-pattern the Engineering
  Tenets forbid by name.

- **The right pattern, three feet away:** `Report` and `RawSDKAudit` are each ONE
  canonical `sidecar.*` type that evals consumes directly and round-trips through
  JSON (`episode.go:148,273`; `rawsdk.go:92`). The OTLP writer machinery is one
  shared `telemetry` package (ADR-0022 D1). These are the model of a real DDD
  shared kernel and prove the pattern works here.

**The one concept that, given one canonical type, eliminates a class of eval↔runtime
divergence is `ToolCallTrace`.** Collapsing the evals copy into `sidecar.ToolCallTrace`
— exactly as evals already does for `sidecar.Report` — deletes both converters,
erases the `Locations`-drop bug, and removes one of the two duplicate capturers.
The JSON tags are identical, so at the artifact level it is serialization-preserving
and **not** measurement-touching; only the second-order capture-semantics
reconciliation is. This is *naming a recurring concept*, not extracting a
framework — it passes YAGNI because the second consumer (evals) already exists and
already pays the tax.

The charter's central claim — *"a trace is a trace whether from an eval episode or
a real question"* (NORTH_STAR) — is **true at the OTLP transport layer and false at
the semantic span layer**: the writers are shared, the span vocabulary is forked
(`sidecar.ask`/`ghx.sidecar.*` vs. episode/turn/tool/`ghx.eval.*`). I file that as
a future-facing watch item, not a defect (see §Least-confident call).

## What is already right (verified nulls)

These I checked specifically expecting duplication and found a single owner. They
are the pattern the findings below should be pulled toward.

- **`Report` is one canonical type, and evals round-trips it.** `sidecar.Report`
  (`report.go:38-57`) is used directly by evals everywhere: the episode field is
  `*sidecar.Report` (`episode.go:148,273`), reward scoring reads it
  (`rewards.go:88,121-122`), the judge bundle projects from it
  (`judge_bundle.go:142`), and anticipation loads runtime-written report JSON
  straight back into `sidecar.Report` (`anticipation_predictor.go:323`). There is
  **no parallel report struct** and the extractor/validator lives once
  (`report.go:74-132`). This is the exemplar: a Report is a Report whether the
  runtime wrote it or evals read it. Tie: Engineering Tenets "Define proper domain
  models" — satisfied.

- **`RawSDKAudit` is one canonical type with one behavior owner.** Defined once
  (`rawsdk.go:37,92`), with the `Record` method (`rawsdk.go:173`) and
  `CanonicalJSONDigest` (`rawsdk.go:115`) as the single owner. Both capturers feed
  the *same* type (`denyclient.go:101-104`; `client.go:206-209`) and the
  trace-capture comparator reads it (`trace_capture.go:66`). No drift possible —
  contrast directly with `ToolCallTrace`, its sibling on the very same
  `TurnResult`. Tie: Engineering Tenets "Encapsulate domain logic in services /
  one authoritative owner" — satisfied.

- **The accounting primitives are shared.** `ContentSize` and `ToolOutputText`
  (`tooltrace.go:13,35`) are the single owner of char accounting; the evals
  capturer calls the `sidecar.*` versions rather than reimplementing them
  (`client.go:159,161,184,186`). This is why char accounting does *not* drift even
  though the surrounding capture loop does — a clean demonstration that "call the
  owner" beats "copy the logic."

- **The OTLP writer substrate is a genuine shared kernel.** The generic OTLP JSON
  File machinery — tracer provider, file exporter, log/metric writers, hex-span-ID
  transcoding, UTF-8 sanitization — lives once in `telemetry`
  (`provider.go:22`, `trace.go:50`, `logs.go:29`, `metrics.go:17`) and is imported
  by both evals (`otel_trace.go:13,36,51`) and the runtime (`emit.go`). This is
  ADR-0022 D1 executed correctly and honors Open-Source-Leverage (official OTLP,
  one writer, custom fields ride alongside as attributes). Tie: NORTH_STAR
  North-Star Filter "agent traces are official OTel exactly per spec" — satisfied.

- **`Ledger` is runtime-owned and not re-derived in evals.** `Ledger`/`LedgerEntry`
  live once (`ledger.go:13,28`); `UpdateLedgerFromTurn` (`ledger.go:87`) consumes
  `[]sidecar.ToolCallTrace` directly. The "ledger" tokens in evals are prose in
  comments, not a parallel struct. The session/ledger noun does **not** drift.
  (Caveat threaded into Finding 3: evals *does* re-derive a command list by a
  different route — a narrower instance, not a duplicate Ledger.)

## Findings

### H1 — `ToolCallTrace`/`ToolStatusTransition` are parallel copies, and they have already drifted

**Severity: High.** `sidecar.ToolCallTrace` (`turnresult.go:79-94`) and
`evals.ToolCallTrace` (`episode.go:183-197`) are **byte-identical struct bodies,
doc comment included** (verified by side-by-side diff — the `Locations` comment is
copied verbatim). Same for `ToolStatusTransition` (`turnresult.go:73-77` vs.
`episode.go:177-181`). Nothing in either type or its JSON tags differs; the evals
copy exists for no structural reason (evals already imports `sidecar` heavily and
uses `sidecar.Report`/`sidecar.RawSDKAudit` directly).

Two converters bridge the copies:

- `convertSidecarTrace` (`trace.go:12-25`) copies sidecar→evals — and **drops
  `Locations`**. It copies `ID, Kind, Title, RawInput, OutputSize, OutputExcerpt`
  and rebuilds `StatusTransitions`, but never assigns `Locations`.
- `hostLiveTraces` (`host_episode.go:296-312`) copies evals→sidecar — and **does**
  copy `Locations` (`host_episode.go:305`).

So a field's survival across the seam depends on the direction of travel. The
`Locations` field was added just this week for ADR-0032.1 S2 (commit
`5aec071`, "populate ToolCallTrace.Locations from ACP tool-call notifications") — it
was added to *both* structs and to the reverse converter, but the forward converter
was missed. **This is the drift the persona exists to find, caught in the act:** a
field added to two hand-maintained copies, one copy path silently not updated.

Consequence, concrete and measurement-adjacent: `Locations` is now
**profile-dependent in committed episode artifacts.** Episodes that run through the
runtime (`sidecar.Ask` → `populateTurnRecord` → `convertSidecarTrace`,
`runner.go:222,290,328-329`) — i.e. the **sidecar profile** — lose `Locations`.
Episodes captured directly by `evalClient` — the **plain/ghx direct profiles**
(`runner.go:344`) and the **host arms** (`host_episode.go:258`) — keep it
(`client.go:155-156`). The same artifact field is populated for some profiles and
empty for others, silently. Today this is *latent* (no recon scorer reads
`Locations`; only the host S2 classifier does, via the direct-capture path that
keeps it), but a committed artifact field whose presence depends on which profile
produced it is a live hazard against Visibility & Truthfulness: "every score
recomputable from committed artifacts" assumes a field means the same thing in
every episode.

**Tie:** Engineering Tenets "Define proper domain models" — *"If a concept appears
in two places, it deserves a type … never plain structs passed around with the
same helper logic hand-rolled at every call site"* (this is the textbook
violation); "No legacy … no dual code paths." Visibility & Truthfulness (silent,
direction-dependent field loss). It also **falsifies ADR-0036's keystone fact**
(`0036-…-runner-port-and-boundaries.md:49-53`), which asserts *"the whole
eval/telemetry stack reads those plain structs — `TurnResult` and `ToolCallTrace`."*
True for `TurnResult` (read directly), **false for `ToolCallTrace`** (read via a
lossy copy). Closing H1 is what makes the target-architecture claim actually true.

**Recommendation:** delete `evals.ToolCallTrace`/`evals.ToolStatusTransition`;
have evals use `sidecar.ToolCallTrace` directly, as it already does for
`sidecar.Report`. JSON tags are identical → episode artifacts are byte-preserving →
**not measurement-touching**. Both converters vanish; the `Locations`-drop bug
becomes structurally impossible. (Phase 1 in the sequence below.)

### H2 — The ACP-notification→trace capture logic is implemented twice and the two disagree on `Locations` semantics

**Severity: High** (but measurement-touching — flag, do not refactor).
`denyClient.SessionUpdate` (`denyclient.go:230-320`) and `evalClient.SessionUpdate`
(`client.go:124-193`) are near-line-for-line parallel implementations of the same
operation: decode an ACP `SessionNotification` into a `ToolCallTrace`, appending
status transitions, sizing output, upserting by tool-call ID. This is the "same
helper logic hand-rolled at each call site" tenet violation one level up from the
type itself — the *capture* is duplicated, not just the struct.

The two capturers **do not agree on the domain rule for `Locations`**:

- Runtime **unions** paths across the tool-call start and every update, deduped and
  order-stable, with a documented rationale (`mergeLocations`, `denyclient.go:140-150`:
  *"we accumulate the union of every path seen for the call rather than replacing"*).
- Evals **replaces** the whole collection on each event
  (`client.go:178-179`: `tr.Locations = locationPaths(tcu.Locations)`, commented
  *"ACP semantics: replace the collection"*).

These are two incompatible authoritative definitions of the same noun ("the set of
paths a tool call touched"). The one that actually reaches a consumer — the
ADR-0032.1 S2 attribution classifier — is the evals *replace* version
(`host_episode.go:273` → `hostLiveTraces` reads the `evalClient`-captured traces).
The runtime *union* version is currently **write-only** (nothing in
`internal/sidecar` reads `tr.Locations`; grep confirms only `denyclient.go` writes
it). So the "canonical-looking" runtime rule is dead for measurement, and the rule
that feeds attribution is the one buried in the eval client. That is groundability
inverted: the authoritative-looking owner is not the one in force.

Two smaller duplications ride along: `appendExcerpt` is **byte-identical** in both
packages (`tooltrace.go:126-136` vs. `client.go:215-225`), and `toolSummary`/
`resolveToolInput` (`tooltrace.go:56-104`) vs. `toolSummary`/`resolvedToolInput`
(`trace.go:34-81`) are near-copies that already differ (the evals variant adds
`strings.TrimSpace` guards and inlines the Title/ID fallback).

**Tie:** Engineering Tenets "Encapsulate domain logic in services / one
authoritative owner"; Visibility & Truthfulness (two definitions of a measurement
input). **Binding constraint:** the `Locations` semantics feed host-task
attribution — reconciling union-vs-replace *changes what committed artifacts
contain* and is therefore measurement-touching. **Flag, do not refactor here.**
Reconciliation belongs behind a pre-registered eval ADR (Phase 2).

**Recommendation:** once H1 lands (one type), extract a single trace-capturer
(builds the `ToolCallTrace` from an ACP update) shared by both clients; the clients
keep their distinct *permission* policies (`denyClient` deny-writes vs. `evalClient`
workspace-write) but stop owning trace-building. The union-vs-replace decision is
made **once, deliberately, pre-registered**, because it is a measurement choice.

### M1 — Evals re-derives the tool-call summaries the runtime already produced, with a different function

**Severity: Medium.** The runtime computes `TurnResult.ToolCalls` (the
human/agent-facing summary strings) via `refreshToolSummaries`→`toolSummary`
(`denyclient.go:152-157`, `tooltrace.go:56`). `populateTurnRecord` copies that
result (`rec.ToolCalls = turn.ToolCalls`, `runner.go:321`) and then **immediately
throws it away and recomputes it** with the evals `toolSummary` via
`rebuildToolSummaries(rec)` (`runner.go:334` → `trace.go:27-32,34`). Because the two
`toolSummary` implementations already differ (M-noted whitespace/fallback handling
in H2), the summary string a human saw stream live can differ from the summary
string persisted and scored for the *same* tool call. This is precisely the lens's
"where does evals re-derive what the runtime already produced" smell — and here the
re-derivation is not even needed: the runtime already computed the authoritative
value and evals discards it.

A narrower sibling: evals re-extracts a command list from traces via
`commandsFromEpisode`/`commandInvokesGhx` (`trace.go:164-277`) for ghx-invocation
attribution, parallel to the runtime's `TraceCommandLedger` (`ledger.go:122`). The
purposes differ (profile attribution vs. ledger evidence), so this is a weaker
instance — noted, not escalated.

**Tie:** Visibility & Truthfulness (live surface vs. scored artifact may disagree
for the same event); Engineering Tenets (one owner). **Recommendation:** after H1,
have evals carry `turn.ToolCalls` through unchanged (the runtime is the owner of
the summary projection), or move `toolSummary` to a single `sidecar` owner both call.
Delete `rebuildToolSummaries`. Serialization-preserving where the two funcs already
agree; where they differ, treat the reconciliation as measurement-touching (the
`ToolCalls` array is a committed artifact field) and pre-register.

### M2 — "A trace is a trace" holds at the writer, forks at the semantic span model

**Severity: Medium (future-facing watch).** The charter's load-bearing NORTH_STAR
claim is that SAF and SAFE share one trace infrastructure. Verified split:

- **Shared (correct):** the OTLP writer/exporter/provider substrate (`telemetry`,
  see verified nulls). One owner, official format.
- **Forked:** the *semantic* span tree and attribute vocabulary. The runtime emits
  spans named `sidecar.ask`/`sidecar.turn` with `ghx.sidecar.*` attributes
  (`emit.go:133,155`, `emit.go:108-112,187-208`). Evals emits an episode→turn→tool
  span tree with `ghx.eval.*` attributes (`otel_trace.go:72,103,123,206`). There is
  no shared turn-span or tool-span builder; the two vocabularies are maintained
  independently. A production-question trace and an eval-episode trace are **not
  the same shape**, so a tool (or a future judge) that understands one does not
  understand the other without translation.

This matters for one specific future: the NORTH_STAR observability tenet
("the judge scorer runs over real sessions, not only benchmark episodes … it only
works if runtime and evals share one trace/eval capability from the start"). That
future needs a *shared span model*, not just a shared writer. **But it is not a
defect today** and the second consumer (continuous eval over production traces,
workstream C6) does not yet exist — extracting a unified span builder now would be
the framework-before-second-consumer move the charter's YAGNI adversary rightly
rejects. And eval spans legitimately carry reward/check attributes a production
span has no business emitting, so *some* divergence is correct, not drift.

**Tie:** NORTH_STAR "Observability is the substrate for self-improvement" / charter
QA #1. **Recommendation:** watch-list only. When C6 (judged production sessions)
becomes real, unify the *shared* subset (turn-span + tool-span shape and the
`ghx.…tool.*` attributes) behind one builder, letting each side add its own
scope-specific attributes. Do nothing now beyond recording the boundary. Any change
to `ghx.eval.*` attributes is measurement-touching and pre-registered regardless.

### L1 — Route provenance is dropped when a runtime turn becomes an eval turn

**Severity: Low.** `TurnResult.Route` (`turnresult.go:23`, `*RouteDecision`, the
ADR-0030.1 D7 noun that "rides back on every response surface so the caller sees
where the answer came from") is **not** carried into `TurnRecord`:
`populateTurnRecord` (`runner.go:316-335`) copies text, thinking, tool traces, RawSDK,
and the report flags, but never `Route`; grep finds no `Route`/`RouteDecision`
reference anywhere in `internal/sidecar/evals`. For today's recon episodes (each
episode owns a single fresh session) routing is arguably irrelevant, which is why
this is Low — but it is the same class of gap as H1/M1: a noun that exists on the
runtime response object is silently not preserved in the eval record. If session
routing ever becomes a scored dimension, its provenance is already absent from the
artifact. **Tie:** Visibility & Truthfulness. **Recommendation:** carry `Route`
onto `TurnRecord` (additive, `omitempty`) as an audit field when H1/M1 are touched;
cheap and non-measurement (no scorer reads it).

## Recommended sequence (phased, non-rewrite, frozen-stack-respecting)

Ordered so each phase is independently landable, and the measurement-touching work
is quarantined behind pre-registration. This is *naming an existing recurring
concept*, not extracting a framework — the second consumer already exists.

- **Phase 0 — Guardrail (immediate, non-measurement, do-nothing-eligible if
  deferred).** Add a `reflect`-based field-parity test asserting `sidecar.ToolCallTrace`
  and `evals.ToolCallTrace` have identical fields, and that `convertSidecarTrace`
  copies every field. This *fails today* on `Locations` — it turns the latent drift
  into a red test and prevents recurrence even if Phase 1 is deferred. No production
  behavior change.

- **Phase 1 — Name the concept once (H1; pure, serialization-identical, NOT
  measurement-touching).** Replace `evals.ToolCallTrace`/`ToolStatusTransition` with
  the `sidecar.*` types (evals already imports `sidecar`). Delete `convertSidecarTrace`
  and `hostLiveTraces`. JSON tags are byte-identical, so every committed episode
  artifact serializes identically — verify with `go test ./...` plus a golden-episode
  round-trip. This alone deletes both converters and the `Locations`-drop bug, and
  makes ADR-0036's keystone fact true.

- **Phase 2 — One capturer, one `Locations` rule (H2 + M1; MEASUREMENT-TOUCHING →
  pre-registered eval ADR).** Extract a single ACP-update→`ToolCallTrace` builder
  shared by `denyClient` and `evalClient` (clients keep their permission policies).
  Decide union-vs-replace for `Locations` and one `toolSummary` deliberately and
  once; record it. Because this changes what some profiles' artifacts contain, it
  must be pre-registered before any run that would quote numbers — this is exactly
  the frozen-measurement-stack rule (AGENTS.md; the compliance-detector precedent).

- **Phase 3 — Watch, do not build (M2).** Record the semantic-span fork in the
  AA-0002 distillation as a C6-gated item. Revisit only when judged-production-session
  eval becomes a real second consumer.

L1 folds into Phase 1/2 as a cheap additive audit field.

## Method / auditability

- **Approach:** read-only. Enumerated the seam nouns from the charter, read each
  type definition and every conversion/capture/consumption site, and diffed the two
  copies field-by-field and comment-by-comment.
- **Primary evidence, re-checkable by anyone:**
  - Duplicate types: `internal/sidecar/turnresult.go:73-94` vs.
    `internal/sidecar/evals/episode.go:177-197` (byte-identical bodies).
  - Lossy forward converter: `internal/sidecar/evals/trace.go:12-25` (no `Locations`);
    lossless reverse: `internal/sidecar/evals/host_episode.go:296-312`.
  - Profile-dependent drop path: `internal/sidecar/evals/runner.go:222,290,316-335`
    (sidecar-`Ask` profiles) vs. direct/host capture `internal/sidecar/evals/client.go:155-156,178-179`.
  - Duplicate capturers & divergent `Locations` semantics: `internal/sidecar/denyclient.go:140-150,230-320`
    (union) vs. `internal/sidecar/evals/client.go:124-193` (replace).
  - Re-derived summaries: `internal/sidecar/evals/runner.go:321,334` +
    `internal/sidecar/evals/trace.go:27-32,34-81`.
  - Semantic span fork: `internal/sidecar/emit.go:133,155` (`sidecar.ask`/`ghx.sidecar.*`)
    vs. `internal/sidecar/evals/otel_trace.go:72,103,123` (`ghx.eval.*`).
  - Shared kernel (nulls): `internal/sidecar/report.go:38`, `internal/sidecar/rawsdk.go:92`,
    `internal/sidecar/telemetry/{provider,trace,logs,metrics}.go`.
  - ADR-0036 keystone tension: `docs/adr/0036-target-architecture-runner-port-and-boundaries.md:49-53`.
- **Grep commands run (representative):**
  `grep -rn "ToolCallTrace" internal/sidecar/evals/*.go`;
  `grep -rn "\.Locations" internal/sidecar internal/sidecar/evals`;
  `grep -rhoE '"ghx\.[a-z_.]+"' internal/sidecar/*.go internal/sidecar/evals/*.go | sort | uniq -c`.
- **Not done (out of scope / respected constraints):** ran no code, changed no
  code, proposed no drive-by change to `internal/sidecar/evals` scoring/gates.
  Phase-2 items are explicitly marked measurement-touching and deferred to
  pre-registration. `internal/ghx` core recon and CLI/MCP frontends read as
  evidence only.
- **Least-confident call:** the severity of M2 (semantic-span fork). It is the
  charter's central claim, and a maximalist read would file it High. I hold it at
  Medium/watch because (a) the fork may be *correct* — an eval trace carrying
  reward/check attributes a production trace must not emit is honest namespacing,
  not drift; (b) the "one trace capability" claim is arguably satisfied by the
  shared *writer* today; and (c) the second consumer that would force unification
  (judged production sessions, C6) does not exist, so acting now would trip the
  charter's own YAGNI guard. If the distillation disagrees, M2 is the finding most
  likely to move — H1/M1 are unambiguous duplication with a live drift bug; M2 is a
  judgment call about when a shared *format* must become a shared *model*.
