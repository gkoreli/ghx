# AA-0002.4 — YAGNI skeptic

> Mandate (charter §"Binding constraints"): *"the mandatory adversary argues
> the inline/do-nothing side; 'do nothing + watch-list' is a valid, first-class
> outcome. Do NOT recommend extracting a framework before a second consumer
> exists."* This artifact is the counterweight. Its job is to stop AA-0002 from
> manufacturing a framework-extraction refactor that competes with the M5 / C4 /
> C7 / C8 frontier and starves the moat (the brain).

## Executive summary — the bottom line first

**The audit's headline question is already answered by shipped code, and the
answer is "genuine shared kernel, already extracted, correctly sized."** The
charter asks (line 30-33) whether the eval↔runtime core is *"a genuine DDD
Shared Kernel … or accidental duplication drifting apart,"* and what should be
*"consolidated/extracted to make the SAF a cleaner reusable boundary — without
extracting a framework before a second consumer proves it."* The honest,
evidence-backed answer:

1. **The shared kernel exists and is right.** `internal/sidecar/telemetry` is a
   small, pure-OTLP substrate with **two real consumers** — the runtime
   (`emit.go`) and evals (`otel_trace.go`) — that *compose on top of it without
   duplicating it*. This is exactly the *"share one trace/artifact
   infrastructure"* NORTH_STAR §"Sidecar Product Capabilities" demands, and M6 /
   ADR-0022 already shipped it. Nothing to do.
2. **The evals→runtime seam is already "depend, not copy" for every large
   type.** Evals reuses `sidecar.Report` (×46), `sidecar.Claim` (×17),
   `sidecar.RawSDKAudit` (×16), `sidecar.Ask`, `sidecar.BuildPrompt`,
   `sidecar.LoadConfig`, `sidecar.RunPreflightForAgent`, `sidecar.ContentSize`,
   `sidecar.ToolOutputText`. The dependency graph is a clean **layered
   hierarchy** — `telemetry ← sidecar ← evals` — not "two copies drifting apart."
3. **There is exactly ONE genuine duplication**, and it is tiny (~30 LOC): the
   `ToolCallTrace` / `ToolStatusTransition` struct pair is defined in both
   `turnresult.go` and `episode.go`, bridged by `convertSidecarTrace`. It is
   **measurement-artifact-touching** (it serializes into `episode.json` and feeds
   Locations-based scoring), so it is a pre-registered-eval-ADR item, **not** a
   drive-by refactor and **not** evidence for a framework boundary. Watch-list.

**Recommended output of AA-0002: do nothing structural + a 3-item watch-list.**
Any proposal to mint a `pkg/saf` / lift the SAF out of `internal/`, or to merge
the eval/runtime span-composition into a second "trace kernel," should be
**rejected** as speculative generality that (a) has no second consumer, (b)
risks the frozen measurement stack, and (c) directly violates NORTH_STAR line
102 (*"The framework will outgrow ghx — later"*) and line 261 (*a consequence
product *"only gets investment when the north-star filter passes and the ghx
frontier milestone is not starved by it"*). The whole SAF-as-infra sub-question
of this charter is, today, a **treadmill risk against the moat**
(NORTH_STAR line 78: *"The moat is the agentic brain, not the tools"*).

## What is already right (do not touch)

These are load-bearing "leave it alone" findings — the strongest evidence that
the extraction thesis is answering a question that shipped code already closed.

- **`telemetry` is the real, correctly-sized DDD Shared Kernel.** It exports
  only OTLP primitives: `NewTracerProvider` (`telemetry/provider.go:22`),
  `NewTraceExporter` + `TraceFileName` (`telemetry/trace.go:41,50`), `WriteLogs`
  + `LogRecord` (`telemetry/logs.go:18,29`), `WriteMetrics` / `HistogramMetric` /
  `AppendAttrs` (`telemetry/metrics.go:17,43,94`). Total package: 1,188 LOC incl.
  tests. **Two consumers, verified:** the runtime composes turn spans on it
  (`emit.go:120,148,154,407`) and evals composes episode spans on it
  (`evals/otel_trace.go:36,51,72`). Neither duplicates the OTLP encoding; each
  owns only its *domain* attribute/span shape. This is the textbook
  substrate-plus-composition layering. Tie: NORTH_STAR §"Sidecar Product
  Capabilities" / Open-Source-Leverage tenet ("official formats exactly").
  **Status: shipped (M6 / ADR-0022). No action.**

- **The big eval↔runtime types are shared by dependency, not copied.** The
  frozen gates literally score a runtime-owned type: `evals/rewards.go:88
  scoringReport(ep *Episode) *sidecar.Report`. `Episode` embeds
  `Report *sidecar.Report` (`episode.go:148,273`) and `RawSDK
  *sidecar.RawSDKAudit` (`episode.go:146`). This is "depend, don't copy" already
  applied to precisely the types a naïve duplication scan would flag. Tie:
  charter §"Ranked quality attributes" #2 (copy vs depend vs name) — the repo
  already chose *depend* for the expensive types.

- **The two suspected runtime→evals couplings are false positives.**
  `tier2/clone.go`'s "evals" hit is a **comment** (`clone.go:104`), not an
  import. The only real runtime-tree→evals edge is a **frontend** wiring the SFT
  export (`internal/cli/sidecar.go:213 evals.ExportSFT`) — the ADR-0010
  "frontends wrap the core" pattern, not a kernel coupling. Evals ← runtime is
  one-directional and clean.

- **It compiles as one coherent tree today.** `go build ./internal/sidecar/...`
  → exit 0. There is no build-level pressure forcing a split.

## Findings, by severity of the *risk the audit introduces*

For an adversarial YAGNI persona, "severity" is the severity of the harm a
proposed extraction would cause. Highest = the extraction most likely to be
proposed and most damaging; lowest = the one real (small) thing worth watching.

### S1 (Critical) — reject any `pkg/saf` / framework-lift proposal outright

**Target (steelmanned):** the reusable-core lead (AA-0002.1) and the charter's
own §"Replaceability / framework-extractability" will argue the SAF should be
lifted toward reusable infra — a `pkg/saf`, an exported runtime module, a
"framework boundary" — so *"the SAF boundary could be lifted toward reusable
infra without a rewrite."*

**Flaw:** there is **exactly one product**. Zero second consumers. `grep`
confirms a single `Runner` implementation exists —
`acprunner.go:23 _ Runner = (*claudeACPRunner)(nil)` — and *no* second
implementer anywhere, not even a test mock. Extracting a framework now is
textbook speculative generality:

- It is **explicitly forbidden by the charter** (line 63: *"Do NOT recommend
  extracting a framework before a second consumer exists"*) and by the very
  question it poses (line 33: *"without extracting a framework before a second
  consumer proves it"*).
- It contradicts the durable steer: NORTH_STAR line 102 (*"The framework will
  outgrow ghx — **later**"*) and line 261 (a consequence product *"only gets
  investment when the north-star filter passes and the ghx frontier milestone is
  **not starved** by it"*). The Agent Sidecar Framework is a **mental model and a
  consequence product** (NORTH_STAR §"Consequence Products"), not a package to
  mint in July 2026.
- It fails the **north-star filter** (NORTH_STAR §"The North-Star Filter"): a
  `pkg/saf` extraction removes zero tokens from the main agent's context, makes
  reconnaissance neither cheaper nor more proficient, adds no auditability, and
  produces no training trajectory. All four gates fail → *reject or defer*.
- It **competes with the live frontier.** The open frontier is M5 / B2
  (zero-CLI ergonomics, dogfood week), C4 (judge κ calibration), C7 (trust
  ledger to green), C8 (host-task combined-objective). A framework refactor
  spends the exact review/merge budget those need, for a benefit that
  materializes only if a hypothetical second brain ever ships. Tie: NORTH_STAR
  line 78 (*"the moat is the agentic brain, not the tools"*) — a framework is
  *tools*; refactoring it is the cheapest-to-replicate, least-defensible work in
  the repo.

**Verdict: do nothing. The SAF already lives cleanly in `internal/sidecar`;
`internal/` is exactly where an unexported, single-product runtime belongs.**
The moment a second consumer is real (a second brain, or an external adopter
with a signed reason), a *mechanical* package promotion from `internal/sidecar`
to `pkg/…` is a day's work — Go makes this a rename, not a rewrite. Paying that
cost now buys nothing and freezes an API surface against a consumer that does
not exist.

### S2 (High) — do not merge the span-composition into a second "trace kernel"

**Target (steelmanned):** a persona notices `evals/otel_trace.go` and
`sidecar/emit.go` *both* build OTLP spans and proposes unifying the
span/attribute construction into a shared "trace kernel" above `telemetry`.

**Flaw:** the shared *primitive* is already `telemetry`; what remains is
**domain-specific composition that must stay separate**:

- `emit.go` builds **sidecar-turn** spans/metrics/logs keyed to runtime
  concepts (routes, wrap-up recovery, session recreation — `emit.go:154,181,330`).
- `evals/otel_trace.go` builds **episode** spans keyed to eval concepts
  (turns → tools → **rewards**: `emitTurnSpan`/`emitToolSpan`/`emitRewardSpan`,
  `otel_trace.go:103,123,138`; `episodeAttributes`/`rewardAttributes`).

Merging these forces the eval `Episode` / `RewardBreakdown` schema
(`episode.go:232,255`) and the runtime `TurnResult` schema (`turnresult.go:6`)
through one code path. That **couples the frozen measurement stack to runtime
refactors**: a change to how the runtime emits a turn span would ripple into how
episodes (and their reward attributes) serialize. Charter §"Binding
constraints" line 57 makes this out of bounds — *"any evals-reachable change is
measurement-touching → pre-registered eval ADR."* The current split is not
duplication; it is the correct application of *copy-vs-name*: shared substrate
(`telemetry`), separately named domain composers. Metz applies exactly here —
"duplication is far cheaper than the wrong abstraction," and a forced
turn/episode span abstraction is the wrong one. **Verdict: do nothing.**

### S3 (Medium) — the Runner port is a one-implementation boundary; freeze it, don't multiply it

**Target:** ADR-0036's `Runner` port (`runner.go:27`, a 275-line surface:
`Runner`, `Session`, `TurnRequest`, `SteeringSpec`, `Isolation`, `ToolPolicy`,
`Outcome`, `FailureClass`, `EventSink`, …). The charter cites it approvingly as
*"one config-selectable reusable boundary"* and the lead will use it as the
template for *more* ports.

**Flaw (a caution, not an action):** this port has **one implementation** —
`claudeACPRunner` (`acprunner.go:23`) — and no second, not even a mock. It is
already carrying its full abstraction cost (an interface + five satellite
types + a marker enum) while earning only the single-consumer benefit of
decoupling the ACP adapter. I am **not** relitigating a shipped ADR — the port
may be justified as pre-wiring for the P4 model swap. But it is concrete proof
that **this repo already has an appetite for ports-before-second-consumers**,
which is precisely the pattern this audit must not feed. **Verdict: freeze the
count of speculative boundaries at exactly one. AA-0002 must not add a second.**
If anything, the port is the ceiling of acceptable speculative generality here,
not a pattern to replicate.

### S4 (Low, but real) — the one honest duplication: `ToolCallTrace` / `ToolStatusTransition`

This is where a red-team that only cries wolf would be useless, so I concede it
plainly: **there is a genuine, small duplication.**

- `ToolCallTrace` + `ToolStatusTransition` are defined **byte-identically** in
  the runtime (`turnresult.go:73-77,79-94`) and in evals
  (`episode.go:177-181,183-197`) — same six fields, same JSON tags, and the
  **same copy-pasted ADR-0032.1 `Locations` doc comment**. They are hand-synced:
  when `Locations` was added, both copies were edited.
- A field-by-field bridge exists both ways: `evals/trace.go:12
  convertSidecarTrace(in sidecar.ToolCallTrace) ToolCallTrace` (called at
  `runner.go:329,332`) and the reverse `host_episode.go:296 hostLiveTraces(...)
  []sidecar.ToolCallTrace` (`host_episode.go:300,305`). That is ~30 LOC of
  definition + two conversion functions maintaining two identical shapes.
- **Concrete smell:** `convertSidecarTrace` copies six fields + `StatusTransitions`
  but **drops `Locations`** (`trace.go:12-25`). The runtime *just started*
  populating `Locations` (ADR-0032.1 S2), so on the sidecar-profile episode path
  it is silently lost, while the eval harness's *own* ACP client populates it
  natively (`client.go:155-156,178-179`) and host episodes carry it
  (`host_episode.go:305`). This is either intentional (Locations is a host-arm /
  attribution concern, not needed for standard episodes) **or** a latent drift
  bug — and *"which one?"* being non-obvious is itself the maintenance tax of two
  parallel structs.

**But the honest scope is small, and it argues for a targeted fix, not a
kernel.** Two facts bound it:

1. The types reflect a **real two-capture-site boundary**, not laziness: the
   runtime captures traces through `sidecar.Ask`; the eval harness captures its
   *own* traces via `evalClient` for the direct/plain baseline profiles that
   **bypass the runtime entirely** (`client.go:42 upsertTrace`, `:52`,
   `:155`). Two independent producers is a legitimate reason two owners exist —
   "a little duplication is better than a little dependency" is defensible here.
2. **It is measurement-touching.** The evals `ToolCallTrace` serializes into the
   canonical `episode.json` (`episode.go:130` `ToolTraces []ToolCallTrace`) and
   its `Locations` feed the host-arm write policy and attribution classifier
   (ADR-0032.1). Per charter line 57 and AGENTS.md §"Visibility and Truthfulness"
   (*"The measurement stack is frozen during a run… must be pre-registered in an
   ADR"*), unifying it **cannot** be a drive-by; it needs a pre-registered eval
   ADR that also settles the `Locations`-drop question.

**Verdict: watch-list, eval-ADR-gated, opportunistic.** If AA-0002.5's metrics
show this duplication has already caused a scoring drift, the dedup wins its
ADR. Absent that, it is ~30 LOC that is not worth a dedicated refactor and is
*certainly* not evidence for a framework boundary. **Do not let this tiny wart
be laundered into a "shared kernel extraction" narrative** — it is the opposite:
a case study in why the existing depend-and-convert seam is already fine.

## Where the audit itself is the risk

The charter's trigger (line 15-25) is honest that this run is partly motivated
by the *framework half of the vision needing "a real reusable boundary, not an
aspiration."* That motivation is the hazard. NORTH_STAR is emphatic that the
framework is **later** and the moat is the **brain**. An architecture audit that
converges on "extract the SAF" would:

- convert a *consequence product* (NORTH_STAR §"Consequence Products") into
  present-tense engineering it explicitly forbids until the north-star filter
  passes and the frontier is unstarved (line 261);
- spend the scarce serial merge/review budget (the one true bottleneck in the
  fleet model, per CLAUDE.md §"Delegation Model") on tool-shaped work that "the
  moat is the brain" says is the least defensible in the repo;
- **increase** the minimal-legible-edit-unit for the common case: today, a
  sidecar change is one edit in `internal/sidecar`; after a `pkg/saf` split it is
  an edit + an exported-API review + a consumer-update, for a consumer set of
  size one. That is a *higher* context tax, the exact opposite of charter
  §"Ranked quality attributes" #2.

Naming it directly, as the mandate requires: **the SAF-as-infra half of this
charter is a treadmill against the brain, and its correct 2026-07-07 output is
"not yet — watch-list."**

## Recommended sequence — do nothing structural + watch-list

1. **Record the answer to the charter question and close the extraction thread:**
   the eval↔runtime core is a *genuine shared kernel* (`telemetry`) plus a
   *clean depend-not-copy layering* (`evals → sidecar`). It is **not** accidental
   duplication drifting apart. No consolidation or extraction is warranted now.
2. **Do not mint any new reusable boundary.** No `pkg/saf`, no framework lift,
   no second port, no merged trace kernel. Freeze speculative boundaries at the
   one that already exists (`Runner`).
3. **Watch-list (revisit only when a trigger fires):**
   - **W1 — second consumer appears.** A real second brain/domain, or an external
     adopter with a signed reason, is the *only* trigger to promote
     `internal/sidecar` → `pkg/…`. Until then, the promotion is a mechanical
     rename deferred at zero cost.
   - **W2 — `ToolCallTrace` drift bites.** If AA-0002.5 (or a live run) shows the
     duplicated struct / `convertSidecarTrace` `Locations`-drop caused a scoring
     or artifact-schema divergence, open a **pre-registered eval ADR** to (a)
     resolve the `Locations` question and (b) decide unify-vs-keep — a ~30-LOC
     change, not a kernel.
   - **W3 — `telemetry` starts sprouting domain logic.** If eval- or
     runtime-specific concepts leak *into* the `telemetry` package (reward
     attributes, route semantics), that is the shared kernel eroding — pull them
     back out into the domain composers. Today it is clean; keep it clean.

### Least-confident call

**S4 — whether the `ToolCallTrace` duplication should be unified at all.** The
case is genuinely balanced: evals already depends on `internal/sidecar` and
already embeds a runtime-owned `sidecar.Report` in its *scored* artifact
(`rewards.go:88`), which weakens the "insulate the measurement schema from the
runtime" argument for keeping a separate `ToolCallTrace` — a careful unification
(have `client.go` build `sidecar.ToolCallTrace` directly, delete
`convertSidecarTrace`) is plausibly *safe* and removes a lossy conversion. I
land on **watch-list / eval-ADR-gated** rather than "do it now" because (a) the
two-capture-site boundary is real, (b) it is measurement-touching and cannot be
a drive-by, and (c) the payoff (~30 LOC) is too small to risk the frozen stack
without a triggering drift. AA-0002.5's duplication metrics are the tie-breaker;
I defer to them on W2 specifically. Everything in S1–S3 I hold with high
confidence.
