# Competitive-Paranoid (generative) — absorb `codebase-memory-mcp`?

**Persona posture (binding):** competition never means retreat. Per `AGENTS.md`
*"Competitive analysis is generative, not defensive … the question a competitor
raises is never 'do we back down' but 'what — from one idea to the whole thing —
do we take, and where does it plug in.'"* This is Grove's *Only the Paranoid
Survive* pointed **outward as acquisition**, not inward as fear.

## Verdict

**ABSORB-PARTS** — and the headline "part" is large: swallow the **whole engine
as an optional tier-2 backend binary** the sidecar shells out to (this *is*
"swallow the tool" in the exact P3/M7 sense), but **NOT** as a source-fork into
ghx's Go tree, and **explicitly reject** its in-context PreToolUse distribution
hook (which inverts the "context is sacred" tenet). One line: *its knowledge
graph is the deepest structural signal-per-token engine in the verified OSS set
and slots into the `ghx tier2` backend registry unchanged; its brain-less,
local-only, quality-trading design is exactly the commodity tool layer the
north star says the sidecar brain swallows — so we take the engine, gate it with
the brain, and win on the two things it structurally cannot do (remote/GitHub-
wide discovery + persisted audit-designed evidence).*

This **sharpens** PA-0001.7 A1 (which proposed a `ghx tier2 graph` backend) with
three deltas it did not have: (1) the plug-in mechanism is now **confirmed to
already exist and match** (`ghx tier2 <tool>`, backend `local:<tool>`, blobless
SHA-cached snapshot); (2) the target ships a **CLI mode** (`codebase-memory-mcp
cli <tool> <json>`) so it absorbs as a shell-out binary like codemap — **no MCP
dependency, no source fork required**; (3) the honest **83%-vs-92% quality
tradeoff** and the **anti-absorb distribution hook** are new counter-evidence
that bound the absorption.

## Top 3 absorption candidates (ranked)

1. **The whole tree-sitter + Hybrid-LSP knowledge-graph engine → `ghx tier2
   graph` (backend `local:codebase-memory-mcp`).** Deepest structural signal per
   token in the set: call chains, cross-service HTTP/gRPC/GraphQL linking, impact
   analysis, Cypher queries, dead-code — beyond codemap/aider-repomap. Anchor:
   <https://github.com/DeusData/codebase-memory-mcp/blob/main/internal/cbm/lsp/ts_lsp.c>
   (the from-scratch C Hybrid-LSP resolver — the hard, novel core).
2. **The team-shared graph artifact idea →** `~/.ghx/cache/tier2` + M8
   anticipation. A zstd-compressed `.codebase-memory/graph.db.zst` committed next
   to source, decompressed on clone, incremental-filled — a clever cross-machine
   cache-warm. Anchor:
   <https://github.com/DeusData/codebase-memory-mcp/blob/main/README.md> ("Team-

3. **One-command host auto-install idea → M5/B2 zero-CLI adoption.** `install`
   auto-wires MCP entries across 11 agents. Take the *host-wiring onboarding*;
   **do not** take the in-context Grep/Glob injection hook. Anchor:
   <https://github.com/DeusData/codebase-memory-mcp/blob/main/src/cli/hook_augment.c>.

## 1. What it is (dogfooded)

`DeusData/codebase-memory-mcp` — a **persistent code knowledge-graph MCP server**
in **pure C**, single static binary, that indexes a *local* codebase into a
tree-sitter + Hybrid-LSP graph and answers structural queries over it.

**Maturity (2026-07-07, `gh api`):** **27,884★**, 2,074 forks, **264,405 release
downloads**, created **2026-02-24** (~4.5 months old), MIT, active
(`pushed 2026-07-07`), 204 open issues, latest release `v0.8.1`. Explosive
growth curve — a category-defining velocity.

**The decisive design fact (their own README, `ghx read … README.md`):**

> **"codebase-memory-mcp is a structural analysis backend … It does **not**
> include an LLM. Instead, it relies on your MCP client (Claude Code, or any
> MCP-compatible agent) to be the intelligence layer."**

That single sentence is the whole absorption thesis: **they built a tool; ghx is
building a brain.** They *outsource* the intelligence layer to the host agent;
ghx's north star is to *be* that layer (the sidecar) and make the tools
disappear beneath it. Their tool is precisely what NORTH_STAR P3 calls a
"tiny building block the sidecar swallows."

**What the engine gives you** (README "Features" + `docs/llms.txt`, dogfooded):
14 MCP tools — `index_repository`, `index_status`, `list_projects`,
`delete_project`, `search_graph`, `search_code`, `trace_path`, `detect_changes`,
`query_graph` (Cypher), `get_architecture`, `get_code_snippet`, `manage_adr`,
`semantic_query` (bundled `nomic-embed-code`, 768-dim, no API key), and more;
158 vendored tree-sitter grammars; **Hybrid LSP** type resolution in C for 9
language families; cross-service HTTP/gRPC/GraphQL/tRPC linking; Louvain
community detection; `SIMILAR_TO` (MinHash+LSH) and `SEMANTICALLY_RELATED` edges.

**What it is NOT** (confirmed by dogfood — this is the ghx-defensible residue):
- **No brain / no LLM** — verbatim above.
- **No remote / GitHub-wide capability.** `ghx grep … "git clone"` and
  `"github.com/repos"` show git-clone only in *vendor/setup scripts* and the only
  GitHub-API call is a background release-update check (`SECURITY.md`). Indexing
  is strictly local over a `repo_path`. It is a **P3/M7 escalation tier by
  construction**, never a P1/P2 remote path.
- **No persisted, audit-designed evidence report** — it returns query JSON to
  the host; there is no ghx-style compact evidence report with backends +
  uncertainty + session artifacts.
- **Lower answer quality than file reading.** Its own arXiv abstract
  (2603.27277): *"achieves **83% answer quality versus 92% for a file-
  exploration agent**, at ten times fewer tokens and 2.1 times fewer tool
  calls."* It trades quality for tokens — honest, and load-bearing (see §3).

## 2. The threat (competitive-paranoid — narrow AND holistic)

**Narrow (is this a real threat?): yes, on distribution and mindshare.** It ships
**ghx's exact signals-per-token pitch** (README: *"120x fewer tokens"*), an
**arXiv benchmark** (the "consequence product" ghx *planned* but has not
published), **and** the **distribution Power ghx lacks** (auto-installs into 11
agents including Claude Code), all at once, at 27.9k★ in 4.5 months. Persona
signature question — *"what would let a competitor make this product irrelevant
in 12 months?"* — has a concrete answer here: **if it bolts on (a) remote/GitHub-
wide discovery and (b) any routing brain, it becomes ghx.** Both are within
reach: it already has cross-repo `CROSS_*` edges and a background watcher.

**Holistic (does the threat reach the *defensible* layer?): no.** The moat is
`NORTH_STAR.md:78` — *"The moat is the agentic brain, not the tools. CLI tools,
frameworks, and ergonomics are reusable, replaceable building blocks that anyone
can replicate."* Everything codebase-memory-mcp does is in the **tool layer the
north star explicitly cedes as commodity**. It has *declared* it has no brain.
So the paranoia resolves generatively: the strongest rival is also the strongest
absorption target — its engine becomes a tier-2 building block, and ghx competes
where it is blind (remote-first, GitHub-wide discovery, persisted evidence). The
DRAM-moment self-check (persona): the stale belief to *avoid* is "our CLI tools
are the product." They are not; the brain is. This competitor **proves** that by
being brain-less and still 27.9k★.

**One genuine strategic warning (track, don't panic):** it is **setting the
category's public numbers first.** An arXiv preprint (Vogel et al., submitted
2026-03-28) + a reproducible PASS/PARTIAL/FAIL benchmark exist *now*; ghx's SAFE
benchmark is a Consequence Product that is **not yet published**. Whoever
publishes the citable recon benchmark frames the category. This is a "why now"
for SAFE, not a reason to retreat.

## 3. Absorption map: idea → utility → feature → whole-tool

Each rung: *what to take · where it plugs in · north-star filter*. The filter
(NORTH_STAR): *removes tokens/knowledge from the main agent's context ·
cheaper/more-proficient recon · more auditable evidence · better training
trajectories.*

| Rung | What to take | Where it plugs in | North-star filter |
|---|---|---|---|
| **Whole-tool** | The **engine binary** (tree-sitter + Hybrid-LSP graph, 14 tools, Cypher, semantic search) as an **optional tier-2 backend** invoked via its **CLI mode** (`codebase-memory-mcp cli search_graph '{…}'`) | **`ghx tier2 graph`, backend `local:codebase-memory-mcp`** — a 4th sibling beside the existing `local:ast-grep` / `local:codemap` / `local:repomap`. `ghx tier2` already "materializes a read-only snapshot under `~/.ghx/cache/tier2` … and runs absorbed structural tools over it" (verbatim `ghx tier2 --help`). Sidecar decides to escalate; provenance printed; fully traced. | **PASSES** — deepest structural signal per token; sidecar brain gates *when* the graph beats file-reading (recall: graph-native queries match/exceed on 19/31 langs; else file-read wins) |
| **Feature** | The **team-shared graph artifact** (`.codebase-memory/graph.db.zst`, zstd two-tier, decompress-on-clone, incremental fill, `merge=ours` to avoid conflicts) | ghx's `~/.ghx/cache/tier2` (already SHA-keyed) + **M8 anticipation** — a committed/warm graph is a prefetched artifact; answers land sub-second because the index already exists | **PASSES** — cheaper/faster recon + reusable artifact; nudges the stalled M8 prefetch gate |
| **Utility/mechanic** | **One-command host auto-install** (`install` auto-detects 11 agents, writes MCP entries) | **M5/B2** "one-command setup, zero-CLI adoption" for `ghx serve` — contests the distribution lever instead of ceding it | **PASSES as onboarding** — reduces the operator setup tax (the FRICTION.md M5 gap) |
| **Idea** | **Bundled on-device embeddings** (`nomic-embed-code`, 768-dim, compiled in — no API key/Ollama/Docker) for semantic name→code discovery | A future `local:` semantic tier under tier-2 — *evidence that local semantic search needs no service*, informing (not forcing) ghx's discovery substrate | **PASSES** — more-proficient recon with zero added service dependency |
| **Idea** | **The arXiv benchmark + deterministic PASS/PARTIAL/FAIL methodology, and its honesty** (lead with 83%-vs-92%, not only "99% fewer tokens") | **SAFE (Consequence Product)** — a template for ghx's own published recon benchmark, on the axes their local indexer can't score (remote-first, GitHub-wide discovery, persisted evidence) | **PASSES as positioning/validation** — "why now" to publish SAFE; a lesson in honest quality framing |

**Anti-absorb (a rung we must NOT take):** the **in-context PreToolUse hook**
(`hook_augment.c`) that *"injects matching graph symbols as `additionalContext`"*
into every Grep/Glob the main agent runs. That is the **exact inversion of the
north star**: it *adds* structured context **into the main agent's window** on
every search, whereas ghx's whole thesis is to *subtract* recon from that window
by delegating to a sidecar. Absorbing this mechanic would pull ghx toward the
"augment the main agent's context" model NORTH_STAR rejects ("The main agent's
context is sacred"). Take their *host-wiring* onboarding; leave the injection
hook. DH6: their hook is a *good design for a brain-less tool* (make the agent
never learn a new tool) — but it is a **strategic misfit** for a product whose
value is delegation, not injection.

## 4. What argues AGAINST absorbing (nulls / counter-case — equal rigor)

The persona's own blind spot is thrash — chasing every shiny threat. Held
honestly:

1. **"Absorb entirely" as a *source-fork* is a trap, not a win.** It is ~40k+
   lines of **security-sensitive pure C** (reads code, writes agent config; 204
   open issues; 5,604 tests), 158 vendored grammars with **mixed permissive
   licenses** (mostly MIT, some CC0/Apache-2.0/ISC per `THIRD_PARTY.md`). ghx is
   **Go**. Forking that into ghx's tree violates the Engineering Tenets ("no
   legacy maintenance … refactor cleanly or not at all") and inverts the OSS
   filter ("hand-roll only when nothing serves") into "adopt an enormous foreign
   surface." **Only the shell-out-to-binary reading survives** — which is why the
   verdict is absorb-parts, not absorb-entirely-into-the-codebase.
2. **Lower answer quality (83% vs 92%) means it cannot be a default.** If the
   sidecar naively routed all recon to the graph, exploration answer quality
   would *drop*. The north star wants "better answers AND cheaper," not "cheaper
   at the cost of answers." This is an argument **FOR the brain** (selective
   escalation) and **AGAINST** a blind swallow — the graph is a scalpel, not the
   default hammer.
3. **It's local-index-only, so the absorption is bounded to the escalation
   tier.** It cannot touch ghx's remote-first P1/P2 differentiator; "absorb
   entirely" can never mean "make it the product." It's a P3/M7 add, no more.
4. **ADR-0024 already picked codemap/ast-grep/repomap.** Adding a heavy C engine
   is not free. The honest generative move is a **tier-2 backend bake-off** —
   benchmark `local:codebase-memory-mcp` against the incumbents on the M7 tasks
   and let evals decide, per "evidence, not vibes." Do **not** commit sight-
   unseen. Route: **extend ADR-0024**, don't blind-merge.
5. **Supply-chain trust.** Shelling to an external prebuilt binary that reads
   source and writes config puts a third party in ghx's trust boundary. Pin a
   version, verify checksums/SLSA-3, sandbox invocation — or build from their
   MIT source in CI. Non-trivial, must be designed.

## 6. Was ghx usable for the recon? (dogfood log + friction)

**ghx was highly usable** — `explore`, `read` (line ranges), `grep` (repo-wide),
and `tree` (with `--depth`) verified every load-bearing in-repo fact for E1–E5,
E7–E9 with no `gh` fallback. Commands run:

| # | Command | Result |
|---|---|---|
| 1 | `ghx explore DeusData/codebase-memory-mcp` | ✓ Branch/tree/README in one call — surfaced 158-langs, 14 tools, arXiv, "99% fewer tokens" |
| 2 | `ghx read … README.md --lines 220-360` | ✓ "does not include an LLM" + team-shared graph artifact + perf table (E1) |
| 3 | `ghx grep … "git clone"` / `"github.com/repos"` | ✓ Confirmed local-index-only / no remote recon (E2) |
| 4 | `ghx tree … --depth 2` | ✓ src/{cli,cypher,semantic,pipeline,store,…} + internal/cbm layout |
| 5 | `ghx read … src/cli/hook_augment.c --lines 1-70` | ✓ The PreToolUse injection mechanic verbatim (E7) |
| 6 | `ghx read … docs/llms.txt` / `docs/BENCHMARK.md` | ✓ 9 LSP families, embeddings, 12-question PASS/PARTIAL/FAIL method (E5, E6) |
| 7 | `ghx grep … "Hybrid LSP"` | ✓ Located `internal/cbm/lsp/ts_lsp.c` — the hard novel core (E5) |

**Top friction (2, both real):**
1. **`ghx tree --path src` failed** — `"unknown flag --path; use --depth"`. The
   correct grammar is the **positional** `ghx tree <repo> [path]`. A natural
   desire-path (the `--path` muscle-memory from other tools) hits a hard error
   before `--help` reveals the positional form. Low severity, but a named
   *frictionax* desire-path: agents will type `--path`. Class:
   *unclear_interface*. Suggest accepting `--path` as an alias or naming it in
   the error.
2. **ghx cannot reach non-GitHub docs** — the arXiv abstract (E6, the single most
   decision-relevant external number, 83% vs 92%) required `WebFetch`, and
   maturity stats/download counts used `gh api`. Same scope-edge PA-0001.7
   logged; re-confirmed. Not a defect — a logged scope boundary: the recon's most
   load-bearing external fact lives outside ghx's GitHub-only reach.

## 7. Least-confident call

**Whether the graph engine actually *beats* the incumbent tier-2 backends
(codemap/ast-grep/repomap) enough to justify a heavy C binary in ghx's supply
chain.** The capability is clearly deeper (LSP type resolution, cross-service
linking, Cypher), and its own arXiv shows graph-native queries match/exceed
file-exploration on **only 19 of 31** languages — i.e. the win is real but
**partial and language-dependent**, and answer quality is *lower* overall (83 vs
92). Without ghx's own tier-2 bake-off eval, "it's the best backend" is a
hypothesis, not a finding. **Route: extend ADR-0024 with a tier-2 backend
comparison before merging `local:codebase-memory-mcp`.** This finding — that the
strongest rival should be swallowed as a tier-2 backend — is **self-verified
only**; per the product-audit self-preference guard it needs the orchestrator's
independent (ideally cross-family) adjudication before it is milestone-citable.
