## Abstract

I audited ghx as its primary consumer — an AI agent — using the AX signature test:
*"If a fresh agent had only this tool's name, description, and one error message,
could it do the job and know it succeeded?"* On the **recon path** the answer is a
strong yes: a live `ghx sidecar ask` returned in 38 s, exit 0, with an accurate
answer whose every verified claim cited the exact `ghx read --lines` command, plus
a durable artifacts pointer — HIC 0, false_errors 0, goal_reached yes. That path is
the north star working.

The problem is that **the product's own defaults route the agent away from that path.**
Every default distribution surface — `ghx skill`, `ghx serve`, and the
`.claude-plugin/plugin.json` manifest / README install commands — ships the
high-context-tax power-user layer (232-line CLI skill ≈ 3,900 tokens; 7 MCP tools),
while the ≈460-token recon skill and single `recon` tool are opt-in behind flags the
agent must already know to pass. For a product whose headline claim is *"the main
agent needs zero ghx knowledge,"* the default install adds the exact context the
product exists to subtract. That is the top finding. Below it: a confirmed exit-code
false-success (`read` of a nonexistent repo returns exit 0), the highest
signal-per-token command (`inspect`) missing from all doctrine surfaces, and two
report-contract gaps (no "un-verified" elevation; no repo qualifier on cited paths)
that pinch the trust and compose pillars.

Sources: 6 external (persona Source Ledger, all deep-verified in artifact 06) + the
repo's own NORTH_STAR, FRICTION.md dogfood log, plugin manifest, and a live dogfood
run.

## Ranked findings

### F1 — The default distribution surfaces invert the north star (max doctrine, not zero)

- **Persona · Scope · Surface:** AX (#16) · Context-budget / progressive-disclosure + Distribution-in-agent-ecosystems · `.claude-plugin/plugin.json`, `ghx skill`, `ghx serve`, README install commands.
- **Evidence (re-derived live):**
  - `.claude-plugin/plugin.json` lists `"skills": ["./skills/ghx", "./skills/ghx-mcp"]` — the two power-user skills. `./skills/ghx-recon` (the north-star surface) **is not in the manifest.**
  - README:551 documents `npx skills add … --skill ghx` and `--skill ghx-mcp`; there is **no documented install of `ghx-recon`.**
  - `ghx skill` (no flag) prints the 232-line CLI skill (`wc`: 232 lines / 15,626 chars ≈ **3,900 tokens**). The recon skill (`ghx skill --recon`) is 47 lines / 1,840 chars ≈ **460 tokens** — 8.5× less — but requires knowing the `--recon` flag.
  - `ghx serve` (no flag) registers 7 tools (`internal/cli/serve.go:146-152`: explore/read/search/repos/tree/search_tools/code). The single `recon` tool (`serve.go:163`) requires `--recon`.
- **Severity:** Likelihood **High** × Impact **Medium** → **Escalate now** (High). It is the literal shipped default on three independent surfaces (High likelihood); it is a fixable packaging defect, not a thesis invalidation (Medium impact) — but it undercuts the headline claim *at the point of adoption*.
- **Who judged it & how to check:** Re-derived from `plugin.json`, README:550-551, `wc -l` on the three skills, and `serve.go:146-163`. A reader reruns `cat .claude-plugin/plugin.json`, `ghx skill | wc -l`, `ghx skill --recon | wc -l`. Recommend one independent cross-family confirmation (Codex read-only) before it feeds a milestone decision, per the self-preference guard.
- **North-star relationship:** **Fails the filter's first clause.** NORTH_STAR: *"a main agent … needs zero knowledge of the ghx CLI — it never loads the ghx skill file at all"* and *"The outside world knows only a very concise skill."* The product's own default distribution installs precisely the skill file the north star wants gone. The prose intent is right (README leads with the sidecar; calls recon *"recommended for agents"*), but an agent consumes the manifest and `ghx skill`, not the README's prose.
- **Disposition:** Needs work → **workstream B2** ("Zero-CLI adoption surface"). Concrete moves to weigh (not prescribing the fix): add `./skills/ghx-recon` to `plugin.json` (or make it the primary), and/or make `ghx skill` default to the recon skill with `--cli`/`--mcp` as the opt-ins, inverting today's default so the low-tax path is the one an uninformed agent lands on.
- **Cross-reference:** Anthropic, *Code execution with MCP* — https://www.anthropic.com/engineering/code-execution-with-mcp — quantifies why this matters: loading tool/skill definitions into the main agent's window is the dominant context tax (their worked case cuts 150,000 → 2,000 tokens); shipping the 3,900-token skill as the default is that tax, paid every session.

### F2 — `read` of a nonexistent repo returns exit 0 — the agent cannot know it failed

- **Persona · Scope · Surface:** AX (#16) · Tool-affordance / error-as-affordance · CLI (`ghx read`).
- **Evidence (re-derived live):**
  ```
  $ ghx read totally/nonexistent-repo-xyz123 README.md
  === README.md (not found) ===

  EXIT: 0
  ```
  A scripting/agent consumer that checks `$?` reads exit 0 as success and proceeds on empty content. This is the inverse of axprobe's `false_errors` — a **false-success** — and it directly fails the signature test's *"…and know it succeeded"* clause. The skill itself teaches `0 = results, 1 = no results` (skills/ghx/SKILL.md:52,232), so the exit code is a documented contract the tool here violates.
- **Severity:** Likelihood **Medium** (needs a bad slug / stale ref, common in discovery and in agent retries) × Impact **Medium-High** for an agent consumer (silent-wrong is the worst affordance class; a human sees "(not found)", a `$?`-checking agent does not) → **Scoped fix / escalate**. The FRICTION log rates this "soft"; for the *agent* consumer it is under-rated — silent success is exactly the confidently-wrong-at-the-exit-code failure the north star's "evidence, not vibes" tenet is built to prevent.
- **Who judged it & how to check:** Live command above; reproduce verbatim. Already logged with a suggested fix at `docs/dogfood/FRICTION.md:137-143` — this audit's contribution is the AX re-severity (silent-success is a trust failure, not a papercut) and mapping it to the signature test.
- **North-star relationship:** Fails **evidence/auditability** — a report/exit an agent cannot distinguish from success is not auditable. "The sidecar may be opinionated because its trace is visible"; here the *tool* is silent when it should be loud.
- **Disposition:** Needs work → **workstream A4** ("Error messages as agent affordances") / A2 mining batch. Return `ExitNoResults` (1) when zero requested files resolve, or `ExitUpstreamFailure` (3) when the repo/ref 404s.
- **Cross-reference:** Anthropic, *Writing effective tools for AI agents* — https://www.anthropic.com/engineering/writing-tools-for-agents — tools should *"return only high signal information"* and meaningful status, because for an agent the return is a control surface, not a courtesy; a `(not found)` body under exit 0 is the opposite.

### F3 — `inspect` (the highest signal-per-token command) is absent from every doctrine surface

- **Persona · Scope · Surface:** AX (#16) · Token-economics / progressive-disclosure · `ghx skill`, `ghx skill --mcp`, MCP tool set.
- **Evidence:** `ghx inspect --help` describes it as *"collapses the explore → search → map → read loop into a single result"* — i.e. one budgeted call instead of 3-5 round-trips, the strongest signal-per-token move in the CLI. Yet:
  - `grep -n inspect skills/ghx/SKILL.md` → only 2 hits, both prose (the frontmatter description line and a `### Where … how to inspect` header). **`inspect` is not in the skill's Commands block or Chain-of-Thought.**
  - `grep -c tier2 skills/ghx/SKILL.md` → **0**.
  - It is not an MCP tool: `serve.go:146-152` registers explore/read/search/repos/tree/search_tools/code — no `inspect`. Confirmed by empty `grep` for an inspect tool.
  - The skill's own "map before reading, grep before full read" doctrine (SKILL.md:123-128) teaches the *multi-call* loop `inspect` was built to replace.
- **Severity:** Likelihood **Medium** × Impact **Medium** → **Track / scoped fix**. An agent driving via the skill never learns the one command that would cut its recon round-trips; it is a signal-per-token regression baked into the doctrine, but only on the power-user (CLI-driving) path — the recon path doesn't touch it.
- **Who judged it & how to check:** `grep -n inspect skills/ghx/SKILL.md`; `ghx inspect --help`; `grep NewTool internal/cli/serve.go`.
- **North-star relationship:** Fails **cheaper/more-proficient reconnaissance** and **signals-per-token**. NORTH_STAR: *"Every unit of context … should carry maximum reconnaissance signal."* The doctrine surface omits the command that best realizes that.
- **Disposition:** Needs work → **workstream A2/A4**. Either add `inspect` to the CLI skill's Commands + Chain-of-Thought (and consider it as an MCP tool), or — if it is being kept CLI-only deliberately — record that decision, because right now its absence reads as an oversight, not a choice.
- **Cross-reference:** Anthropic, *Effective context engineering for AI agents* — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents — *"finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"*: `inspect` is the CLI's best instance of that principle, and the skill hides it.

### F4 — The report contract has no "this answer is not verified" elevation affordance

- **Persona · Scope · Surface:** AX (#16) · Trust & verifiability of output · report schema (`internal/sidecar/report.go`), recon skill + tool description.
- **Evidence:** `Report` (report.go:38-57) separates `Verified` / `Inferred` / `Unverified` claims — a genuinely good trust structure. But the consumption surface never forces the distinction up to the `answer`:
  - The recon skill (skills/ghx-recon/SKILL.md:41-47) says *"verified … trust these"* and *"Treat inferred or unverified claims as leads"* — advisory prose, not a structural signal.
  - The recon MCP tool description (recontool.go:29) repeats *"verified … trust these"* but says nothing about the case where `verified` is **empty**.
  - My live report had `verified: 3, inferred: 1, unverified: 0` — the good case. Nothing in the schema or surface distinguishes that from a fluent `answer` with `verified: 0` and everything in `inferred`. An agent that reads only `answer` (the field named first, and the one a hurried main agent will grab) cannot tell a fully-evidenced answer from a confidently-guessed one.
- **Severity:** Likelihood **Medium** (the sidecar usually verifies, but discovery / deep / large-repo turns are exactly where it may not) × Impact **Medium** (a confidently-wrong recon report is a severity-4 class failure per the audit skill) → **Track / scoped fix**.
- **Who judged it & how to check:** Read report.go:38-57 and the report JSON at `~/.ghx/sessions/jordancoin-codemap/reports/1-*.json` (`verified`/`inferred`/`unverified` arrays); confirm the recon skill/tool text carries no empty-verified guidance.
- **North-star relationship:** Bears on **evidence/auditability** and the "evidence, not vibes" tenet. The evidence *exists* in the artifact; the gap is that its absence is not made loud on the surface the agent acts from.
- **Disposition:** Needs work → propose an **ADR-scoped report-surface rule**: when `verified` is empty (or `answer` rests only on inferred/unverified claims), the answer surface should carry an explicit unverified banner/field the agent cannot miss — the trust analog of F2's loud exit code.
- **Cross-reference:** Anthropic, *Writing effective tools for AI agents* — https://www.anthropic.com/engineering/writing-tools-for-agents — tools as *"a contract between deterministic systems and non-deterministic agents"* designed for a caller that will act on the return without a skeptical human pause; the contract must make low-confidence structurally visible, not merely available.

### F5 — Cited paths don't compose across repo drift (no repo qualifier)

- **Persona · Scope · Surface:** AX (#16) · Orchestration pillar (does the output compose into the next action) · report schema (`RelevantFile`, `NextReads`).
- **Evidence:** `RelevantFile` (report.go:23-27) is `{Path, Reason}` — no repo field. My live report's `relevantFiles` came back as bare paths (`main.go`, `blast_radius.go`, `handoff/types.go`). Fine when scope holds; but FRICTION.md:77-81 documents the failure mode: on a repo-scoped ask where the agent correctly followed code into a *different* repo, `relevantFiles` returned bare paths while `meta.json` still pinned the original repo — *"Any consumer resolving those paths against the session's repo gets 404s."* The discovery tier already prefixes `owner/repo:path`; the repo-scoped format assumes scope never drifts. `NextReads` (normalized in report.go:151-173) has the same shape.
- **Severity:** Likelihood **Medium** (drift happens whenever code has moved / a monorepo splits) × Impact **Medium** (breaks the compose pillar — the agent's next `read` 404s) → **Track / scoped fix**.
- **Who judged it & how to check:** report.go:23-27; the FRICTION trace at `~/.ghx/sessions/all-hands-ai-openhands/` (compare `reports/1-*.json` relevantFiles vs meta.json repo).
- **North-star relationship:** Bears on **auditability + cheaper recon**: the whole point of `relevantFiles`/`nextReads` is that the main agent (or the sidecar's next turn) can act on them without re-deriving; an unresolvable path forces re-exploration, spending the tokens the report was meant to save.
- **Disposition:** Needs work → adopt the discovery tier's `owner/repo:path` convention everywhere, or add an optional `repo` qualifier to `RelevantFile`/evidence/nextReads. Already an open FRICTION item; this audit frames it as an Orchestration-pillar (composability) defect, not just a cosmetic one.
- **Cross-reference:** Mathias Biilmann, *Introducing AX* — https://biilmann.blog/articles/introducing-ax/ — the four pillars name **Orchestration** (*how the agent combines tools/outputs*) as first-class; a citation the next call can't resolve fails that pillar specifically.

### F6 — Minor doctrine accuracy / completeness nits (low)

- **Persona · Scope · Surface:** AX (#16) · Positioning (machine-readable messaging) / docs accuracy · README, recon skill/tool.
- **Evidence:** README:337 calls the recon skill *"≤ 30 lines"*; it is **47 lines** (`wc -l skills/ghx-recon/SKILL.md`) — 56% over the stated bound. Separately, the recon skill and tool description explain `answer/verified/relevantFiles/uncertainty/nextReads` but never `tierUsed` or `backendsUsed`, which the report carries (`tierUsed: tier1`, `backendsUsed: [remote]` in the live report) and which are exactly the "which tier answered, and why should I trust the depth" signal the north star's visibility contract promises the main agent.
- **Severity:** Likelihood **Medium** × Impact **Low** → **Log**. Individually trivial; grouped because doc claims an agent (or an eval) may check against reality should hold, and because the tier/backend provenance is a trust signal the consumption surface currently drops.
- **North-star relationship:** Weak-but-real: the concise skill *is* the agent's "positioning," so its own accuracy is part of the contract.
- **Disposition:** Needs work → workstream B2 doc pass. Fix the line-count claim; consider surfacing `tierUsed`/`backendsUsed` in the recon skill's "Reading the report" section.
- **Cross-reference:** OpenAI, *Function calling* — https://developers.openai.com/api/docs/guides/function-calling — the guidance to *"describe when (and when not) to use each function"* and keep descriptions accurate applies to the recon skill as the agent's sole selection metadata.

## What I checked and found SOUND (nulls)

- **Error-as-affordance on bad invocations is genuinely good (workstream A4 delivering).** Re-derived live:
  - `ghx read … --start 40` → exit 2, `use --lines START-END, e.g. ghx read owner/repo main.go --lines 40-80` — names the correct next invocation with a worked example.
  - `ghx explroe …` → exit 2, `unknown command "explroe" … Did you mean this? explore`.
  - `ghx explore gkoreli/does-not-exist` → exit + `→ Repository, branch, or path not found. Confirm owner/repo with 'ghx repos <query>' and the layout with 'ghx explore owner/repo' before reading a path.` — a real affordance, not a traceback.
  This is exactly what the AX error-as-affordance scope asks for, and it holds on the paths I tested.
- **The FRICTION "explore malformed slug → exit 3 not 2" item is now FIXED (corrects the open log).** `ghx explore badslug` → exit **2** with `invalid repo "badslug": expected owner/repo, e.g. ghx explore gkoreli/ghx`. The FRICTION.md:129-135 open entry describes exit 3 with no example; the current mainline binary gives exit 2 with an example. That open item should be closed. (The bare-Cobra `ghx explore` with zero args still returns `accepts between 1 and 2 arg(s), received 0` — a lesser, affordance-free message, but the malformed-slug path is fixed.)
- **The recon path is the AX gold standard — the north star working.** Live `ghx sidecar ask --repo JordanCoin/codemap "…entrypoint?"`: 38 s, **exit 0**, accurate answer; every `verified` claim cites the exact `ghx read … --lines` command and what it showed; `relevantFiles` + `uncertainty` present; trailing `artifacts: <session dir> (trace <id>)`. On disk: `verified:3, inferred:1, unverified:0, tierUsed:tier1`, plus `actualCommandLedger` and `traceCommands` (5 each) as ground-truth of what actually ran — auditability made real, not asserted. axprobe rubric: **HIC 0, false_errors 0, goal_reached yes, weak-driver n/a** (adapter = claude-sonnet-5, a reasonable specialist floor).
- **The recon MCP tool description is well-crafted and near-minimal** (recontool.go:29, 935 chars ≈ 230 tokens). It correctly tells the agent to *"ask the goal in plain English … do not step-drive repository exploration yourself,"* enumerates the report fields, and notes automatic session routing — the irreducible floor of main-agent doctrine, and about as small as a self-describing tool can be. This is the right target; F1 is that the *defaults don't route here*, not that this surface is wrong.
- **Exit-code semantics are documented and mostly honored** — `ghx --help` and skills/ghx/SKILL.md:52 both publish `0 ok / 1 no results / 2 bad invocation / 3 upstream`, and 2/3 were honored on every path I tested except F2's `read` false-success.
- **`sidecar doctor` is a strong operator/agent affordance** — PASS output enumerates every check (token, network, ghx binary, tier2 backends with per-backend install hints, ACP handshake, report-sink version match) and points at where artifacts land. Setup friction the north star's dogfood tenet cares about is being actively driven down (config exists out of the box; `--claude-acp` writes the pinned adapter).

## What was not audited (this round)

- **The agent-safety / adversarial-tool-use scope** (indirect prompt-injection via surfaced repo content → report → main agent's next action; lethal-trifecta exposure) — named in the Tier-B menu but deliberately out of this persona's four scopes; flagged for a security-adjacent pass (Willison, *Designing agentic loops* — https://simonwillison.net/2025/Sep/30/designing-agentic-loops/).
- **The MCP `recon` tool's live error affordances** — I reasoned from the schema (`question` Required) but did not drive a live MCP client against `ghx serve --recon`.
- **Token-economics level 2/3** (sidecar-internal ~400-line persona doctrine tax; whole-workflow vs native-Explore delegation) — those need eval artifacts, not this surface pass.
- **Cross-session tool-selection retention** (does an agent keep *choosing* recon over grepping itself across sessions) — the real agent-PMF signal, measurable only in production/eval traces.

## Single least-confident call

**F2's severity.** I am confident the behavior is real (re-derived live: `read <nonexistent-repo>` → exit 0) and that silent-success is the worst affordance class for a `$?`-checking agent. What I am less sure of is whether real main agents route file reads through the bare CLI often enough for this to bite in practice, versus going through the recon sidecar (which wraps and validates). If the dominant real path is recon, F2 is a tool-layer papercut; if agents drive the CLI directly (the power-user skill exists precisely for that), it is a genuine trust hole. Resolving it needs production/eval trace evidence on how often the direct `read` path is exercised — which I could not see from this surface pass.
