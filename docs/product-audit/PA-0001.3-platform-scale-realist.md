# Platform/Scale Realist — ghx product audit (PA-0001.3)

## Abstract

I audited ghx as the thing the north star says it is: a **platform** — a sidecar
that "the outside world talks only to" (NORTH_STAR P3), whose `~/.ghx` artifacts
are "an API surface" the main agent "reads as a first-class consumer"
(NORTH_STAR §cap-3), and whose boundary contract "must survive replacing ACP,
the brain, or both" (tenet "Protocols are stepping stones"). My signature
question: *is our surface a contract other agents can rely on, or just today's
convenient shape?*

The single highest-leverage finding, in north-star terms: **the evidence report
— the literal product ("the report is the product," ADR-0021) — is an
unversioned contract, serialized three different ways across three surfaces, and
described in three places that already disagree.** The team versions its
*eval-internal* artifacts (`judge-bundle-v1`, `judge-config-v1`) but not the
*customer-facing* report. For a product whose defensibility thesis is aggregation
("the tool the agent reaches for") and whose flywheel precondition is a
*trustworthy substrate*, an unversioned, thrice-forked contract is the crack the
flywheel can't turn on. Every downstream consumer the P3/P4 arc invents will be
building on a shape that no policy promises to keep.

Second-order: the persona doctrine that anchors a *pre-registered P4 exit
trigger* measures ~3× smaller than the figure cited to justify it, and the
distribution/selection question ("does the agent choose ghx over the host's
native Explore?") is entirely unmeasured — the two facts that most directly gate
the "below ACP" and "no real competition" claims are both softer than the
strategy docs state.

None of this invalidates the thesis. The producer-side contract (submit_report)
is genuinely rigorous; the data model for provenance is clean; the fixes are
serialization, documentation, and one strategy reconciliation — workstream-sized,
not architectural. But a platform that ships an API surface under a "no
compatibility junk" tenet with no version stamp is one external consumer away
from the exact failure the Platform/Scale Realist exists to prevent.

## Ranked findings

### F1 — The evidence report contract carries no schema version, yet it is consumed over three surfaces and declared an API

**Persona · Scope · Surface.** Platform/Scale Realist · Agent-Experience
contract-stability · report schema (`internal/sidecar/report.go`).

**Evidence.** The `Report` struct — the boundary contract — has **10 fields and
no version marker** (`internal/sidecar/report.go:38-57`). Schema evolution is
encoded by *absence*: `TierUsed string json:"tierUsed,omitempty"` with the
comment "Empty on reports produced before tier tracking" (report.go:45-52).
That is ambiguous by construction — an absent `tierUsed` means *either* "a
producer that predates tier tracking" *or* "tier0 was used"; a downstream
consumer cannot distinguish "old contract" from "cheap answer." Meanwhile the
team demonstrably knows how to version a schema and does it — but only for
eval-internal artifacts: `bundleSchemaVersion = "judge-bundle-v1"` with
`SchemaVersion string json:"schemaVersion"`
(`internal/sidecar/evals/judge_bundle.go:12,36`) and
`judgeConfigSchemaVersion` (`judge_config.go:13`), the latter with a test that
*rejects* `judge-config-v0` (`judge_config_test.go:76`). And ADR-0032.1 S3
freezes-and-hashes the MCP tool schema as a "frozen identity" that "any change
here is a measurement-identity change" (`internal/sidecar/recontool.go:17-26`)
— proving the schema is understood as a driftable identity, but only for eval
reproducibility, never for the consumer's benefit. `grep -rn "schemaVersion"
internal/` returns hits **only** under `internal/sidecar/evals/`; the product
report has none.

**Severity: Medium × High → Escalate now.** Likelihood medium: the schema *has
already* evolved (`tierUsed`, `backendsUsed`, `nextReads` were all added post-M4)
and will again (M7 tier-2, M8 nextReads). Impact high: silent downstream
breakage is the defining platform failure, and it directly negates the flywheel's
"trustworthy substrate" precondition.

**Disposition: needs-work → new ADR** ("Report contract versioning & deprecation
policy"). Minimum: a `schemaVersion` field on the report, a stated
add-only/deprecation rule, and the same reflection-derived-schema discipline
ADR-0021 already applied on the producer side extended to a published consumer
contract.

**North-star relationship.** Bears directly on the tenet *"Protocols are
stepping stones… the boundary must survive replacing ACP, the brain, or both"*
and on §cap-3 (`~/.ghx` / the report "as an API surface"). An unversioned
contract cannot survive a swap the consumer is able to *detect* — the P4 "below
ACP" move silently changes the producer, and no consumer can tell.

**Cross-reference.** [semver.org](https://semver.org/) — the canonical answer to
persona #4's "what's our deprecation/versioning policy, and would a builder
actually trust it?" Right now the honest answer is "there is none for the
report"; a `schemaVersion` + add-only rule is the minimum a builder would trust.

**Who judged it / how to check.** Re-derivable in one command:
`grep -rn "schemaVersion\|SchemaVersion" internal/` (hits only in `evals/`),
then read `report.go:38-57`. Pure structural fact, judge-independent.

### F2 — The *recommended* agent surface (MCP `recon`) returns JSON-plus-trailing-prose — a worse contract than the CLI `--json` envelope for the same service

**Persona · Scope · Surface.** Platform/Scale Realist · contract-stability +
Trust/verifiability · MCP `recon` vs CLI `ask --json`
(`internal/cli/serve.go`, `internal/cli/sidecar.go`).

**Evidence.** `ghx serve --recon` is documented as *"the recommended surface for
a main agent that should delegate reconnaissance"* (`serve.go:57-60`). Its
handler serializes the report to JSON and then **appends two prose lines outside
the JSON**:

```go
data, _ := json.Marshal(report)
text := string(data)
if turn.Route != nil { text += "\n" + turn.Route.Line() }        // "session: X (routed: overlap 0.42…)"
if footer := turn.Artifacts.FooterLine(); footer != "" {          // "artifacts: /path (trace abcd…)"
    text += "\n" + footer
}
return mcp.NewToolResultText(text), nil                            // serve.go:208-221
```

`Route.Line()` (`route.go:208-210`) and `Artifacts.FooterLine()`
(`artifacts.go:40-48`) render **human prose**, not JSON. So a downstream agent
that `JSON.parse`es the recon result breaks on the trailing lines, and one that
string-scans for provenance breaks the moment the footer wording changes. The
*same logical answer* on the CLI path is a clean structured envelope:
`enc.Encode(askEnvelope{Report: report, Artifacts: artifacts, Route: route})`
(`sidecar.go:114`), where `askEnvelope` (`sidecar.go:157-163`) carries `Report`,
`Artifacts`, and `Route` as first-class JSON fields. `ghx-recon/SKILL.md:22-24`
presents MCP and CLI as *"same service, two entry points"* — but they are **not
wire-compatible**, and the recommended one has the degraded contract.

**Severity: High × Medium → Escalate now / scoped fix.** Likelihood high (every
recon call does this); Impact medium (a careful consumer can still recover the
JSON, and today's sole consumer is well-behaved) — but the machine-readable
*visibility* pointer (which session answered, where the audit trail is) is
delivered as regex-bait on the surface the north star recommends for delegation.

**Disposition: needs-work → workstream B.** Return the `askEnvelope` shape (or an
MCP structured-content block) from `handleRecon` so provenance is a field, not a
suffix. The data model already exists (`askEnvelope`, `AskResponse`); this is a
serialization fix, not a redesign.

**North-star relationship.** Violates *"Evidence, not vibes / full visibility as
an API surface"* on the exact surface (§cap-3) the north star names the main
agent's first-class consumption path. Visibility delivered as prose the consumer
must scrape is visibility theater.

**Cross-reference.** [Anthropic — Writing effective tools for AI
agents](https://www.anthropic.com/engineering/writing-tools-for-ai-agents):
tools are *"a contract between deterministic systems and non-deterministic
agents"* — a contract that mixes JSON and prose in one text blob asks a
non-deterministic caller to parse two formats out of one field.

**Who judged it / how to check.** Diff `serve.go:208-221` against
`sidecar.go:111-114`; run `ghx sidecar ask --json "…"` (clean envelope) vs a
`recon` MCP call (JSON+prose). Structural, judge-independent.

### F3 — Distribution/moat: ghx is default in no ecosystem, the true alternative ships zero-install in the primary host, and no eval measures whether the agent *selects* ghx

**Persona · Scope · Surface.** Platform/Scale Realist (platform-aggregation
angle) · Distribution in agent ecosystems + Moat · CLI/MCP surface + evals +
strategy docs.

**Evidence.** Reaching ghx requires an opt-in three-step: `ghx serve --recon`
(`serve.go:73-78`) + MCP server registration + skill install
(`skills/ghx-recon/SKILL.md`). There is **no default-ness anywhere** and **no
measurement of selection**: `grep -rln "tool.selection\|selects ghx\|native
explore\|Explore agent" internal/ docs/evals/ docs/adr/` returns nothing but a
false positive in ADR-0017 research. ADR-0032.1 arm-B wires the recon tool to
measure host-task success *with ghx enabled* — that is an ablation, **not** a
selection test against the true alternative. Per this audit's own guidance the
true alternative is *"the host's native, context-subtracting recon subagent —
e.g. Claude Code's read-only Explore"* (product-audit SKILL.md), which is
**default and zero-install** in ghx's primary host. NORTH_STAR §Moat asserts
*"There may be no real competition in code reconnaissance at all."* But
aggregation theory says the new agent-era Power is *"being the default in
MCP/skill ecosystems (Thompson aggregation / demand-side default),"* while
*"switching cost weakens — an agent can swap tools per-call"* (research/06 §3
row 10). ghx holds **neither** the default nor switching-cost lock-in today; the
only durable moat named is a *future* trained model (M10 → blocked on M9 →
blocked on judge calibration C4). Defensibility therefore rests on being
*selected*, which is un-defaulted and unmeasured.

**Severity: Medium × High → Escalate — verify before dismissing.** Likelihood
medium (a host shipping a strong native Explore is not hypothetical — it exists),
Impact high (if the agent defaults to native Explore, ghx's demand-side
aggregation path never opens and the moat waits entirely on P4).

**Disposition: needs-work → workstream C + strategy note.** Add a
tool-selection eval arm — `plain-host` vs `host + ghx-recon` vs
`host + native-Explore`, measuring which surface the agent *picks* when both are
offered (research/06 §3(g),#8: "tool-selection accuracy"). Amend NORTH_STAR §Moat
to name native-Explore as the selection-time competitor (as the audit's PMF-scope
note already prescribes for ablation baselines).

**North-star relationship.** The moat thesis "the agentic brain, not the tools"
is sound *as a barrier*, but a barrier with no distribution has no benefit to
protect. This is the platform-angle sharpening of the Competitive-Paranoid lens:
being reachable ≠ being selected ≠ being default.

**Cross-reference.** [Ben Thompson — Aggregation
Theory](https://stratechery.com/2015/aggregation-theory/): aggregation Power
comes from owning the *demand-side default relationship* at zero marginal
distribution cost. ghx owns neither today; the whole "no competition" claim
hinges on winning a selection contest it does not yet run.

**Who judged it / how to check.** Re-run the grep above; read ADR-0032.1 arm-B
(measures success-with-ghx, not selection); read NORTH_STAR §Moat. The *absence*
of a selection eval is the finding — verifiable by its non-existence.

### F4 — `~/.ghx` is declared an "API surface" but governed by a "no compatibility junk" tenet with no version stamp

**Persona · Scope · Surface.** Platform/Scale Realist · contract-stability ·
`~/.ghx` artifacts (ADR-0022) + strategy docs.

**Evidence.** NORTH_STAR §cap-3 declares the artifacts *"an API surface"* the
main agent *"reads… as a first-class consumer"* — naming `traces.jsonl`,
`logs.jsonl`, `metrics.jsonl`, `reports/`, ledgers, `live.jsonl`,
`tier-decisions.jsonl` as the surface. ADR-0022 D3-update (lines 195-202) then
applies *"the AGENTS.md engineering tenet ('no legacy maintenance, no
compatibility junk')"* to delete a storage-root migration shim. The session
artifact layout has **no declared version and no stability guarantee**; only the
eval bundles carry `schemaVersion` (F1). The tenet is correct engineering for a
sole-consumer install (which ADR-0022 explicitly notes: *"we are the sole
consumers"*), but the north star's own P3 end state — *"the outside world talks
only to the sidecar"* — manufactures external consumers of exactly these
artifacts, at which point "break freely" and "API surface" are in direct
contradiction.

**Severity: Medium × High → Track, revisit (latent landmine).** Likelihood
medium (currently sole-consumer, so no live breakage — I am *not* claiming a
consumer was broken), Impact high once P3 opens external consumers. This is a
tension flagged early, not a present outage.

**Disposition: needs-work → ADR.** Declare which `~/.ghx` paths are a *stable
contract* (report JSON, OTel traces — the latter already ride the frozen OTel
spec, good) versus *internal scratch* (caches, ledgers), and version the
contract ones. This is the artifact-side companion to F1.

**North-star relationship.** A clean instance of the persona's core tension: an
API surface (§cap-3) governed by a break-freely build tenet. Naming the boundary
now — before external consumers exist — is exactly the "protocols are stepping
stones, the boundary must survive replacement" discipline.

**Cross-reference.** [Brandon Chu — Platform
Management](https://www.mindtheproduct.com/platform-management-by-brandon-chu/)
(persona #4's source): trust is *"the flywheel's grease"* — a versioned,
stability-declared artifact layout is the trust investment; an undeclared one
governed by "no compatibility junk" is the opposite signal to any builder.

**Who judged it / how to check.** Read NORTH_STAR §cap-3 against ADR-0022:195-202;
`ls ~/.ghx/sessions/<name>/` and note no version file. Structural.

### F5 — The report contract is described in three places that already disagree; the consumer-facing docs are a lossy subset

**Persona · Scope · Surface.** Platform/Scale Realist · contract-stability +
Positioning (tool description as "messaging") · report schema vs MCP tool
description vs SKILL.md.

**Evidence.** The Go struct exposes **10 fields** (report.go:38-57). The MCP
`recon` tool description names **6** — *"answer… verified… evidence /
relevantFiles… uncertainty / nextReads"* (`recontool.go:29`) — omitting
`inferred`, `unverified`, `tierUsed`, `backendsUsed`, `commandsRun`.
`ghx-recon/SKILL.md:40-43` names the **same 6**, with the **same omissions**. So
a downstream agent building on the documented contract does not know `tierUsed` /
`backendsUsed` exist — yet those *are themselves a contract* ("ADR-0024.1
Visibility Contract," per the field's own doc-comment, report.go:45-51). The
producer side is single-sourced and clean (reflection-derived `reportInputSchema`,
ADR-0021 D1), but the two *consumer*-facing descriptions are hand-maintained and
have already drifted from the struct they describe.

**Severity: Medium × Medium → scoped fix.** Likelihood medium (drift is already
present), Impact medium (an agent under-reads the tier/backend visibility fields
— degrades the very auditability that is the product's differentiator).

**Disposition: needs-work → workstream B.** Generate the consumer field list from
the `Report` struct (the reflection machinery already exists), or document the
full field set once and reference it from both the tool description and SKILL.md.

**North-star relationship.** The north star's end state is *"a very concise
skill: how to talk to ghx."* Concise is right; *silently lossy* is not — the
skill drops the tier/escalation-visibility fields that make "which tier answered
is always visible in the report" (§cap-1) true.

**Cross-reference.** [Anthropic — Agent
Skills](https://www.anthropic.com/news/skills): progressive disclosure is about
loading the *right* context, not an *incomplete* one; the concise skill should
point at a complete field reference, not silently omit half the schema.

**Who judged it / how to check.** Compare the `json:"…"` tags in report.go:38-57
against the field names in recontool.go:29 and SKILL.md:40-43. Direct.

### F6 — `nextReads` is a promised contract the producer does not enforce; a first-party consumer (M8 anticipation) already could not build on it

**Persona · Scope · Surface.** Platform/Scale Realist · contract-stability ·
report schema + evals (the "if it broke silently, would we find out?" test).

**Evidence.** The persona doctrine promises consumers a strict shape:
*"'nextReads' … Each entry must be ONE concrete repo-relative file path … no
prose, no descriptions, no line ranges"* (`prompt.go:111-115`). But the runtime
normalizer explicitly **keeps prose**:
`if strings.ContainsAny(unwrapped, " \t\n") { // Prose: keep it (lenient
contract) … return trimmed }` (`report.go:167-171`). So the emitted contract and
the promised contract diverge — and the consumer built on the promise, M8
anticipation prefetch, **failed its gate on exactly this**: NORTH_STAR M8 —
*"D1 gate FAILED — nextReads recall 0.071/0.000, field sparse in practice;
prefetch build correctly halted."* This is the persona's signature question —
*"if this broke silently for one downstream consumer, would we find out before
they complained?"* — answered *yes, via a failed gate*. That is a **win for the
eval discipline** and a **loss for the contract design**: the field's promised
shape was never enforced on the producer, so the one consumer that depended on it
could not.

**Severity: Medium × Medium → scoped fix (already in flight).** Likelihood high
that the shape is violated (the normalizer is designed to tolerate it), Impact
medium and *already caught* — net severity lowered because remediation exists.

**Disposition: needs-work → already routed to ADR-0031.2** ("nextReads contract
revision"). This finding *validates* the concern and the existing remediation;
the lesson to carry forward (into F1's versioning ADR): a field a downstream
consumer will depend on must be enforced on the producer, not merely requested in
prose and coerced.

**North-star relationship.** Direct evidence for the moat/flywheel argument:
"full control… with defaults that just work" (§cap-3) requires that the *dials
and fields* the framework exposes actually hold their shape. The honest negative
(committed in the M8 row) is the tenet "negative results committed" working as
intended.

**Cross-reference.** [Postel's law / robustness principle,
RFC 1122 §1.2.2](https://datatracker.ietf.org/doc/html/rfc1122#section-1.2.2):
"be conservative in what you send, liberal in what you accept." ghx is liberal in
what it *accepts from its own producer* (coercion) but has no conservative
enforcement of what it *sends to consumers* — the modern critique of Postel is
exactly that lenient-accept without strict-emit produces contracts no one can
depend on.

**Who judged it / how to check.** Read prompt.go:111-115 (promise) against
report.go:167-171 (non-enforcement) against NORTH_STAR M8 row (the failed gate).

### F7 — The "~400-line persona doctrine" that anchors a pre-registered P4 exit trigger measures 141 lines / ~1.7k tokens, and is already cache-stabilized

**Persona · Scope · Surface.** Platform/Scale Realist · Token economics
(sidecar-internal SPT) · persona doctrine (`internal/sidecar/prompt.go`) +
strategy docs.

**Evidence.** NORTH_STAR cites the tax twice as a decision anchor: §Moat line 95
*"today's ~400 lines of quirky instructions"* and the **pre-registered P4 exit
trigger #2** (line 223) *"a measured SPT plateau attributable to harness overhead
ACP cannot remove (the ~400-line persona doctrine paid every session)."* Measured
directly (in-package, reproducible):

```
BuildPersonaSystemPrompt():          141 lines, 6858 bytes, ~1714 tokens
BuildDiscoveryPersonaSystemPrompt(): 174 lines, 8657 bytes, ~2164 tokens
```

So the rendered doctrine that would be "baked into the weights" (§Moat line 95)
is **~141 lines, ~2.8× smaller** than the cited 400. And it is *already
cache-stabilized*: prompt.go:30-36 documents that the persona was deliberately
moved to the ACP **session-level system prompt** precisely to be *"cache-stable
(single position, never shifts with turn count)"* and to remove per-turn cost
(ADR-0020.1). So "paid every session" is literally true but understates that
ADR-0020.1 already neutralized the *per-turn* and (with prompt caching) most of
the *per-inference* cost the moat argument leans on (§Moat: *"deleting that
preamble alone… makes inference cheaper and faster"*).

**Severity: Medium × Medium/High → scoped fix.** Likelihood medium (the figure is
load-bearing in two strategy passages and a *pre-registered trigger*), Impact
medium-to-high because trigger #2 gates a *costly* P4 rewrite / model-training
decision. A pre-registered exit trigger keyed to a ~3×-inflated, already-amortized
figure could fire on a phantom.

**Disposition: needs-work → doc reconciliation.** Update NORTH_STAR line 95/223
and ADR-0020.1's SPT accounting with the measured figure, and re-derive whether
trigger #2 is anywhere near firing at ~1.7k *cache-stable* tokens. This is the
project's own tenet applied to itself: *"Measured, not aspirational"* (§Moat
line 98).

**North-star relationship.** Bears on the SPT moat thesis and on the
pre-registration discipline the eval stack demands of everything else — a P4
exit trigger is a pre-registered gate and must be as accurate as any eval gate
(AGENTS.md "Visibility and Truthfulness"; AI-PM-Pragmatist / Experimentation-
Rigorist lenses).

**Cross-reference.** [Anthropic — Effective context
engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents):
context is a finite resource *with diminishing marginal returns* — a ~1.7k-token
*cache-stable* system prompt is a very different (and much cheaper) line item
than "400 lines paid every session" implies; the SPT case for P4 should rest on
the measured number.

**Who judged it / how to check.** Reproduce: add a throwaway test in
`internal/sidecar` calling `BuildPersonaSystemPrompt()` / `…Discovery…()` and log
`len`, line count, `len/4`. Pure measurement — judge-independent, no LLM in the
loop.

## What I checked and found SOUND (nulls)

- **The producer-side report contract is genuinely rigorous.** `submit_report`
  (ADR-0021 D1) derives its input schema by reflection from the `Report` struct
  (`reportInputSchema`) and validates via `DecodeReportStrict` —
  `json.Decoder` with `DisallowUnknownFields`, trailing-token check, non-empty
  answer — **with no coercion on this path**. Completion is gated on a valid
  submission; the model sees the exact validation error and self-corrects. This
  is textbook "make invalid states unrepresentable" on the *producer* side. Every
  contract-drift finding above is on the *consumer-facing description/serialization*
  side, not producer validation. **Not a problem.**

- **The schema *is* treated as a versionable identity where it matters for
  reproducibility.** ADR-0032.1 S3 freezes and hashes the MCP tool schema into
  run manifests (`recontool.go:17-26`); eval bundles/configs carry real
  `schemaVersion` strings with rejection tests. The versioning *machinery and
  discipline exist* — F1 is that they aren't applied to the customer report, not
  that the team lacks the capability.

- **Provenance is structurally clean in the data model and the CLI envelope.**
  `askEnvelope{Report, Artifacts, Route}` (sidecar.go:157-163) and
  `ArtifactsRef` / `RouteDecision` are first-class typed values with JSON tags.
  F2 is a *serialization* defect on the MCP path, not a data-model gap — the fix
  reuses existing types.

- **Input dials are validated, not silently coerced.** `handleRecon` rejects an
  invalid `depth` naming the valid set (`serve.go:191-196`) rather than quietly
  defaulting — a correct error-as-affordance on the input contract. Good AX.

- **The recon tool's *call-time positioning* is well-authored.** The description
  (`recontool.go:29`) tells the agent *"do not step-drive repository exploration
  yourself; ask the goal in plain English"* and scopes one-question-per-call —
  strong tool-selection copy. F3's distribution gap is about default-ness and
  *measurement*, not description quality; the messaging is sound.

- **Routing is contract-stable across execution paths.** `RouteQuestion`
  preserves the ADR-0019.1 D2 precedence *"byte-for-byte"* between daemon and
  daemonless paths (route.go:229-233 and comments) — the two runtimes of the same
  service agree on routing semantics. Good platform discipline; I tried to find a
  daemon/daemonless contract divergence and could not.

- **OTel traces ride the frozen open standard exactly.** ADR-0022 keeps
  `~/.ghx` traces byte-spec-compatible with OTLP so third-party tooling works
  "within seconds" (open-source-leverage tenet). The *trace* half of the `~/.ghx`
  API surface is already a versioned, external contract (the OTel spec); F4's gap
  is the ghx-specific artifacts (report JSON, ledgers) around it.

## Least-confident call

**F7's "~400" provenance.** I am highly confident in the *measurement* (141/174
lines, reproducible by the method given) and in the narrow claim that the
rendered doctrine "baked into the weights" is ~141 lines. I am *less* confident
*why* the docs say 400 — it may be a legacy figure from the pre-ADR-0020.1
monolithic prompt, or a count of `prompt.go` source lines (~351) rather than the
rendered doctrine, or it may fold in per-turn context + ledger. My disposition is
therefore "reconcile the figure," not "the figure is wrong about everything" —
the load-bearing point survives either way: a pre-registered P4 exit trigger
should cite the measured, cache-stable token cost, not a round number ~3× larger.

## What I did not audit (axes omitted this round)

Agent-safety/adversarial tool-use (indirect prompt-injection via surfaced repo
content into the report); eval *trustworthiness mechanics* (deferred to
`docs/evals/TRUST.md`); monetization/cost-to-serve; the human-operator
install/first-run layer (persona #14); code correctness/architecture (the
`docs/audits/*` homes). A live Phase-6 weak-driver agent session was out of scope
for a text-only single-persona pass — F3's selection eval is the recommendation
to *build* that measurement, and it should be the next thing run before the "no
real competition" claim is quoted externally.
