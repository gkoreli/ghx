# Platform/Scale Realist — tier-fit of codebase-memory-mcp (PA-0002.2)

## Abstract

I audited one question from the platform seat: should ghx **absorb
`DeusData/codebase-memory-mcp` *entirely* as an internal tool/tier**, the way
NORTH_STAR P3/M7 promises to swallow codemap? My signature question — *is our
surface a contract other agents can rely on, and does this thing plug cleanly
under the platform without changing the contract underneath consumers?*

**Verdict: fits-with-caveats — but the word "entirely" is the caveat, and I
reject it.** The *engine* is a near-ideal Tier-2 backend: a structural-analysis
tool with no LLM ("it relies on your MCP client … to be the intelligence layer",
README) that clones/indexes locally and answers call-graph / impact / reference
questions — the exact job NORTH_STAR §1 hands Tier 2. Better still, it exposes a
documented **one-shot CLI** (`codebase-memory-mcp cli <tool> '<json>'`,
`src/main.c` `CLI_USAGE`) that drops into ghx's *existing* absorbed-subprocess
pattern (`internal/sidecar/tier2/toolrun.go` `subprocessAdapter`) with **zero
architecture change** — the same shape that already carries codemap and ast-grep.
It is MIT-licensed and its cache is redirectable (`CBM_CACHE_DIR`,
`pkg/go/cmd/codebase-memory-mcp/main.go`), so ghx keeps provenance ownership. One
binary would close *two* open watchlist gaps at once — codemap's call-graph reach
**and** the stack-graphs "precise reference/implementor" item ADR-0026 rates
HIGH/HIGH.

The load-bearing finding, in north-star terms: **"absorb entirely" imports the
half of codebase-memory-mcp that is the antithesis of our `remote-first,
escalation explicit` tenet.** Its identity is a *persistent* knowledge graph with
a *background watcher*, *auto-index on session start*, an always-listening *MCP
server*, a *3D UI*, and an installer that writes *pre-tool hooks + instruction
files into 11 agents*. NORTH_STAR is one sentence long on this: "**No clone, no
local index by default**" (l.207). Adopting the tool whole makes ghx *a local
index by default* and re-teaches every main agent to call structural tools
directly — the precise inversion of the sidecar boundary. The disciplined move is
to absorb a **subset** — the engine as a Tier-2 `cli` subprocess backend
(`local:cbm`) — and quarantine every stateful/MCP/distribution surface *behind*
the escalation policy that already gates Tier 2 (ADR-0024.2). Absorb the engine;
refuse the posture.

Second-order: this is a large, pre-1.0 (v0.8.1), fast-moving C binary owning a
14-tool JSON contract — a heavier external dependency than tiny codemap. But
ghx's own pattern already *bounds* that liability (typed not-installed error →
graceful remote-Tier-1 fallback; one-place arg mapping; optional-by-design
backend), so the versioning risk is manageable, not disqualifying — provided the
absorbed cbm **version is pinned in snapshot metadata** and its numbers are cited
with the quality trade its own paper reports, not the README's marketing.

**None of this is a retreat** (AGENTS.md "Competitive analysis is generative"):
the answer to a strong competitor is "what do we take, and where does it plug
in," and the answer here is "the engine, into `internal/sidecar/tier2/cbm.go`."

## Ranked findings

### F1 — The engine is a near-ideal Tier-2 backend, and its `cli` mode plugs into ghx's *existing* absorbed-subprocess pattern with no new architecture

**Persona · Scope · Surface.** Platform/Scale Realist · tier-2 fit + integration
point · `internal/sidecar/tier2/` (ghx) · `src/main.c`, README (target).

**Novelty.** `NEW` (this target); extends the *pattern* proven in ADR-0024.1 /
ADR-0026 absorption watchlist.

**Evidence.**
- The target *is* a Tier-2-shaped tool by its own description: "codebase-memory-mcp
  is a **structural analysis backend** — it builds and queries the knowledge
  graph. It does **not** include an LLM. Instead, it relies on your MCP client …
  to be the intelligence layer" (README, "How It Works"). That is exactly ghx's
  tier-2 contract: dumb structural backend, the *sidecar brain* is the
  intelligence.
- It has a documented **one-shot CLI**, not only a server:
  `#define CLI_USAGE "Usage: codebase-memory-mcp cli [--progress] [--json]
  <tool_name> [json_args]\n"` (`src/main.c`), used as
  `codebase-memory-mcp cli index_repository '{"repo_path":"…"}'` then
  `codebase-memory-mcp cli search_graph '{…}'` (`pkg/npm/README.md`; recompute:
  `/tmp/ghx grep DeusData/codebase-memory-mcp "codebase-memory-mcp cli"`).
- ghx's absorption seam already exists and is generic: `subprocessAdapter` owns
  "PATH discovery with a typed not-installed error, and evidence-capturing
  execution inside the snapshot directory. Codemap and AstGrep embed it"
  (`internal/sidecar/tier2/toolrun.go:53-58`). A `Cbm` adapter is a ~40-line
  sibling of `codemap.go:104-121`. The single owner that both CLI and the future
  runtime call is `Service` (`service.go:176-198`).
- CLI wiring is a copy of an existing block: `ghx tier2 cbm <owner/repo>` next to
  `tier2CodemapCmd`/`tier2AstGrepCmd` (`internal/cli/tier2.go:73-190`), including
  the fail-fast-before-clone `Discover()` guard (l.111-116) and the
  provenance-then-tool-output stderr flow (`tier2Snapshot`, l.39-55).
- Capability superset: cbm resolves **call graphs** "across files and packages
  (import-aware, type-inferred)", **impact analysis** (`detect_changes`),
  **dead-code**, **Cypher** traversal, and precise reference resolution via
  "Hybrid LSP semantic type resolution … structurally inspired by … gopls,
  pyright, tsserver, rust-analyzer" (README, Features). That Hybrid-LSP capability
  is precisely the **stack-graphs** watchlist item ADR-0026 rates *HIGH impact /
  HIGH effort, behind codemap* (`docs/adr/0026-prior-art-landscape.md:441`) — one
  absorption would close it *and* codemap's call-graph reach.

**STRATEGY (exact passage).** NORTH_STAR §1: "Tier 2: when questions demand
deeper structural understanding, the sidecar decides to pull the codebase locally
and run codemapping under the hood — integrating codemap (and repomap-style
analysis) as internal tools" (l.119-124). ADR-0024.1 Decision: "Tier 2 means
**local structural analysis over a cloned repo snapshot**" (l.55). cbm's `cli`
mode fits the *literal* absorption mechanism ADR-0024.1 chose over MCP:
"Subprocess JSON is easiest to test, trace, sandbox, and attribute. MCP/HTTP can
be reconsidered after the always-on daemon owns warm tool lifecycles" (l.384-386).

**North-star relationship.** **PASS** — removes structural reconnaissance from
the main agent's context, keeps the sidecar the decision-maker, and every answer
stays auditable to a recomputable `cli` command (ADR-0024.1 Visibility Contract).

**Severity.** Likelihood High × Impact Medium → **Track / adopt as a scoped
ADR-0024.x tool addition.** Disposition: **sound** (as a *backend*, per F2).

**Verification state.** `self-verified` (persona) — plug-in point re-derived from
ghx source I read and the target's own `src/main.c`/README. Cross-family
adjudication recommended in synthesis for the "supersets codemap+ast-grep" claim.

**Cross-reference.**
[`DeusData/codebase-memory-mcp/blob/main/src/main.c`](https://github.com/DeusData/codebase-memory-mcp/blob/main/src/main.c)
— the `CLI_USAGE` one-shot entrypoint is the integration lever; without it we'd
be forced into MCP-mode absorption that ADR-0024.1 explicitly deferred.

### F2 — "Absorb *entirely*" fails `remote-first`: cbm's identity is a persistent local index + watcher + auto-index + MCP server + agent-installer. Absorb the engine (subset); quarantine the posture

**Persona · Scope · Surface.** Platform/Scale Realist · remote-first compliance ·
NORTH_STAR tenets + target README ("Distribution & operation", "Auto-Index").

**Novelty.** `NEW`. This is the load-bearing pushback on the audit's framing.

**Evidence.**
- cbm's *default* posture is stateful and eager: "**Auto-sync**: Background
  watcher detects file changes and re-indexes automatically"; "Enable automatic
  indexing on MCP session start: `config set auto_index true`" with "new projects
  … indexed automatically on first connection" and "registered with the
  background watcher" (README). It persists to `~/.cache/codebase-memory-mcp/`
  (SQLite) and even commits a `.codebase-memory/graph.db.zst` **into your repo**
  for team reuse (README, "Team-Shared Graph Artifact").
- Its distribution injects itself into the agent directly: "**11 agents, one
  command** — `install` auto-detects Claude Code, Codex CLI, Gemini CLI, Zed,
  OpenCode … — configures MCP entries, **instruction files, and pre-tool hooks**
  for each" (README).
- It is *itself* an MCP server (`server.json`: `"transport": {"type":"stdio"}`,
  14 MCP tools), i.e. a **direct** tool the main agent calls — the same category
  as codemap that NORTH_STAR reframes as a swallowed building block, not a peer.

**STRATEGY (exact passage).** NORTH_STAR tenet, verbatim: "**Remote-first,
escalation explicit.** No clone, no local index by default. Pulling code locally
and codemapping it is a deliberate, visible deeper layer (P3), never silent
magic" (l.207-209). And Non-Goal: "**Teaching every main agent the ghx CLI (the
opposite of the goal).**" (l.268). cbm-as-shipped is a *default* local index with
a *background watcher* and an *installer that teaches 11 agents to call it
directly* — three simultaneous violations if adopted whole.

**The disciplined absorption (subset, not "entirely").** Take the engine as a
Tier-2 `cli` subprocess and force its statefulness *off* at the boundary:
- Run `codebase-memory-mcp cli index_repository` over the **ghx-owned snapshot
  dir** (F1), not over the user's live tree; `CBM_CACHE_DIR` →
  `~/.ghx/cache/tier2/cbm/` so ghx owns provenance and eviction, not `~/.cache`.
- Disable the watcher/auto-index (`auto_watch false`, `CBM_INDEX_SUPERVISOR=0`
  observed in `src/mcp/index_supervisor.c`) so no background process survives the
  turn — matching ghx's "read-only snapshot … Service exposes no mutating
  operations" domain contract (`service.go:40-43`, ADR-0024.1 impl notes).
- Never install cbm's MCP entry, instruction files, or pre-tool hooks into the
  main agent. The escalation policy (ADR-0024.2) decides when `local:cbm` runs;
  the main agent still sees one sidecar and one small skill.

**North-star relationship.** As a *subset behind the escalation gate*: **PASS**.
As "entirely as an internal tool/tier": **FAIL** (remote-first + non-goal).

**Severity.** Likelihood High × Impact **High** (thesis-bearing: a careless
whole-tool absorption inverts the product's core posture) → **Escalate — resolve
the framing before any build.**

**Verification state.** `self-verified`; the remote-first/non-goal reading is a
direct quote — but because it's a High, thesis-bearing finding, it is **not
milestone-citable below cross-family adjudication** (skill Process step 5). Flag
for the distiller.

**Cross-reference.**
[`codebase-memory-mcp#readme` "Auto-Index"](https://github.com/DeusData/codebase-memory-mcp#auto-index)
— the auto-index-on-session-start + watcher defaults are the concrete
remote-first collision; *what we take* is the engine, *what we refuse* is these
defaults.

### F3 — Contract/versioning liability: a pre-1.0 (v0.8.1) C binary owning a 14-tool JSON contract is a heavier dependency than codemap — but ghx's existing pattern *bounds* the blast radius

**Persona · Scope · Surface.** Platform/Scale Realist · contract-stability /
versioning · `server.json`, target release cadence · `toolrun.go`, `service.go`
(ghx).

**Novelty.** `KNOWN-CONFIRMED⟨PA-0001.3 F1: ghx's own report contract is
unversioned⟩` — this finding adds the *external-dependency* delta.

**Evidence.**
- `server.json` pins `"version": "0.8.1"` — pre-1.0, no semver-stability promise,
  and a "checks for updates on startup" auto-updater (README) implies a fast
  release train. The MCP tool schemas (14 tools, complex JSON args like
  `search_graph '{"name_pattern":…,"min_degree":…}'`) are the contract ghx would
  pin to, and DeusData owns every field.
- The dependency is *large*: `internal/cbm/` is pure C with **158 vendored
  tree-sitter grammars compiled in** (`/tmp/ghx tree` shows `grammar_*.c` for
  ~158 languages) — a very different weight class from codemap (a small Go binary)
  or ast-grep (one Rust binary). More surface = more that can break under us.
- **But the blast radius is already bounded** by the pattern F1 reuses:
  `subprocessAdapter.Discover()` returns a *typed* not-installed error so "callers
  can `errors.Is` against it and fall back gracefully" (`toolrun.go:62-81`);
  `internal/cli/tier2.go:111-116` degrades a missing binary to remote Tier-1
  rather than failing the ask; the arg→CLI mapping lives in *one* `Request` type
  (`codemap.go:70-89`) so a cbm CLI change touches one file. A `local:cbm` break
  degrades exactly one *optional* backend, and the escalation policy still has
  remote evidence to fall back on.
- ghx already stamps a version into snapshot metadata (`GhxVersion`,
  `service.go:346`). The fix is symmetric: record the **resolved cbm version**
  (`codebase-memory-mcp --version`) in `SnapshotMetadata` so a cited `cli` command
  is reproducible against the same engine — otherwise ADR-0024.1's "Evidence
  entries cite recomputable commands" (l.259) silently drifts when cbm updates.

**STRATEGY (exact passage).** ADR-0024.1 Visibility Contract: "Evidence entries
cite recomputable commands or artifacts: `ghx tier2 codemap …`, `codemap --json
…`" (l.259-261). A recomputable command is only reproducible if the engine
version is pinned. AGENTS.md Engineering Tenets: "No legacy maintenance, no
compatibility junk" — pinning + typed-fallback is the clean way to hold an
external contract without shims.

**North-star relationship.** Bears on the **evidence-not-vibes** tenet: an
unpinned external engine erodes recomputability. PASS *with* the version-pin fix.

**Severity.** Likelihood Medium × Impact Medium → **Scoped fix → ADR-0024.x:
pin cbm version in snapshot metadata; contract-break test with a fake cbm shim
(mirrors the codemap/ast-grep shims, ADR-0024.1 verification).**

**Verification state.** `self-verified`. The "blast radius bounded" claim is
re-derived from ghx source; the "fast release train" is inferred from the
auto-updater + pre-1.0 version, not measured — flagged.

**Cross-reference.**
[`codebase-memory-mcp/blob/main/server.json`](https://github.com/DeusData/codebase-memory-mcp/blob/main/server.json)
— the `0.8.1` pin and stdio-MCP identity; *what we take* is the `cli` output, *what
we guard* is its schema drift.

### F4 — cbm's statefulness is a liability under remote-first *today* but an asset under B6 (warm daemon) / M8 (anticipation) — absorb the stateless `cli` now, revisit persistent/MCP mode when the daemon lands

**Persona · Scope · Surface.** Platform/Scale Realist · adjacent-opportunity /
sequencing · NORTH_STAR §4 (always-on runtime), M8 · target persistence model.

**Novelty.** `NEW`.

**Evidence.**
- The very property that violates remote-first (a *persistent, incrementally
  maintained* graph — "background watcher … re-indexes automatically",
  "incremental indexing fills in the local diff", README) is exactly what a
  **warm daemon** (B6: "resident, reusable process … no cold starts", NORTH_STAR
  l.161-165) and **anticipation** (M8: "answer … in under a second instead of
  30", l.135-143) want: a pre-warmed index makes an anticipated structural query
  sub-second.
- ADR-0024.1 already wrote the timing rule for this exact tradeoff: MCP/HTTP tool
  mode is "reconsidered after the always-on daemon owns warm tool lifecycles"
  (l.384-386). cbm has *both* a `cli` one-shot and a stdio-MCP server — so the
  same tool can be absorbed **stateless-now** (`cli`, ephemeral per-turn index,
  remote-first-clean) and **warm-later** (MCP under B6, persistent index as an
  escalated cache), with the persistence turned on only inside the daemon's
  visible lifecycle.
- Cost check for stateless-now: cbm claims "average repo in milliseconds",
  "Django full index ~6s" (README Performance) — plausibly cheap enough to index
  a ghx snapshot *per escalation* for small/medium repos; Linux-kernel-scale (3
  min) would need the persistent path, i.e. it self-selects into the B6 future.

**STRATEGY (exact passage).** NORTH_STAR "Working the Loop" / P3 sequencing +
ADR-0024.1 l.384-386. The Moat: "The moat is the agentic brain, not the tools …
they become tiny building blocks the sidecar swallows" (l.78-89) — cbm's
statefulness is a *building-block property to schedule*, not a posture to inherit.

**North-star relationship.** PASS — a sequencing plan that keeps remote-first
intact now and banks cbm's persistence for when the runtime can own it visibly.

**Severity.** Likelihood Medium × Impact Medium → **Track; record as an
ADR-0024.x "phase 2 (warm cbm under B6)" open item.**

**Verification state.** `self-verified`; the "milliseconds/6s is cheap enough per
turn" is the target's unverified marketing claim — **least-confident**, see close.

**Cross-reference.**
[`codebase-memory-mcp#team-shared-graph-artifact`](https://github.com/DeusData/codebase-memory-mcp#team-shared-graph-artifact)
— persistent-graph reuse is the B6/M8 asset; *what we take later* is the warm
index, *gated by* the daemon's visible lifecycle.

### F5 — Part (d): the auto-install-into-11-agents pattern is *half* absorbable — take the MCP-registration mechanism for `ghx serve` (B2); refuse the instruction-file + pre-tool-hook injection (it re-teaches the main agent, the exact non-goal)

**Persona · Scope · Surface.** Platform/Scale Realist · distribution in agent
ecosystems · `ghx serve` (B2) · target `install.sh` model (README).

**Novelty.** `NEW`.

**Evidence.**
- cbm's installer does three distinct things: (1) writes **MCP server entries**,
  (2) writes **instruction files / skills**, (3) writes **pre-tool hooks**, into
  each of 11 detected agents (README "11 agents, one command"; "The `install`
  command auto-detects all installed coding agents and configures MCP server
  entries, instruction files, skills, and pre-tool hooks for each").
- ghx's B2 milestone is literally "**one-command setup**" for "a recon skill,
  single MCP tool" (NORTH_STAR l.311; workstream B2). Mechanism (1) — detect
  installed agents, write the MCP entry for **`ghx serve`** (the *single sidecar
  tool*) — is directly on that path and worth absorbing.
- Mechanisms (2) and (3) are the opposite of the ghx thesis: they push
  *structural-tool knowledge and hooks* into the main agent so it calls the tool
  directly. That is "Teaching every main agent the ghx CLI (the opposite of the
  goal)" (NORTH_STAR Non-Goal l.268) and contradicts the end-state "a main agent
  … needs **zero knowledge of the ghx CLI** … it never loads the ghx skill file
  at all" (l.23-24). ghx's report *is* the interface; it does not want hooks in
  the host.
- Platform note: cbm installing itself as a *direct* MCP tool into 11 agents is
  the same competitive shape ghx has with codemap — a tool bidding for the main
  agent's tool-slot. ghx wins by *not* being a tool-slot but a sidecar; copying
  cbm's "colonize the agent config" distribution would trade that advantage away.

**STRATEGY (exact passage).** NORTH_STAR l.23-28 (zero-CLI end state) + Non-Goal
l.268 + B2 (l.311). The distinction is sharp: **register the sidecar** (aligned)
vs **inject tool doctrine + hooks into the host** (anti-thesis).

**North-star relationship.** Mechanism (1): PASS (advances B2 zero-friction
setup). Mechanisms (2)/(3): FAIL (re-teach the main agent).

**Severity.** Likelihood Medium × Impact Medium → **Track; the detect-and-register
half routes to B2 setup work as a scoped idea, not this audit.**

**Verification state.** `self-verified` from README + `server.json`. I did not
read `install.sh` line-by-line (code-search rate limit, dogfood log) — the
three-part breakdown is from the README's own enumeration; flag as
README-sourced, not code-verified.

**Cross-reference.**
[`codebase-memory-mcp/blob/main/install.sh`](https://github.com/DeusData/codebase-memory-mcp/blob/main/install.sh)
— the auto-detect-and-configure installer; *what we take* is agent detection +
MCP registration for `ghx serve`, *what we refuse* is instruction/hook injection.

### F6 — Trust/DH6: the token-efficiency headline is real, but cbm's own paper reports a *quality trade* (83% vs 92%) the README omits, and "158 languages" (README) vs "66" (paper). If ghx surfaces cbm evidence, cite the trade, not the badge

**Persona · Scope · Surface.** Platform/Scale Realist (trust-of-output lens) ·
target README vs. arXiv:2603.27277 · verify-by-reading doctrine.

**Novelty.** `NEW`.

**Evidence.**
- README: "83% answer quality, 10× fewer tokens, 2.1× fewer tool calls vs.
  file-by-file exploration" and "**158 languages**".
- The paper it cites (WebFetch of
  [arXiv:2603.27277](https://arxiv.org/abs/2603.27277), *"Codebase-Memory:
  Tree-Sitter-Based Knowledge Graphs for LLM Code Exploration via MCP"*, Vogel et
  al., submitted 2026-03-28) abstract states the result as a **trade**: "**83%
  answer quality versus 92% for a file-exploration agent**, at ten times fewer
  tokens and 2.1 times fewer tool calls," across **66** languages. The graph path
  is *lower quality, far cheaper* — not a strict win, and the README drops the
  "versus 92%" comparator and inflates 66→158.
- Implication for absorption: cbm is a **signals-per-token** play (perfectly
  aligned with The Moat, "The optimization target is signals per token", l.91),
  but its structural answers trade ~9 points of quality for the token savings. As
  a Tier-2 backend that feeds ghx's evidence report, its findings must be
  **verified by reading** before ghx claims them — which is already ghx doctrine
  ("verifies candidates by reading before claiming", NORTH_STAR l.132) and the
  ADR-0029.2 tier-2 citation persona rule.

**STRATEGY (exact passage).** AGENTS.md Visibility/Truthfulness: "we must not lie
to ourselves or our customers"; NORTH_STAR "Evidence, not vibes. Every sidecar
answer carries files, commands, snippets, backends, and uncertainty" (l.202-204).
Absorbing cbm's *numbers* uncritically would import a marketing overclaim into
ghx's evidence surface.

**North-star relationship.** PASS *iff* ghx cites cbm's quality/token trade
honestly and verifies cbm findings by reading — the tenet is a guardrail on how
we present an absorbed backend, not a reason to reject it.

**Severity.** Likelihood Medium × Impact Low → **Log; becomes a doctrine line in
the tier-2 citation persona (ADR-0029.2) if cbm is absorbed.**

**Verification state.** `cross-checked` against primary source (arXiv abstract
via WebFetch) — the README/paper discrepancy is directly quoted from both.

**Cross-reference.**
[arXiv:2603.27277](https://arxiv.org/abs/2603.27277) — the primary benchmark; the
"83% vs 92%" line is the honest framing ghx must carry if it cites cbm.

## What is actually fine (nulls — checked and found sound)

- **The seam is ready; no re-architecture.** I looked for a reason the tier2
  package couldn't take a fourth backend and found none: `subprocessAdapter`
  (`toolrun.go:53-127`) is generic PATH-discovery + capture; `Service` is the
  documented single owner both CLI and runtime call (`service.go:176-198`);
  adding `local:cbm` is a `cbm.go` sibling + one CLI block + one policy signal.
  The ADR-0024.1 "Implementation Shape" *anticipated* more tools.
- **License is clean.** `LICENSE` is MIT ("Copyright (c) 2025 DeusData") — matches
  AGENTS.md "MIT in, MIT out" for absorption. No copyleft lineage risk.
- **Provenance ownership is preservable.** `CBM_CACHE_DIR`
  (`pkg/go/cmd/codebase-memory-mcp/main.go`) lets ghx point the DB under
  `~/.ghx/cache/tier2`, so cache location/eviction stay ghx's — the ADR-0024.1
  "cache is provenance, session dir is evidence" contract holds.
- **Graceful degradation is already the pattern.** A missing/broken cbm binary
  degrades to remote Tier-1 exactly like codemap (`internal/cli/tier2.go:111-116`);
  cbm being optional is the *default* behavior, not new work.
- **Remote-first is enforceable for free.** The escalation policy (ADR-0024.2)
  already gates *when* any Tier-2 backend runs; `local:cbm` inherits "escalate
  only when `local` is in `AllowedBackends`, on explicit signals" — cbm does not
  get to self-trigger.
- **Competitive posture is correct, not fearful.** Per AGENTS.md
  "Competitive analysis is generative," a strong, paper-backed competitor doing
  the structural-backend job is a *supply of building blocks*; the audit's job is
  "what do we take," and F1 answers it. cbm does not threaten the moat (the
  brain); it's a bigger codemap.

---

## What argues AGAINST / where it does NOT fit

- **"Entirely" is the wrong verb (F2).** The persistent index, background watcher,
  auto-index, MCP server, 3D UI (`localhost:9749`), team-shared `graph.db.zst`,
  `manage_adr` tool, and 11-agent installer are all *out of scope* for
  reconnaissance and several actively fight remote-first / the sidecar boundary.
  Absorbing the tool whole imports its posture; absorbing the engine does not.
- **Heavy dependency for a sidecar that prizes leanness (F3).** A pure-C binary
  with 158 compiled grammars, pre-1.0, auto-updating, is a much larger thing to
  pin and trust than codemap. It's a *dependency-weight* regression even if the
  capability is a gain.
- **Redundancy / re-architecture cost, not free addition.** ghx *already ships*
  codemap + ast-grep + repomap (ADR-0024.1 slices 1-2, all live-verified). cbm
  overlaps most of that (importers, deps, structural search, ranking-adjacent
  centrality). Adding it may mean **replacing** codemap+ast-grep with one engine —
  a migration and re-measurement cost, not a bolt-on — and the ADR-0024.1
  rationale for *starting* with codemap (HIGH/MED, small, easy to sandbox) still
  argues for keeping the small tools unless cbm measurably beats them.
- **Semantic/vector search may be SPT-negative.** cbm bundles Nomic embeddings for
  `semantic_query`; ghx has no evidence that local vector search beats remote ghx
  `search` on signals-per-token. Unmeasured; do not absorb that surface on faith.
- **Moat caution.** cbm is well-funded, academically published, and moving fast at
  *exactly* the "structural memory for agents" job. Absorbing its engine is smart;
  mistaking that for owning the moat is not. The defensible layer remains the
  brain that *decides to escalate and how to verify* (NORTH_STAR The Moat) — cbm
  gives ghx a sharper Tier-2 knife, not a strategy.

---

## Verdict, plug-in point, top risk, least-confident call

**Verdict: fits-with-caveats.** The **engine** is an excellent Tier-2 backend and
plugs into ghx's existing absorbed-subprocess pattern with no architecture change
(F1) — and it would close the codemap call-graph gap *and* the stack-graphs
precise-reference gap in one MIT-licensed tool. **But absorbing it "entirely"
does not fit** (F2): its persistent-index / watcher / auto-index / MCP-server /
11-agent-installer identity is the antithesis of `remote-first, escalation
explicit` and of the sidecar boundary. Absorb a **subset** — the engine as a
`local:cbm` Tier-2 `cli` subprocess — and quarantine every stateful/distribution
surface behind the ADR-0024.2 escalation policy.

**Concrete plug-in point (ghx file).**
`internal/sidecar/tier2/cbm.go` — a new `Cbm` adapter embedding
`subprocessAdapter` (`toolrun.go:53-58`), backend ID `local:cbm`, a `CbmRequest`
type mapping to `codebase-memory-mcp cli <tool> '<json>'` with `CBM_CACHE_DIR` →
`~/.ghx/cache/tier2/cbm` and watcher/auto-index forced off; owned by `Service`
(`service.go:176-198`), wired as `ghx tier2 cbm` in `internal/cli/tier2.go`
(clone of the codemap block l.73-136), gated by an escalation signal in
`policy.go` (ADR-0024.2). Governed by a new **ADR-0024.x** before build.

**Top risk.** Remote-first tenet violation by absorption creep: cbm's *reason to
exist* is a persistent local index with a background watcher, and adopting it
without forcibly disabling that posture turns ghx into "a local index by default"
— the one thing NORTH_STAR l.207 forbids — while its 11-agent installer would
re-teach the main agent the non-goal (l.268). The mitigation is architectural
(subprocess behind the escalation gate, `CBM_CACHE_DIR`, watcher off), so the
risk is one of *discipline*, not feasibility.

**Least-confident call.** Whether **stateless per-turn indexing** (index the ghx
snapshot fresh each escalation, preserving ephemeral remote-first semantics) is
fast/valuable enough on *real* repos to be worth adopting *now* — the README's
"average repo in milliseconds / Django ~6s" is the target's own unverified claim,
I did not benchmark it on a ghx snapshot, and cbm's headline quality is a *trade*
(83% vs 92%, F6), not a win. If per-turn indexing is too slow, the honest answer
is "wait for B6 and absorb cbm warm" (F4) — which means the *right time* to
absorb, more than the *whether*, is the open question. A measured cbm-vs-codemap
tier-2 bake-off (token cost, latency, answer quality on the ADR-0024.1 smoke
repos) should precede the ADR-0024.x decision.
