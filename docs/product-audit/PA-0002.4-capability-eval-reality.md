## Abstract

I audited the **absorb-`DeusData/codebase-memory-mcp`-entirely** proposal as the
**AI PM Pragmatist** (#15). My reflex: distrust a capability claim with no
calibrated eval behind it; *interview the tool, don't trust the demo*; ask
"what traced, calibrated eval backs this, and who scored it, from what
evidence?" The target is unusually inviting to that reflex because it *leads*
with numbers — "99% fewer tokens," "158 languages," "sub-ms queries," "an arXiv
paper." So I chased each number back to its source.

**The headline: the claims are partly real and partly inflated, and the paper's
own evidence quietly argues *against* the marketing.** The arXiv preprint is
real (arXiv:2603.27277, resolves, five named authors, 28 Mar 2026, **preprint —
not peer-reviewed**). But its abstract measures **83% answer quality versus 92%
for the file-exploration baseline** — the knowledge graph is **9 points
*worse* on answer quality** — at **10× fewer tokens** (= 90% fewer), on 31
repos. The "**99% fewer tokens**" splashed across the repo description is not
that number: it is a **5-query microbenchmark** ("99.2% reduction … ~3,400 vs
~412,000 tokens," `README.md:240`) against a **file-by-file grep strawman**,
an order of magnitude more aggressive than the paper. "**158 languages**" is the
tree-sitter *grammar* count; the paper parses **66**; semantic ("Hybrid LSP")
resolution — the part that makes the graph *accurate* — covers **9–11**. And
the "answer quality" score is assigned by the vendor's **own LLM-as-a-Judge**,
whose plan admits a "documented 10–25% self-preference inflation" when judge and
answer-writer share a model family (`docs/EVALUATION_PLAN.md:558-564`).

**Verdict on "absorb entirely": no — and the framing is the first error.** It is
a **173 MB pure-C** codebase with vendored grammars, a persistent SQLite index,
and a localhost 3D-graph UI server. ghx is Go and **already absorbed the
overlapping 80%** — codemap, ast-grep, and a native repomap ranking engine are
live tier-2 backends behind an escalation policy (`internal/sidecar/tier2/service.go:185-187,393`;
ADR-0024.1/.2). The genuinely *additive* 20% (a persistent queryable
call-graph via Cypher, community discovery, semantic/BM25 search) is worth
**evaluating as one more tier-2 backend**, on **ghx's own ablation**, on the
narrow question class where the paper shows it even competes — never absorbing
whole, and never on the vendor's benchmark.

Severity is Likelihood × Impact on a 3×3. Every finding ties to the
Visibility/Truthfulness tenet: *who scored this, from what evidence, and how do
I check it myself.*

## Ranked findings

### F1 — "99% fewer tokens" is a microbenchmark against a strawman; the paper's own generalizable number is 10× (90%), *at a 9-point answer-quality cost*

**Persona · Scope · Surface.** AI PM Pragmatist · capability-claims / evals-as-user-research · target `README.md`, arXiv abstract.

**Novelty.** NEW (target-specific).

**The claim (quoted).** Repo description (verified via `gh api`): *"158 languages,
sub-ms queries, **99% fewer tokens**."* README body: *"**120x fewer tokens** — 5
structural queries: ~3,400 tokens vs ~412,000 via file-by-file search"*
(`README.md:36`) and *"Five structural queries consumed ~3,400 tokens … versus
~412,000 tokens via file-by-file grep exploration — a **99.2% reduction**"*
(`README.md:240`).

**The flaw (named).** Three different token numbers circulate — **99%**, **120×**,
**10×** — and the one that ships in the description is the *least* defensible.
The 99%/120× figure is a **5-query microbenchmark** whose denominator is
*reading whole files* ("file-by-file grep exploration," 412K tokens). The
**paper's 31-repo study reports 10× fewer tokens** (= 90%), i.e. an order of
magnitude below the headline. Worse, the same abstract states the graph scores
**"83% answer quality versus 92% for a file-exploration agent"** — the token
saving is bought with a **9-point (≈10% relative) quality regression** that the
marketing never mentions. For a tool sold to reduce an agent's context tax, a
buyer who reads only the badge sees "100× cheaper" and misses "and somewhat less
correct." **Recompute:** `gh api repos/DeusData/codebase-memory-mcp/contents/README.md --jq .content | base64 -d | grep -nE '99%|120x|412,000'` and compare to the abstract at `arxiv.org/abs/2603.27277`.

**North-star relationship.** Directly bears on ghx's **signals-per-token** optimization
target (`NORTH_STAR.md:91`, "The optimization target is signals per token"). A
backend that raises tokens-saved but *lowers* signal correctness has an
ambiguous SPT effect — it must clear a correctness floor, not just a token
ceiling. It also fails ghx's anti-pattern guard against **capability claims with
no eval** (the whole reason this persona is near-mandatory here).

**Severity.** Likelihood High × Impact Medium → **Track / gate before absorbing.**
The number is real *somewhere*, but absorbing on it would import the strawman.

**Disposition.** *Sound.* Routes to Workstream C (measure the real delta in
ghx's harness, F5) before any absorption decision.

**Verification state.** `self-verified` — recomputed from the raw README and the
resolving abstract. Medium finding; no cross-family adjudication required.

**Cross-reference.** [README.md L240 "99.2% reduction"](https://github.com/DeusData/codebase-memory-mcp/blob/main/README.md)
(the microbenchmark) vs [arXiv:2603.27277 abstract](https://arxiv.org/abs/2603.27277)
("ten times fewer tokens … 83% answer quality versus 92%") — the exact gap
between marketing and the tool's own paper.

### F2 — "158 languages" is a parse-grammar count; capability degrades sharply as you move from "parses" to "graphs" to "resolves semantically"

**Persona · Scope · Surface.** AI PM Pragmatist · capability-claims · target `README.md`, badges, abstract.

**Novelty.** NEW.

**The claim (quoted).** Badge + description: *"languages-158."* README: *"158
languages, all parsed via vendored tree-sitter grammars … Benchmarked against 64
real open-source repositories"* (`README.md:561`), followed by a ~100-entry list
prefixed *"Also supported (not yet benchmarked)"* (`README.md:569`).

**The flaw (named).** "158" is the count of *bundled tree-sitter grammars*, not
the count of languages the knowledge graph actually understands. The capability
tiers down hard: the **paper parses 66**; the graph-extraction benchmark covered
**64 repos**; **Hybrid-LSP semantic type resolution** — the layer that makes
call-chains and types *correct* rather than heuristic — is a badge-advertised
**9 languages** (README enumerates ~11). So "158 languages" for a *code
intelligence* claim is like advertising a dictionary's page count as vocabulary:
true, and misleading about the thing that matters. An agent asking "what calls
X" in, say, Zig or COBOL gets bare tree-sitter parsing, not the graph the badge
implies. **Recompute:** count Hybrid-LSP languages in `README.md` §hybrid-lsp
vs the "158" badge vs the paper's "66."

**North-star relationship.** ghx's tier-2 already scopes structural precision to a
handful of well-supported languages (`mapengine` autodetects Go/TS/JS/Python/Rust
per ADR-0024 research). Importing "158 languages" as a headline would set an
expectation ghx cannot honor and the target cannot either — a **trust-and-verifiability**
violation (`AGENTS.md` Visibility/Truthfulness) if ghx repeated it.

**Severity.** Likelihood High × Impact Low → **Log.** Not a blocker; a caution
against parroting the number.

**Disposition.** *Sound.* Note in any absorption ADR: quote the 9–11 semantic-
resolution languages, never "158."

**Verification state.** `self-verified` from README + abstract.

**Cross-reference.** [README languages section](https://github.com/DeusData/codebase-memory-mcp/blob/main/README.md)
("158 … tree-sitter grammars … Also supported (not yet benchmarked)") vs the
abstract's "66 languages" — the parse-vs-understand gap.

### F3 — "83% answer quality" is scored by the vendor's own uncalibrated LLM judge; the same self-preference regime ghx's TRUST ledger is *explicitly* engineered to close

**Persona · Scope · Surface.** AI PM Pragmatist · evals-as-user-research / trust & verifiability · target `docs/EVALUATION_PLAN.md`.

**Novelty.** NEW; cross-links KNOWN-CONFIRMED⟨ghx C4/ADR-0023.1, TRUST.md H1⟩.

**The claim (quoted).** Abstract: *"83% answer quality."* Who scored it, from the
target's own plan: *"Grading is done by an **LLM judge agent**, not by hand"*
(`EVALUATION_PLAN.md:516`); *"a **same-family judge** carries a documented
**10–25% self-preference inflation** … Prefer a judge from a *different* family
than the answer-writing agent"* (`:558-564`).

**What is genuinely good (state it plainly).** This is a **more rigorous
disclosure than most vendor benchmarks**: blind A/B labeling with randomized
order (`:523`), a **position-bias swap check** (`:555-556`), **verification-
required** capping unconfirmable claims at 0.5 (`:557`), and ground-truth
grep/read access for the judge (`:526`). Credit where due — they *named the
self-preference risk themselves*.

**The flaw (named).** It remains a **vendor self-evaluation by an LLM judge with
no human-label calibration** (no κ against annotators anywhere in the plan; the
bias *checks* mitigate position bias, not absolute-score validity). The
answer-writing agent is Claude-family; if the judge is too, the disclosed
**10–25% inflation** rides on both the 83% and the 92% — and the *un-verifiable*
piece is exactly which judge model the paper's run used (plan says "named in
`SUMMARY.md`"; I could not extract it — see could-not-verify). The one robust
signal that survives any judge bias is the **relative** result, and it points
the wrong way: **graph 83% < explorer 92%.** Notably, this is the *same
self-preference regime* the product-audit skill itself flags (arXiv:2404.13076)
and that ghx's own judge layer is being **held-from-citation until κ ≥ 0.6
against founder hand-labels** (`NORTH_STAR.md:348-353`; ADR-0023.1; TRUST.md H1).
**ghx's own standard for a citable quality number is strictly higher than the
one behind "83%."**

**North-star relationship.** Bears directly on **Evals-are-how-we-know** and
Visibility/Truthfulness: *"never present a judge opinion as ground truth"*
(`AGENTS.md:141`). Absorbing on "83% answer quality" would mean citing an
eval ghx itself would not yet let past its own gate.

**Severity.** Likelihood High × Impact Medium → **Escalate before citing.** Do
not repeat "83%/92%" as fact in an absorption ADR without the self-eval caveat.

**Disposition.** *Sound.* The number is directional evidence, not a citable
quality result — treat it as a hypothesis to re-test in ghx's harness (F5).

**Verification state.** `self-verified` (methodology recomputed from the target's
own `EVALUATION_PLAN.md`); the specific judge model is `could-not-verify`.

**Cross-reference.** [EVALUATION_PLAN.md L558-564](https://github.com/DeusData/codebase-memory-mcp/blob/main/docs/EVALUATION_PLAN.md)
(self-preference disclosure) ↔ [ghx TRUST.md H1 / ADR-0023.1 κ-gate](../evals/TRUST.md) —
the vendor discloses the hole ghx is engineering shut.

### F4 — "Absorb entirely" is the wrong verb: it is a 173 MB pure-C tool that overlaps ghx's *already-absorbed* tier-2 by ~80%; only a thin slice is additive

**Persona · Scope · Surface.** AI PM Pragmatist / (borrowing Platform-Realist) · absorption / overlap · `internal/sidecar/tier2/`, ADR-0024.x, target repo metadata.

**Novelty.** NEW; KNOWN-CONFIRMED⟨ADR-0024 already absorbed codemap/ast-grep/repomap⟩.

**The claim under test.** The audit prompt: *should ghx absorb `codebase-memory-mcp`
**entirely**.*

**The flaw (named).** Two independent reasons "entirely" fails.

1. **It is a pure-C, 173 MB, single-static-binary tool** (`gh api` → `language: C`,
   `size: 173308` KB) with vendored grammars, a persistent SQLite index at
   `~/.cache/codebase-memory-mcp/`, and a localhost:9749 3D-graph UI server. ghx
   is Go. "Absorb entirely" degenerates to either (a) shelling out to an opaque
   C binary that maintains its own persistent index (a far heavier dependency
   than codemap, which is Go and stateless-per-call) or (b) a reimplementation.
   Neither is "swallow the tool" in the NORTH_STAR P3 sense — that sense is a
   *tier-2 backend behind the sidecar brain*, which is a **slice**, not the whole
   173 MB.

2. **ghx already absorbed the overlapping majority.** `internal/sidecar/tier2/service.go`
   is *"the single owner of the Tier-2 substrate"* and already wires *"the
   absorbed codemap adapter"* (`:185`), *"the absorbed ast-grep adapter"*
   (`:187`), and a native repomap where *"there is no external binary behind
   local:repomap"* (`:393`), over blobless+sparse snapshots (`clone.go`), gated
   by an escalation policy (`policy.go`, ADR-0024.1/.2). Tree-sitter symbol
   extraction (ghx `mapengine`), import/dependency graph (codemap), structural
   search (ast-grep), and PageRank-style ranking (repomap) are **already
   present**. codebase-memory-mcp re-implements all four.

   The genuinely **additive** delta is narrow: a **persistent, queryable
   call-graph via Cypher**, **community discovery / impact analysis / change
   detection**, and **bundled semantic (nomic-embed) + BM25 FTS5 search**
   (`README.md:155-156`). That is a real capability ghx's *on-demand,
   per-question* tier-2 lacks — but it is the 20%, and it arrives welded to the
   80% ghx already owns and a persistent-index maintenance burden ghx's
   **remote-first, no-local-index-by-default** tenet (`NORTH_STAR.md:207`)
   deliberately avoids. **Recompute:** `grep -nE 'absorbed|repomap|codemap|astgrep' internal/sidecar/tier2/service.go`.

**North-star relationship.** Passes the **Open-Source-Leverage** filter *only* as
selective absorption (*"what — from one idea to the whole thing — do we take, and
where does it plug in,"* `AGENTS.md:211`), and only if the north-star filter
(does it make recon cheaper/more proficient) is satisfied by measurement, not
by the badge. "Entirely" fails the Picasso rule's companion clause — *hand-roll
/ adopt-whole only when nothing existing serves*, and ghx's tier-2 already
serves the overlapping part.

**Severity.** Likelihood High × Impact High (on the audit's own thesis) →
**Stop & resolve: reject "entirely," scope to a backend evaluation.**

**Disposition.** *Invalidates* the "absorb entirely" framing. Re-routes to: an
ADR-0024-family evaluation of the *knowledge-graph backend* as a tier-2 option,
decided by F5's ablation.

**Verification state.** `self-verified` from ghx source + `gh api`. High finding;
the reject-entirely call is **not milestone-citable** until an independent
(ideally cross-family) reviewer confirms the overlap accounting — I flag it
`self-verified only`, needs adjudication before it gates a real decision.

**Cross-reference.** [ghx service.go absorbed adapters](https://github.com/gkoreli/ghx/blob/mainline/internal/sidecar/tier2/service.go)
↔ [target README architecture](https://github.com/DeusData/codebase-memory-mcp/blob/main/README.md) —
what ghx already has vs the additive graph slice.

### F5 — The only honest way to price this: a pre-registered ghx ablation on ghx's own tasks and judge — *not* the vendor's 31 repos vs a file-by-file strawman

**Persona · Scope · Surface.** AI PM Pragmatist · evals-as-user-research · `internal/sidecar/evals/`, ADR-0032.1, ADR-0019.2, ADR-0016.8.

**Novelty.** NEW (proposal).

**The claim under test.** *"If absorbed as a tier-2 backend, what would it move for
ghx?"* The Pragmatist's answer: **we do not know, and the vendor benchmark cannot
tell us** — different baseline (file-by-file, not ghx-sidecar's already-16.6×-
compressed recon per C3), different task mix, uncalibrated same-family judge
(F3). Interview the tool on *our* tasks.

**Proposed ablation (`ghx-sidecar` vs `ghx-sidecar+graph`).**

- **Arms.** (1) `ghx-sidecar` — existing tier-2 (codemap/ast-grep/repomap).
  (2) `ghx-sidecar+graph` — tier-2 backend = codebase-memory-mcp run as an MCP
  subprocess over the **existing** blobless+sparse snapshot the tier-2 `Service`
  already produces (`clone.go`), so the clone/cache cost is shared and isolated
  out. Optionally (3) native-Explore as the "true alternative" baseline
  (product-audit skill's note) and (4) plain, for the standard ladder.
- **Task scope — narrow, deliberately.** Only the **cross-file / graph-native /
  discovery** question class: "what calls X," "blast radius / what breaks if I
  change Y," "hub detection," "caller ranking," "which repos/modules do X." These
  map to the escalation signals already enumerated in `policy.go` and the
  discovery fixtures of ADR-0019.2. **Exclude single-file tasks** — ADR-0024's
  own cited evidence ("Code Isn't Memory," arXiv:2606.22417) says grep suffices
  there, and the target's own abstract only claims graph parity on **19 of 31**
  even for graph-native queries. Diluting across the full suite would wash out a
  real effect that lives in one question class.
- **Metrics — ghx's, not theirs.** Three-level SPT (main-agent / sidecar-internal
  / whole-workflow, ADR-0016.6); deterministic correctness gates (fact recall,
  the frozen backstop); and the LLM **judge scorer once C4's κ ≥ 0.6 lands**
  (never before — same discipline F3 faults the vendor for skipping).
- **Pre-registered gate (before the run — the tenet).** Reuse the ADR-0032.1
  vector-verdict shape: the graph arm must show **correctness non-inferiority**
  (δ ≈ 0.05–0.10 — i.e. it must *not* reproduce the paper's 9-point 83%-vs-92%
  regression on ghx's distribution) **AND SPT superiority** on the cross-file
  subset. Fail non-inferiority ⇒ the vendor's own regression replicated ⇒
  reject the backend. Win both ⇒ absorb *the graph slice* as a gated tier-2
  option, visible in `backendsUsed` like every other tier-2 (ADR-0024.1 C1).
- **Guards.** Memorization/contamination canary (ADR-0016.8 C3 contamination
  guard) — the paper's 31 repos and ghx fixtures may sit in training data; and
  end-to-end latency accounting that **includes** index build + clone, not the
  "sub-ms" steady-state number (F1/could-not-verify).

**North-star relationship.** This *is* the Evals-are-how-we-know tenet applied to
an absorption decision: *"token efficiency and effectiveness are measured, never
assumed"* (`NORTH_STAR.md:181-184`). It converts "27.9k stars and an arXiv
paper" into a go/no-go ghx can defend to itself and quote externally.

**Severity.** Likelihood High × Impact High (this is the deliverable) → **do this
before any integration line is written.**

**Disposition.** *Needs work → Workstream C* (eval task authoring + a tier-2
backend arm) and an **ADR-0024-family decision ADR** gated on its result.

**Verification state.** `self-verified` proposal; the ablation's *result* is by
construction the thing that would be `cross-family-adjudicated` (the judge is
non-Claude per ADR-0023.1's cross-family preference — which also neutralizes the
exact self-preference F3 flags in the vendor's run).

**Cross-reference.** [ADR-0032.1 combined-objective non-inferiority gate](../adr/0032-combined-objective-host-task-evals.md)
(the reusable gate shape) · [ADR-0019.2 discovery fixtures](../adr/0019.2-discovery-eval-tasks.md)
· ["Code Isn't Memory" arXiv:2606.22417](https://arxiv.org/abs/2606.22417)
(why to scope to cross-file tasks) — the machinery to run this already exists.

## What is actually fine (nulls — equal rigor)

- **The arXiv paper is real and the authors are not phantoms.** arXiv:2603.27277
  resolves, five named authors (Vogel, Meyer-Eschenbach, Kohler, Grünewald,
  Balzer), 28 Mar 2026. I attacked "is there even a paper" and found a paper.
  It is a **preprint, not peer-reviewed** — noted, not a knock; ghx cites
  preprints too (ADR-0024 cites arXiv:2606.22417).
- **The benchmark methodology is above vendor average, and self-critical.** Blind
  A/B, randomized order, position-bias swap re-judging, verification-required
  scoring, ground-truth access, and a *self-authored* self-preference disclosure
  (F3). I expected demo-ware; I found a genuine evaluation plan. The flaw is
  no-human-calibration and vendor-run, not fabrication.
- **The abstract does not overclaim quality.** Refreshingly, the *paper* reports
  the graph as slightly *worse* on answer quality (83% vs 92%) and frames the
  win as tokens/tool-calls. The overclaim lives in the *marketing*, not the
  research — an honest paper wrapped in a hype badge.
- **"Sub-ms queries" is plausible for what it measures.** Indexed SQLite/Cypher
  lookups on a prebuilt graph at <1ms on an M3 Pro is believable. It is simply
  *steady-state query latency*, not end-to-end recon cost — true-but-partial,
  not false.
- **The overlap is real, which is *good* news.** ghx having already absorbed
  codemap/ast-grep/repomap means the integration surface for the additive graph
  slice is small and well-precedented (ADR-0024.1/.2), not greenfield.

## Least-confident call

**Whether the knowledge-graph backend would move ghx's signals-per-token *net
positive* on ghx's own task distribution is genuinely unknown — and the
available evidence leans mildly *discouraging*.** The vendor's own paper shows a
9-point answer-quality regression and graph parity on only 19/31 even for
graph-native queries; but that is the wrong baseline (file-by-file, not
ghx-sidecar), the wrong task mix, and an uncalibrated same-family judge, so it
cannot settle ghx's question either way. Only F5's ablation can. **I would not
bet the integration on the vendor numbers in either direction** — I'd bet on the
narrow cross-file question class showing an SPT win *if* the persistent graph's
call-chain traversal beats ghx's per-question codemap/repomap there, and I hold
that as a hypothesis, not a finding.

**Second-least-confident:** I verified the abstract and the arXiv page resolve via
a WebFetch summarizer, and the eval *methodology* from the repo's own
`EVALUATION_PLAN.md`, but **could not extract the paper PDF's body** (compressed
streams) — so *which* judge model the reported run used, and thus whether the
83%/92% carry the same-family inflation the plan warns about, **remains
unverified**. That single gap is the one Pragmatist question I could not fully
close; it lives in the paper's Experimental Setup / the run's `SUMMARY.md`.
